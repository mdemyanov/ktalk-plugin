# Реализация: синхронизация промт-слоя с ломающим изменением `ktalk-cli` 2.0.0

**Capability:** `openspec/specs/release-delivery-tails/spec.md` (шаг 2b, chunking-контракт шага 2
— тот же периметр, что и предыдущие раунды синхронизации промт-слоя анализа).

Пакет `ktalk-cli` закрыл issue #5 (`ktalk-mcp`, ветка `epic-cli-open-issues`): `get-transcript`
получил включённую по умолчанию сверку идентичности транскрипта (`identity_check`,
`--no-verify-identity` отключает). Побочно — ломающее изменение формы JSON чанкированного
ответа: тело чанка (`result`/`chunk`/`total_chunks`/`has_more`/`total_characters`) уехало под
ключ `transcript`, рядом появился `identity_check`. Владелец решил: конверт остаётся, версия
пакета 2.0.0, плагин синхронизируется в этой же волне. Задача — механическая: без правки шага 2b
(собственная сверка идентичности плагина, ADR-026 Д4 — переделка на чтение `identity_check`
вынесена в followup, это смена поведения агента, не синхронизация контракта).

## Что было неочевидно

**Для маленьких (нечанкованных) транскриптов конверт НЕ появляется.** Проверено чтением
исходников `ktalk-cli` (`formatters.py`, функция `render_transcript_output`; `cli_content.py`,
функция `_render_transcript_with_identity`): когда `total_characters <= chunk_size`, CLI возвращает голый markdown
(не JSON) даже с флагом `--json` — `_render_transcript_with_identity()` пытается распарсить
вывод как JSON, ловит `JSONDecodeError` и печатает как есть, без `identity_check` вовсе. Поэтому
описание в `agents/ktalk-processor.md` для малых транскриптов («comes back as plain markdown»)
осталось верным без изменений — правки потребовал только ветвь большого (чанкованного)
транскрипта.

**`references/ktalk-processor/two-pass-analysis.md` правки не потребовал.** Файл упоминает
`total_chunks`/`total_characters` только как концепции (оценка номера чанка по таймкоду,
фронтматтер сохраняемого файла) — не как путь разбора JSON-ответа. Разбор формы ответа целиком
описан в вызывающем `agents/ktalk-processor.md` (шаг 2); дублировать контракт во втором файле не
требовалось.

**Бамп `compat.json` тянет за собой скрытую связность в `test-onboard.sh`.** Часть ассертов
(`stub_uv_installs`, `stub ktalk 0 "ktalk-cli <версия>"`) гоняют реальный
`$ROOT/scripts/ktalk-onboard.sh` против РЕАЛЬНОГО `$ROOT/compat.json` — литерал пина захардкожен
в фикстуре (`1.0.0`), не читается из файла динамически. Найдено запуском (не «на глаз»): после
правки `compat.json` без синхронной правки этих литералов 15 из 106 ассертов упали. Прецедент
уже задан коммитом переименования пакета (`35b3f06`, «Гейты: test-onboard.sh 106/0») — тогда
литералы обновлялись тем же коммитом, что и пин. Обновлены только литералы, СВЯЗАННЫЕ с реальным
деревом (`"$SCRIPT"` без `MIRROR*`-префикса); блоки 47-56 (`MIRROR48`…`MIRROR56`) несут
СОБСТВЕННЫЙ синтетический `compat.json` и не тронуты — они самодостаточны и не зависят от
реального пина. Тесты на асимметрию пина (`1.2.3` «новее пина 1.0.0») сдвинуты на `2.5.0`, чтобы
сохранить намерение сценария («новее»), а не просто перестать падать случайным совпадением кода
возврата.

**README.md несёт живой регресс-гард на этот же пин** (тест 45: `grep -q "$PKG==$PIN"
README.md`) — команда установки правилась синхронно с `compat.json`, иначе гейт `test-onboard.sh`
поймал бы расхождение сам.

**Снимок AC-1 (`EXPECTED_PROMPT_LAYER_SHA256`) перебазирован пятый раз** — тот же ритуал, что и
в 1.9.0/1.10.0/1.11.0: sha256 всего содержимого `skills/+agents/+commands/+references/`,
подъём minor-версии плагина тем же коммитом (NFR-25), дневниковая запись причины прямо над
константой.

## Что осталось без изменений (и почему)

- `references/ktalk-processor/two-pass-analysis.md`, `references/ktalk-processor/vault-update-
  and-report.md` — не описывают форму JSON-ответа, только концепции чанкинга/отчёта.
- Шаг 2b `agents/ktalk-processor.md` (146-165) — логика не читает `identity_check`,
  переделка вынесена в followup по прямому указанию владельца.
