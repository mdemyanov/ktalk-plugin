# Реализация: синхронизация промт-слоя с ломающим изменением `ktalk-cli` 2.0.0

**Capability:** `openspec/specs/release-delivery-tails/spec.md` (шаг 2b, chunking-контракт шага 2
— тот же периметр, что и предыдущие раунды синхронизации промт-слоя анализа).

Пакет `ktalk-cli` закрыл issue #5 (`ktalk-mcp`, ветка `epic-cli-open-issues`): `get-transcript`
получил включённую по умолчанию сверку идентичности транскрипта (`identity_check`,
`--no-verify-identity` отключает). Побочно — ломающее изменение формы JSON чанкированного
ответа: тело чанка (`result`/`chunk`/`total_chunks`/`has_more`/`total_characters`) уехало под
ключ `transcript`, рядом появился `identity_check`. Владелец решил: конверт остаётся, версия
пакета 2.0.0, плагин синхронизируется в этой же волне. Задача — механическая: без правки шага 2b
(собственная сверка идентичности плагина, ADR-026 Д4 — переделка на чтение `identity_check`
вынесена в followup, это смена поведения агента, не синхронизация контракта).

## Что было неочевидно

**Первый раунд этой заметки нёс неверную находку — исправлено по замечанию координатора.**
Утверждение «для маленьких (нечанкованных) транскриптов конверт НЕ появляется даже с `--json`»
было получено ЧТЕНИЕМ исходников и оказалось неверным: `render_transcript_output(data, "raw",
...)` при `--json` зовёт `format_raw(data) == json.dumps(data)` — то есть уже валидный JSON, и
`_render_transcript_with_identity()` успешно его парсит и заворачивает в конверт. Голый markdown
без конверта отдаётся ТОЛЬКО без флага `--json` (там вместо конверта — хвостовая строка
`[identity-check] <result>`), а шаг 2 плагина всегда зовёт с `--json`. Опровергнуто ПРОГОНОМ
(не чтением) координатора и перепроверено здесь тремя фактическими вызовами (см. «Прогоны-
доказательства» ниже). Конверт `{"transcript": ..., "identity_check": ...}` присутствует
ВСЕГДА при `--json`, независимо от размера; различаются только два содержимых `.transcript`:

- малый транскрипт (≤30000 символов, один фетч) — полный сырой объект транскрипта: массив
  `tracks`, у каждого трека `speaker` (ссылка на пользователя) и `chunks` (таймкодированные
  реплики: `startTimeOffsetInMillis`, `text`). Полей `result`/`total_chunks` нет вовсе;
- большой транскрипт (постранично) — объект страницы: `result` (JSON-массив
  плоских, отсортированных по времени записей `{speaker, timestamp_ms, text}` для этой
  страницы), плюс `chunk`/`total_chunks`/`has_more`/`total_characters`.

Ни то, ни другое не готовая проза — `agents/ktalk-processor.md` теперь прямо говорит: перед
анализом/сохранением превратить записи в строки `**Speaker** [HH:MM:SS]: text`.

**Смежная находка тем же прогоном — «снять задвоенный заголовок» тоже была неточной.**
Исходная инструкция шага 2 («strip the duplicated heading from every chunk but the first»)
описывает markdown-чанкинг (`chunk_transcript_markdown` — заголовок `# Транскрипт` правда
повторяется в каждом чанке). Но при `--json` действует `chunk_transcript_raw` — там заголовка
нет вовсе, `result` каждой страницы — самостоятельный JSON-массив записей. Инструкция переписана:
парсить `result` каждой страницы, конкатенировать массивы записей по страницам подряд. Дефект не
привнесён 2.0.0 — судя по коду, был неточным и раньше; вскрыт этим раундом верификации, попутно
с проверкой находки координатора (тот же самый шаг, тот же файл).

**Прогоны-доказательства** (рабочая копия пакета `ktalk-cli`, ветка `epic-cli-open-issues`,
`uv run python -c "..."` — вызовы `render_transcript_output()` + `_render_transcript_with_identity()`
напрямую):

1. Малый транскрипт, `--json` (`fmt="raw"`, chunk=0, размер < 30000): вывод —
   `{"transcript": {"status": "done", "transcriptId": "T1", "tracks": [...]}, "identity_check": {"result": "match"}}`
   — конверт есть, `.transcript` = полный объект.
2. Большой транскрипт, `--json` (размер > 30000, chunk=0): вывод —
   `{"transcript": {"result": "...", "chunk": 1, "total_chunks": N, "has_more": bool, "total_characters": M}, "identity_check": {"result": "match"}}`
   — конверт есть, `.transcript` = объект страницы.
3. Малый транскрипт, БЕЗ `--json` (`fmt="markdown"`): вывод — `"# Транскрипт\n[identity-check] match"`
   (и `"[identity-check] not_checked (timeout)"` при передаче `reason`) — конверта нет,
   `identity_check` — хвостовая строка. Этот путь плагин не вызывает; упомянут в промте только
   чтобы не путался с путём `--json`.

**`references/ktalk-processor/two-pass-analysis.md` правки не потребовал.** Файл упоминает
`total_chunks`/`total_characters` только как концепции (оценка номера чанка по таймкоду,
фронтматтер сохраняемого файла) и предполагает читаемый текст с таймкодами в собранном
транскрипте — это условие теперь выполняется явной инструкцией «отрендерить в `**Speaker**
[HH:MM:SS]: text`» в `agents/ktalk-processor.md` (шаг 2), а не самим `two-pass-analysis.md`.
Дублировать разбор формы ответа во втором файле не требовалось.

**Бамп `compat.json` тянет за собой скрытую связность в `test-onboard.sh`.** Часть ассертов
(`stub_uv_installs`, `stub ktalk 0 "ktalk-cli <версия>"`) гоняют реальный
`$ROOT/scripts/ktalk-onboard.sh` против РЕАЛЬНОГО `$ROOT/compat.json` — литерал пина захардкожен
в фикстуре (`1.0.0`), не читается из файла динамически. Найдено запуском (не «на глаз»): после
правки `compat.json` без синхронной правки этих литералов 15 из 106 ассертов упали. Прецедент
уже задан коммитом переименования пакета (`35b3f06`, «Гейты: test-onboard.sh 106/0») — тогда
литералы обновлялись тем же коммитом, что и пин. Обновлены только литералы, СВЯЗАННЫЕ с реальным
деревом (`"$SCRIPT"` без `MIRROR*`-префикса); блоки 47-56 (`MIRROR48`…`MIRROR56`) несут
СОБСТВЕННЫЙ синтетический `compat.json` и не тронуты — они самодостаточны и не зависят от
реального пина. Тесты на асимметрию пина (`1.2.3` «новее пина 1.0.0») сдвинуты на `2.5.0`, чтобы
сохранить намерение сценария («новее»), а не просто перестать падать случайным совпадением кода
возврата.

**README.md несёт живой регресс-гард на этот же пин** (тест 45: `grep -q "$PKG==$PIN"
README.md`) — команда установки правилась синхронно с `compat.json`, иначе гейт `test-onboard.sh`
поймал бы расхождение сам.

**Снимок AC-1 (`EXPECTED_PROMPT_LAYER_SHA256`) перебазирован дважды в этом же раунде** — тот
же ритуал, что и в 1.9.0/1.10.0/1.11.0: sha256 всего содержимого
`skills/+agents/+commands/+references/`, дневниковая запись причины прямо над константой.
Второй раз — сразу после первого, той же волной: содержимое `agents/ktalk-processor.md` ещё раз
изменилось при исправлении неверной находки, minor-версия плагина повторно не поднималась
(1.12.0 уже строго больше базы origin/main, гейту NFR-25 достаточно).

## Что осталось без изменений (и почему)

- `references/ktalk-processor/two-pass-analysis.md`, `references/ktalk-processor/vault-update-
  and-report.md` — не описывают форму JSON-ответа, только концепции чанкинга/отчёта; условие
  «текст с таймкодами» теперь обеспечено инструкцией по рендерингу в шаге 2.
- Шаг 2b `agents/ktalk-processor.md` (162-184) — по прямому указанию владельца НЕ переписан на
  чтение `identity_check`, это отдельное решение (followup). Проверено также, что 2b НЕ
  опирается на снятое различение «малый=markdown/большой=JSON»: фраза «extract the speaker
  names mentioned in it» формулирована безразлично к форме содержимого (текст или сырые поля
  `tracks[].speaker`/`result`-записи) и не потребовала правки.
