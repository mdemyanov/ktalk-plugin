# Реализация: код возврата `3` у `ktalk-cli` 2.1.0 (`get-transcript`)

**Capability:** `openspec/specs/release-delivery-tails/spec.md` (шаг 2b, chunking-контракт шага
2 — тот же периметр, что и предыдущие раунды синхронизации промт-слоя анализа).

Пакет `ktalk-cli` 2.1.0 ввёл код возврата `3` для `get-transcript --json` (и только для этой
команды): тело ответа полно и валидно, но независимая сверка идентичности транскрипта
(`identity_check.result == "mismatch"`) не сошлась. До этой правки промт-слой трактовал любой
ненулевой код как несостоявшийся вызов — валидный транскрипт при коде 3 был бы выброшен как
ошибка.

## Что сделано

- `compat.json`: пин `2.0.0` → `2.1.0` (точный пин, не порог, ADR-022).
- `README.md`: команда установки и проверка версии в «Быстром старте» синхронизированы с пином.
- `agents/ktalk-processor.md` (шаг 2, место фактического вызова `get-transcript`): рядом с
  описанием конверта `transcript`/`identity_check` добавлено объяснение кода `3` — тело валидно,
  парсить как обычно, код сам по себе не повод откатываться или ретраить как при сетевой ошибке.
  Явно сказано, что это НЕ вторая параллельная логика: последующее решение остаётся целиком за
  шагом 2b (собственная сверка плагина по именам спикеров), который код возврата не читает и не
  менял поведения.
- `skills/ktalk-registry/SKILL.md` и `skills/ktalk-registry/references/registry-format.md`:
  общая формула «ненулевой код = отказ» получила оговорку-исключение для `get-transcript`.
- `scripts/test-onboard.sh`: синхронизированы литералы, зависящие от РЕАЛЬНОГО `compat.json`
  дерева (`stub ktalk 0 "ktalk-cli 2.0.0"` → `2.1.0` и т. п., тот же класс скрытой связности, что
  и в предыдущем раунде синхронизации с 2.0.0); rc-суффиксные тесты (42) сдвинуты на `2.1.0rc1`/
  `2.1.0-rc1`, чтобы усечённое значение по-прежнему численно совпадало с текущим пином — иначе
  регресс-тест перестал бы проверять найденный ранее дефект и просто совпадал бы кодом возврата
  случайно. Снимок AC-1 (`EXPECTED_PROMPT_LAYER_SHA256`) перебазирован, дневниковая запись — над
  константой.

## Что НЕ сделано и почему — конфликт, не решённый исполнителем

Постановка задачи прямо запрещала поднимать `.claude-plugin/plugin.json` («это решение
координатора»). Тем же исполнением задета область NFR-25 (`scripts/check-plugin-composition.sh`,
`check_prompt_version_sync()`): правка `agents/`, `skills/ktalk-registry/` требует подъёма
minor-версии плагина, иначе гейт заявляет `FAIL`. Обе версии (база `origin/main` и рабочее дерево)
равны `1.13.0` — гейт падает предсказуемо и единственно по этой причине; факт проверен прогоном
(`bash scripts/check-plugin-composition.sh`), остальные проверки того же скрипта и весь
`scripts/check.sh --full` — зелёные.

Версия НЕ поднята этим коммитом. `scripts/check-plugin-composition.sh` и, соответственно,
`scripts/check.sh --full` остаются в состоянии `FAIL` до решения координатора: поднять minor
плагина этим же изменением или явно расширить перечень исключений NFR-25. Это не дефект
синхронизации exit code 3 — все остальные критерии приёмки задачи выполнены и подтверждены
прогонами.

## Прогоны-доказательства

```
uv venv /tmp/vv_dev002 && VIRTUAL_ENV=/tmp/vv_dev002 uv pip install --no-cache "ktalk-cli==2.1.0"
/tmp/vv_dev002/bin/ktalk --version   → ktalk-cli 2.1.0
```

Семантика кода 3 подтверждена чтением исходников пакета
(`ktalk_cli/cli_content.py::cmd_get_transcript`, строки 196-198: `identity_check.get("result")
== "mismatch"` → `return 3`, после того как тело уже напечатано) и таблицей кодов возврата в
METADATA пакета 2.1.0 (строка «Только `ktalk get-transcript`. Данные получены и напечатаны
полностью…»).

bash scripts/test-dual-channel-delivery.sh → PASS=38 FAIL=0 SKIP=0
