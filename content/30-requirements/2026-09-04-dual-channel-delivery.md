## Описание

Предмет — что видит потребитель на каждом из двух каналов поставки плагина `ktalk` и что
обязано совпадать между ними. Не предмет: механизм зеркалирования (какой процесс запускает
push на релизном теге, где он исполняется) и точная строка имени маркетплейса второго
канала — это проектные решения SA (ADR-027). Не предмет и открытый архитектурный вопрос
ADR-025 «самообнаружение устаревания плагином» — он остаётся за тем решением и здесь не
пересматривается ни в одну сторону.

Санкция оператора (зафиксирована 2026-09-04) задаёт состав публичного репозитория как вход,
не как предмет анализа этого требования: `github.com/mdemyanov/ktalk-plugin` — публичный,
payload-only (`.claude-plugin/`, `agents/`, `commands/`, `skills/`, `references/`, `scripts/`,
README, LICENSE); `content/`, `openspec/`, `.nauta-*`, `.gitlab/`, `.githooks/`, `docs/`,
`CLAUDE.md`, `AGENTS.md`, `CONTRIBUTING.md` не публикуются; источник истины — внутренний
GitLab, GitHub — одностороннее зеркало без обратной автосинхронизации.

## Почему имена маркетплейсов обязаны различаться, а не совпадать

Оба канала сегодня закономерно тяготеют к одному и тому же имени маркетплейса —
`.claude-plugin/marketplace.json` внутреннего канала уже несёт `"name": "ktalk-plugins"`
(`python3 -c "import json;print(json.load(open('.claude-plugin/marketplace.json'))['name'])"` →
`ktalk-plugins`), и раз GitHub-зеркало копирует тот же `.claude-plugin/` payload-ом один в
один, оно унаследует тот же файл и то же имя, если ничего не изменить намеренно. Наблюдаемое
следствие — коллизия записи в `~/.claude/plugins/known_marketplaces.json` потребителя, который
решит добавить оба канала: платформа хранит маркетплейсы по имени, и вторая команда `add` либо
молча перезапишет источник первой, либо откажет непредсказуемо для потребителя — ни один из
исходов не даёт потребителю способа держать оба канала одновременно.

Требование к наблюдаемому поведению — эти два исхода не равноценны, и данное требование
выбирает первый: имена обязаны быть различимы, так чтобы потребитель, добавивший оба канала,
видел в списке маркетплейсов две разные записи, а не одну затёртую другой. Причина выбора —
не гипотетическая: у одного и того же человека может быть причина добавить оба канала
одновременно (сверка публичного зеркала с внутренней копией при диагностике отставания, работа
на две организации), и цена различимости имён — разовая правка одной строки JSON — заметно
ниже цены немой потери одного из двух источников у того, кому оба нужны сразу. Конкретная
строка имени для публичного канала — решение SA (ADR-027): здесь важен только сам факт
несовпадения, проверяемый сравнением строк `name` двух файлов `marketplace.json`, а не то, как
оно достигнуто.

## Почему совпадение между каналами — проверяемый факт, а не декларация

Три конкретных признака, а не слово «синхронно»: версия плагина (`plugin.json.version`), пин
зависимости (`compat.json` целиком) и состав файлов payload — для одного и того же релизного
тега все три обязаны быть идентичны на обоих каналах. Каждый признак проверяется отдельной,
уже существующей на сегодня командой сравнения (`diff`/чтение JSON), без изобретения нового
инструмента: разойдись хотя бы один из трёх между тегом на GitLab и тем же по номеру тегом на
GitHub — это дефект зеркалирования, а не повод считать зеркало «версией для другой аудитории».
Плагин один, поставочных поверхностей у него теперь две — но не два разных продукта.

## Почему путь установки обязан называть оба канала текстом

README сегодня называет ровно один путь установки (`/plugin marketplace add` с адресом
внутреннего GitLab, шаг 2 «Быстрого старта») — это верно для аудитории, у которой уже есть
доступ к внутреннему GitLab, и неприменимо для внешнего участника, дошедшего только до
публичного GitHub-репозитория. С появлением второго канала документация, которая продолжает
называть только один путь, перестаёт быть полной инструкцией для второй половины своей
аудитории — тот же класс разрыва, который ADR-025 Д3 уже устранял для одного канала (README
называл только половину команд обновления), только на уровне выбора канала, а не команды
внутри канала. Формулировка «источник истины» / «одностороннее зеркало» — не техническая
деталь для внутреннего читателя, а условие, без которого внешний участник не может понять,
куда нести issue и почему изменение через pull request на зеркале не попадёт в код автоматически.

## Почему отставание зеркала называется по своему собственному состоянию, а не по SLA

Между релизом на GitLab и push'ем на GitHub существует окно — операторская санкция называет
его прямо («источник истины — внутренний GitLab; GitHub — одностороннее зеркало, обновляется на
релизном теге; обратной автосинхронизации нет»). Числового порога задержки это требование не
вводит: в проекте нет измерения времени между релизом и push'ем зеркала, а красные линии
`CLAUDE.md` и методология не позволяют вписывать метрику, для которой нет измерения (раздел
«Красные линии» ниже; SLA здесь не открытый вопрос, который стоило бы передавать SA — это
метрика, которую methodология прямо запрещает придумывать без измерения).

Вместо порога — наблюдаемый признак, различающий два состояния без обращения к владельцу
плагина: если версия отсутствует на GitHub, потребитель смотрит на самый свежий тег, который
там реально есть. Тег ниже запрошенной версии означает «релиз существует, зеркало ещё не
подтянуло его» — состояние, совместимое с односторонней, не мгновенной синхронизацией.
Отсутствие любого тега этого номера при заведомо более старшем самом свежем теге на зеркале
означало бы другое — версию, которая никогда не публиковалась. Различие видно потребителю без
привилегированного доступа к внутреннему GitLab: оно целиком читается из состояния самого
зеркала.

## Почему дырка в гейте состава — это NFR с проверяемым критерием, а не заметка на будущее

`scripts/check-plugin-composition.sh` уже содержит проверку на первый известный внутренний домен
продукта (строка 65) — механизм ловли внутреннего литерала в payload у гейта уже есть, только для
одного домена. Чтение того же файла подтверждает: второй внутренний домен,
`doc-hub.gitlab.yandexcloud.net`, тем же гейтом не ловится, при этом
`grep -rn "doc-hub\|yandexcloud" --include="*.md" -l . --exclude-dir=.git --exclude-dir=content`
называет ровно те два файла, где он сегодня встречается, — `README.md` (текст, который
предполагается публиковать) и `CLAUDE.md` (в payload не входит по санкции оператора, но остаётся
находкой для гигиены дерева). Публикация README с этим доменом на публичном канале без починки
гейта была бы утечкой внутренней инфраструктуры при каждом релизе — тот же класс регресса,
который уже случался с retired-именем пакета (урок 2026-09-02) и был закрыт для него по одному
и тому же принципу: авторитетная проверка, не память человека при каждом релизе.

## Почему обращение с публичного канала не автоматизируется

GitHub-issue и pull request на публичном репозитории — новый входной канал, которого у плагина
не было: раньше весь трафик обращений шёл во внутренний трекер `tools-ai/ktalk-plugin`,
управляемый теми же людьми, что и код. Санкция оператора называет режим приёма прямо: «issue и
PR на GitHub принимаются, но переносятся руками» — то есть обязательное свойство обращения не
«автоматический перенос», а «подтверждение источника истины + перенос человеком со ссылкой».
Автоматический перенос или автоматическое закрытие issue на публичной стороне добавили бы
скрытую логику синхронизации именно там, где решение об одностороннем зеркале сознательно её
исключает (санкция оператора, п. 3) — тихое расширение обратного потока было бы отступлением от
уже принятого решения, а не нейтральным техническим удобством.

## Инварианты и защитные ограничения

**По существу:**
- Имя маркетплейса публичного канала не совпадает буквально с именем маркетплейса внутреннего
  канала.
- Для одного и того же релизного тега версия плагина, пин `compat.json` и состав payload
  идентичны на обоих каналах.
- Ни один файл публичного payload не называет внутренний GitLab-домен литералом.
- Ни один issue или pull request на публичном зеркале не вливается и не закрывается
  автоматической синхронизацией без ручного шага человека.
- GitHub-репозиторий не несёт `content/`, `openspec/`, `.nauta-*`, `.gitlab/`, `.githooks/`,
  `docs/`, `CLAUDE.md`, `AGENTS.md`, `CONTRIBUTING.md` — состав ограничен payload-only списком
  санкции оператора.

**Чувствительный контент:** N/A — требование описывает состав и наблюдаемое поведение двух
каналов поставки плагина, не оперирует транскриптами, участниками встреч или токенами контура.
