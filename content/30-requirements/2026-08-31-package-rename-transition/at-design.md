# Тест-дизайн: переход `ktalk-mcp` → `ktalk-cli` (пин 1.8.0)

**Capability:** `openspec/specs/package-rename-transition/spec.md`
**Требование:** [2026-08-31-package-rename-transition.md](../2026-08-31-package-rename-transition.md)
**ADR:** `content/00-project/adr/ADR-024-package-rename-transition.md`
**Архитектура:** `content/40-architecture/2026-08-31-package-rename-transition.md`

Задача QA-001, эпик `ktalk-plugin-foz`, лист `.17`. Предмет — пять свойств перехода на новую
идентичность пакета: сохранение имени команды `ktalk`, схема `compat.json`
(`package_name`/`package_version`), различимость `wrong_package`/`outdated`/`slot_collision`
по коду возврата, отказ от автоматического `--force`, порядок отката (ADR-024 Д4). Стабы
живут в `scripts/test-onboard.sh` (тесты 47–56, продолжение нумерации существующей сьюты).
Дерево пакета (`ktalk-mcp` → `ktalk-cli`, снятие MCP-слоя, идентичность в рантайме) — своя
задача QA-author, `content/40-architecture/at-design-package-rename-transition.md` того
репозитория; здесь только граница интеграции (см. «Не покрыто исполнимым стабом»).

## Сквозные (не отдельный `#### Scenario:`, но явно требует брифа QA-001)

- **Outcome#2 брифа — идентичность параметризована, не литерал.** Тест 55: зеркало с
  ПРОИЗВОЛЬНЫМ, не встречающимся в реальности `package_name` в `compat.json` — если команда
  ремонта называет ИМЕННО это произвольное имя, `pin_name()` реально читает файл; тест на
  буквальное совпадение с «ktalk-cli» был бы vacuous (совпадение сегодня случайно, и осталось
  бы совпадением после ручной правки литерала на новое имя, не решая проблему по существу —
  тот же класс ловушки, что уже нашёл SA-001 в `cli.py:381` дерева пакета).

## Мутации, доказывающие небутафорность тестов

- **Тест 47 (checksum, зелёный сегодня).** Мутация: `echo "" >> skills/ktalk-registry/SKILL.md`
  → пересчитанный sha256 (`171290ac…`) разошёлся с ожидаемым (`658d4111…`) → ассерт стал бы
  красным. Правка отменена (`git checkout --`), рабочее дерево не тронуто.
- **Тест 56 (пустой `package_name` → `20`, изолированный сценарий сравнивается со схожим кодом,
  не с реальным `ktalk-onboard.sh`).** Прогнаны на изолированной scratch-функции ДВЕ версии
  будущей `pin_name()`: наивная (`[ -n "$raw" ] || { printf ''; return 0; }` — пустая строка
  трактуется как «ограничения нет») вернула `rc=0`; fail-closed (`[ -n "$raw" ] || return 1`)
  вернула `rc=1`. Тест 56 (ожидает код `20` у `cmd_check`) отличил бы эти два пути — с наивной
  реализацией `cmd_check` продолжил бы дальше вместо немедленного `20`.
- **Идентичность не хардкод (outcome#2, симметрично тесту дерева пакета).** См.
  `content/40-architecture/at-design-package-rename-transition.md` того репозитория,
  раздел «Мутации» — идентичный приём (подмена метаданных), там же полный прогон.

## Boundary cases

- Версия совпадает с пином при СОВПАДАЮЩЕМ имени — `ok`, не меняется (существующие тесты 4,
  32, 33).
- Имя совпадает, версия отличается в обе стороны — по-прежнему `outdated` (`11`), не `13`
  (тест 49, регресс-guard на то, что новое сравнение имени не «расширяет» старый порог по
  ошибке).
- Оба известных имени видны одновременно в `uv tool list` (`registered_both`) — диагностика,
  не статус отказа сам по себе; отличается от активного отказа `uv` при `install`
  (`slot_collision`, тест 51) — тест 50 проверяет именно пассивное наблюдение при `check`.
- Момент «между» шагами схемы отката (ADR-024 Д4) — не только начальное/конечное состояние
  машины, а именно ПРОМЕЖУТОЧНОЕ: тесты 53/54 фиксируют оба полюса неверного/верного порядка
  ровно в точке, где `uv tool list` уже (тест 53) или ещё (тест 54) расходится с живым
  разрешением команды.

## Error cases (два обязательных класса)

**Malformed/mistyped input** (искажённое, не только отсутствующее значение):
- Тест 56: `package_name` — пустая строка при ПРИСУТСТВУЮЩЕМ ключе (не тесты 37/38 — там ключа
  нет вовсе) → явный отказ `20`.
- Тест 50: `ktalk --version` печатает нераспознанную строку идентичности (первый токен не из
  известного списка) — резервный путь через `uv tool list`, диагностика `registered_both`,
  статус остаётся явным.
- Существующий тест 36 (нераспознанная версия, не имя) — не переписан, актуален без изменений
  под новую схему полей (версия сравнивается тем же `version_eq`).
- Для AC-1 класс не применим — сценарий не принимает пользовательский ввод (диф репозитория,
  не машина оператора) — **N/A**.
- Для AC-2/AC-7 класс не применим в этом дереве — процедурные шаги без исполнимой
  поверхности — **N/A**.

**Masked failure** (тихое принятие/редирект/дефолт вместо наблюдаемой ошибки):
- Тест 48: имя не совпадает с пином, но версия СОВПАДАЕТ буквально — сравнение только по
  версии молча признало бы это `ok`; тест ловит именно эту маскировку через `wrong_package`.
- Тест 51: коллизия слота — распознавание общим `install_failed` (`31`) маскировало бы
  конкретную, атрибутируемую причину («слот занят другим пакетом») под generic «что-то пошло
  не так»; тест требует именно `slot_collision` (`34`), называющий оба пакета.
- Тест 53: неверный порядок отката — `uv tool list`, продолжающий числить снятый пакет
  владельцем, маскировал бы реально сломанную команду под «совместимо»; тест требует
  `missing_cli` по живому разрешению.
- Тест 54 (обратная сторона того же риска) — верный порядок отката НЕ должен откатываться к
  устаревшему `uv tool list`, который ещё числит старый пакет: маскировка в другую сторону
  (ложный `outdated`/`wrong_package` вместо `ok`) так же недопустима.
- Тест 55: хардкод-литерал вместо параметра — маскированный отказ читать реальный источник
  правды (`compat.json`), тот же класс, что уже ударил версию в 0.8.0.
- Тест 47 (регресс-guard) — молчаливое расширение диффа за пределы шести названных файлов на
  промт-слой было бы маскированным нарушением NFR «команда сохранена», не сопровождаемым явной
  ошибкой сборки без этого теста.
- Для AC-2/AC-7 класс не применим отдельным стабом в этом дереве — процедурный контроль,
  замкнутый на ревью человеком, не на автоматическую маскировку — **N/A**.

## Не покрыто исполнимым стабом (out of scope этого дерева)

- **AC-2** (пред-релизный гейт публикации `ktalk-cli`) — сетевой шаг релизного пайплайна;
  расширяется существующий инлайн-скрипт `cli-only-boundary`-рансбука на параметризованное
  имя пакета (Brief for DevOps архитектурной статьи), не тестируется здесь тем же основанием,
  что и предшествующий AC-9.
- **AC-7** (санкция владельца на публикацию) — процедурный контроль без CI-пайплайна
  публикации в этом дереве; закрывается ревью-чеклистом релиза, не автоматическим тестом.
- **Текст депрекации, код возврата и `DeprecationWarning` пакета-указателя `ktalk-mcp`
  0.11.0** — канал пакета (companion-статья, NFR Mapping: «сам текст депрекации — вне этого
  дерева»); тестируется в `ktalk-mcp`, `at-design-package-rename-transition.md`, раздел «Не
  покрыто исполнимым стабом».
- **Полнота переименования модуля `ktalk_mcp` → `ktalk_cli`, литеральный бюджет 12→8** —
  дерево пакета целиком, не затрагивает файлы этого репозитория.

## Расхождение, требующее реконсиляции BA/SA (не решено этой задачей)

Buквальный текст `#### Scenario: An operator installs or already has the final ktalk-mcp
version` требует: «every CLI invocation SHALL print a deprecation notice... **and SHALL NOT
otherwise change the command's existing behaviour or exit code**» — то есть команда `ktalk`,
предоставляемая пакетом `ktalk-mcp`, обязана продолжать РАБОТАТЬ как раньше (с добавленным
предупреждением), не меняя код возврата. Принятое (владельцем, «не пересматривается») решение
`ktalk-mcp` ADR-022 §6/companion-спека §3 — прямо противоположное: пакет-указатель НЕ
объявляет entry point `ktalk` вовсе (`pyproject.toml` указателя не несёт этой команды),
единственная точка входа — `ktalk-mcp = ktalk_mcp:main`, которая печатает сообщение в stderr и
**завершается ненулевым кодом** при каждом вызове. Если оператор, у которого уже стоит
`ktalk-mcp`, апгрейднется до финального указателя БЕЗ параллельной установки `ktalk-cli`, его
привычная команда `ktalk` перестанет резолвиться вовсе (shell-код `127`) — ровно тот «bare
error»/«silent functional degradation», который требование прямо запрещает («Retirement SHALL
NOT take the form of a silent functional degradation or a bare import/runtime error»).

Тесты 48–50/56 этого файла проверяют то, что тестируемо и не зависит от исхода этого спора:
реакцию `ktalk-onboard.sh` НА ФАКТ разрешившейся идентичности `ktalk-mcp` (стабом, не реальным
пакетом-указателем) — она корректна независимо от того, продолжает ли `ktalk-mcp` физически
предоставлять команду `ktalk`. Утверждение сценария о сохранении «existing behaviour or exit
code» самой команды `ktalk` через пакет-указатель — не покрыто нигде и не может быть покрыто
без реконсиляции: тестировать по буквальному тексту спеки значило бы закладывать красный тест
на архитектурное решение, объявленное владельцем принятым и непересматриваемым; тестировать
по факту решения ADR-022 значило бы тихо переписать AC мимо BA. Передаётся координатору для
решения (правка формулировки требования BA, либо пересмотр ADR-022 владельцем) до того, как
Dev станет писать код против этого сценария.

## Не покрыто (out of scope, помимо секции выше)
