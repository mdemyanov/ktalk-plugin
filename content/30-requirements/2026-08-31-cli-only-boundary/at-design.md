# Тест-дизайн: CLI-граница (снятие MCP-поверхности плагина, пин версии пакета)

Предмет этого дерева — три изменения из брифа QA-001: снятие MCP-декларации плагина, точный
пин версии пакета, новая проверка состава на возврат `.mcp.json`. Стабы живут в

пропустил: тесты 42–46 (раздел «Раунд доработки: 5 дефектов code review» ниже). Тест 40 был

## Раунд доработки: 5 дефектов code review

Первый раунд стабов (тесты 32–41) закрыл 100% сценариев формально, но пропустил 5 дефектов,
которые нашло ревью кода реализации DEV-002. Общая причина четырёх из пяти — тест проверял
СВОЙСТВО в точке, где путь к нему короче и чище, чем путь, которым это свойство реально
достигается в проде; дефект жил именно в разнице между этими двумя путями.

| Находка | Дефект | Почему прежнее покрытие его не поймало | Новый тест |
|---|---|---|---|
| 1 | `installed_version()` режет `ktalk --version` регуляркой `[0-9]+\.[0-9]+\.[0-9]+` и теряет пре-релизный суффикс (`rc1`/`-rc1`) ДО того, как строка попадает в `version_eq()` — rc-сборка признаётся равной пину | Тест 39 звал `version_eq()` напрямую (`source ...; version_eq ...`), в обход `installed_version()` — сам путь потери информации оставался невидим | 42 — через `cmd_check` (`"$SCRIPT" check`), стаб `ktalk --version` печатает rc-версию в обеих типографиях |
| 5 | `version_eq()`: `case "$1" in *-*)` смотрит на дефис во ВСЕЙ строке, а не в части до `+` — билд-метаданные со своим дефисом (`+build-1`) читаются как пре-релиз, нарушая semver §10 (билд-метаданные игнорируются целиком) | Тест 39 проверял только `+local` (без дефиса внутри) — комбинация «билд-метаданные + дефис внутри них» не была опробована ни разу | 43 — через `cmd_check`, но со значением ПИНА (не installed): `installed_version()` в реальном пути срезает любой `+`-суффикс регэкспом до сравнения, поэтому единственный путь, которым сырая строка с дефисом реально доходит до `version_eq()`, — значение `ktalk_mcp_version` в `compat.json` (оно не проходит через тот же regex-фильтр) |
| 2 | `check_no_mcp_server()` смотрит только на файл `.mcp.json` и только на ключ, буквально равный `"ktalk"` — сервер, названный `"ktalk-mcp"`, или декларация в `marketplace.json`/`plugin.json` проходят гейт незамеченными | Тесты 40/44 первого раунда мутировали ровно тот файл и ровно тот ключ, которые уже проверяет реализация — «зелёный по построению», не потому что проверка полна, а потому что мутация повторяла форму, под которую гейт писался | 44a (ключ `ktalk-mcp` в `.mcp.json`), 44b (та же декларация в `marketplace.json`) |
| 3 | README жёстко называет версию в команде установки; ранбук подъёма пина правит только `compat.json` — после следующего подъёма документированная команда ставит версию, которую `check` тут же отвергает | Раньше не проверялось вовсе — не дефект прежнего теста, а отсутствие теста; свойство не входит ни в один из 9 сценариев спеки буквально | 45 — сравнивает версию в README с `ktalk_mcp_version` из `compat.json` |
| 6 | `SKILL.md`/`agents/ktalk-processor.md` описывают MCP как живой канал сравнения/альтернативу, хотя `_meta.md` тем же коммитом объявил MCP-поверхность контура `ktalk` снятой | Раньше не проверялось — тесты 40/41 проверяли декларацию (`.mcp.json`) и документацию для оператора (таблица retired→CLI), но не текст промт-слоя, объясняющий модель вызова | 46 — грепает конкретные противоречащие формулировки в конкретных файлах |

Тесты 42/43/44a/44b/46 сегодня красные на неизменённом дереве (реальные дефекты). Тест 45
сегодня зелёный (значения `README.md` и `compat.json` пока совпадают) — это регресс-guard на

## Boundary cases

- Версия равна пину ровно (тест 4) — не меняется, `version_eq` обязана вести себя как `version_ge`
  здесь.
- Версия отличается на один патч в обе стороны (тесты 3/3a — ниже; 5 — выше) — симметрия пина,
  не порога.
- `0.9.2` против `0.10.0` — посегментное числовое сравнение, не лексикографическое (тест 3a, не
  менялся, актуально и для равенства).
- **pre-release/build-метаданные** (`0.10.0+local` против пина `0.10.0`) — тест 39 (реализован
  Dev'ом: билд-метаданные игнорируются целиком — semver §10, пре-релизные идентификаторы
  значимы). **Раунд доработки нашёл, что реализация не полностью следует собственному правилу:**
  тест 42 — пре-релиз теряется ДО `version_eq()` (регэксп `installed_version()` срезает суффикс
  раньше, чем сравнение успевает его увидеть); тест 43 — билд-метаданные со своим дефисом
  (`+build-1`) ошибочно распознаются как пре-релиз внутри самой `version_eq()`. Оба — реальный
  путь (`cmd_check`), не прямой вызов функции, как было у теста 39.
- Постусловие после ремонта (`finish_install`) — тесты 27/29 (не менялись, версия ниже пина после
  ремонта) плюс симметрия для «выше» покрыта тестом 33 через ветку install/upgrade.

## Error cases (два обязательных класса)

**Malformed/mistyped input** (не отсутствие значения и не выход за диапазон — искажённое
значение от пользователя/окружения):
- Тест 36: `ktalk --version` печатает нераспознаваемую строку (`dev-build`, не semver) — `check`
  обязан явно отказать (`11`), не упасть с необработанной ошибкой и не признать версию тихо
  совместимой. AC-7.
- Для AC-5/AC-6 класс не применим: обе стороны сценария не принимают пользовательский ввод
  (декларация файла инспектируется статически, таблица — статичный документ) — **N/A**.
- Для AC-9 класс не применим в этом дереве (сценарий не реализуется здесь) — **N/A**.

**Masked failure** (система тихо принимает, редиректит или откатывается к дефолту вместо
наблюдаемой ошибки):
- Тест 32: версия НОВЕЕ пина без `allow_update` — до этого изменения такое состояние всегда было
  тихим `0` (порог трактовал «новее» как безусловно ОК); теперь обязана требовать санкцию явно.
  AC-7/Д2 ADR-022.
- Тесты 37/38: `compat.json` без ключа пина (вовсе, либо только старый ключ
  `ktalk_mcp_min_version` после переименования) — обязан явно отказать (`20`), не откатиться к
  «любая версия подходит». Мутационная демонстрация (не в составе стаба, приложена в отчёте
  QA-author): фиктивный дефолт `min_version() → 0.0.0` при отсутствии ключа переводит exit code
  20→0 — ассерт ловит эту деградацию. AC-7.
- Тест 40 (обновлено после DEV-002): свойство осталось тем же — регресс «`.mcp.json` вернулся
  и декларирует `ktalk`» обязан ловить гейт, иначе операторская сессия молча получает
  MCP-инструменты контура без единого провалившегося гейта. До DEV-002 стаб был красным на
  живом дереве без мутации (файл реально нарушал норму, проверки для него ещё не было) — это
  были строительные леса, не постоянный контракт: живой `.mcp.json`, декларирующий `ktalk`,
  противоречил бы самому AC-5. После DEV-002 (`.mcp.json` удалён, `check_no_mcp_server()`
  реализована) тест 40 — постусловие на живом дереве («.mcp.json отсутствует», зелёное сегодня,
  красное при мутации — временном возврате файла, отменено сразу после демонстрации) плюс
  регресс-тест на изолированной копии дерева, проверяющий обе стороны: файл вернулся → гейт
  падает и называет файл; файла нет → гейт проходит. AC-5.
- Для AC-6 (таблица) класс не применим отдельным тестом — риск «тихого возврата» инструмента
  закрывается транзитивно тестами 40/44a/44b (декларация — единственный канал, которым
  инструмент вообще становится доступен сессии) — **N/A как отдельная строка, закрыт AC-5**.
- Для AC-9 — N/A в этом дереве (сценарий не реализуется здесь).
- Тесты 44a/44b (раунд доработки, AC-5): гейт состава молчаливо пропускает ту же декларацию
  MCP-сервера контура `ktalk`, если она названа не буквально `"ktalk"` (44a) или лежит не в
  `.mcp.json` (44b) — форма гейта уже, чем формулировка спеки, и это расхождение никак не
  сигнализируется оператору.
- Тесты 42/43 (раунд доработки, AC-7): `check` молчаливо признаёт совместимой версию, которая
  таковой не является — пре-релизную сборку (42) или билд-метаданные, ошибочно принятые за
  пре-релиз (43). В обоих случаях никакого сообщения об ошибке нет вовсе — статус `ok`.
- Тест 46 (раунд доработки, AC-6): промт-слой продолжает описывать MCP как доступный канал,
  хотя декларация снята — оператор, читающий `SKILL.md`, не получает сигнала о том, что путь,
  упомянутый как альтернатива, больше не существует.

## Не покрывается (out of scope этого дерева)

- **AC-1..AC-4** (extra `fastmcp`, холодный старт, dev-группа пакета) — репозиторий `ktalk-mcp`,
  собственный QA-author того дерева. BA-001 §«Область» и companion-статья §«Context» оговаривают
  это явно.
- **AC-9** (пред-релизный гейт «пин уже опубликован») — отдельный шаг релизного пайплайна,
  сетевой, не pre-commit; имя скрипта не выбрано (companion-статья, «Форма пред-релизного
  условия»; «Brief for DevOps»). Не входит в три изменения брифа QA-001 §1 и не входит в «Brief
  for Dev» той же архитектурной статьи — закрывает DevOps отдельной задачей, не Dev этой волны.
- **AC-6, платформенная часть** (реальное отсутствие `mcp__ktalk__*` в списке инструментов
  операторской сессии Claude Code) — поведение хоста, не наблюдаемое статическим тестом в этом
  репозитории (архитектура, «Test-pyramid recommendation»). Ручная/QA-runner проверка после
  установки плагина без `.mcp.json`.
- **Норма semver §10 для пре-релиза/билд-метаданных** реализована и покрыта (тесты 39, 42, 43)
  — раньше здесь стояла заглушка на решение Dev; решение принято (билд-метаданные игнорируются
  целиком, пре-релиз значим), раунд доработки проверил его через реальный путь, не только
  прямым вызовом функции, и нашёл два места, где реализация ещё не следует собственной норме.

## Известное ограничение

`scripts/test-onboard.sh` читает реальный `compat.json` репозитория для большинства тестов пина
(меняя только вывод стаба `ktalk --version`) — это достаточно для симметрии «выше/ниже» и для
проверки текста команды ремонта. Для сценария «ключ пина отсутствует» (37/38) и «пин с
билд-метаданными» (43) тесты зеркалят дерево (`scripts/ktalk-onboard.sh` копируется, `compat.json`
подставляется синтетический) — приём не требует правки реального `compat.json` и не создаёт по
нему конфликт с DEV-002. Тесты 44a/44b идут дальше и копируют ВСЁ дерево (`cp -r "$ROOT"`, тот же
приём, что уже использовал Dev в регресс-тесте теста 40) — тяжелее по вводу-выводу, но нужен,
потому что мутация трогает `.claude-plugin/marketplace.json`, а не только `compat.json`/
`ktalk-onboard.sh`.

Тест 46 целится в две КОНКРЕТНЫЕ подстроки в двух конкретных файлах, а не в общий запрет слова
«MCP» в промт-слое — общий запрет ложно сработал бы на легитимные упоминания стороннего
инструмента `qmd` (`SKILL.md:152`, `agents/ktalk-processor.md:107`), которые эта находка не
затрагивает. Это защищает от конкретного известного регресса, но не гарантирует, что Dev не
введёт эквивалентное по смыслу, но по-другому сформулированное противоречие в другом месте —
семантический дрейф текста промт-слоя остаётся предметом ревью, не автоматической проверки
(тот же класс ограничения, что уже зафиксирован для языковой границы промт-слоя,
`2026-08-29-prompt-language-boundary/at-design.md`, раздел «Известное ограничение»).
