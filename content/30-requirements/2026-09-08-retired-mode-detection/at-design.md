# Тест-дизайн: обнаружение отставного режима авторизации (код 14)

**Capability:** `openspec/specs/session-only-auth/spec.md`
**Требование:** [2026-09-08-retired-mode-detection.md](../2026-09-08-retired-mode-detection.md)
**ADR:** `content/00-project/adr/ADR-029-detection-without-remediation.md` (Д1, Д2)

Предмет — три новых `### Requirement:` (строки 155–227 спеки), шесть `#### Scenario:`. Не
переоткрывает 9 Requirement/10 Scenario, закрытых предыдущим тест-дизайном
(`content/30-requirements/2026-09-07-session-only-auth/at-design.md`) — нумерация AC ниже
**локальна для этого файла и этого требования**, начинается заново с AC-1, не продолжает
AC-1..AC-11 соседнего документа (другой файл, другая приёмочная сводка BA).

**Решение о размещении сьюты — отдельный файл** `scripts/test-retired-mode-detection.sh`, не
блок внутри `scripts/test-session-only-auth.sh`. Обоснование:

- Установленная идиома репозитория — один файл на BA-требование
  (`test-dual-channel-delivery.sh` ← 2026-09-04-dual-channel-delivery, `test-release-delivery-
  tails.sh` ← 2026-09-03-release-delivery-tails, `test-session-only-auth.sh` ← 2026-09-07-
  session-only-auth), каждый со своей строкой в `.nauta-gates.yaml` `projectGates.full`. Общая
  тема capability (`session-only-auth`) не была основанием сливать file прошлых трёх сьют в
  одну — не становится им и здесь.
- Слияние в `test-session-only-auth.sh` создало бы коллизию меток: тот файл уже печатает свои
  собственные `AC-1`…`AC-11` (другие сценарии, другой at-design.md); повторное использование тех
  же меток для новых, не связанных сценариев сделало бы `grep -n "AC-1"` по логу сьюты
  неоднозначным, а нумерация вподряд (`AC-12`…) разошлась бы с этим at-design.md, который
  называет их `AC-1`…`AC-6` (сценарии этого требования, не того).
- Довод в пользу второго варианта (тот же гейт уже исполняется) реален и не снят — он назван
  ниже как явное действие Dev, а не растворён молчанием.

**ОБЯЗАТЕЛЬНОЕ действие Dev** (иначе повторяется находка 2 аудита прошлого эпика — зелёная
сьюта существует, но гейт её не исполняет): добавить строку `scripts/test-retired-mode-
detection.sh` в `.nauta-gates.yaml` → `projectGates.full`, вместе с комментарием-обоснованием
класса стоимости (сьюта делает живые подпроцессы `bash scripts/ktalk-onboard.sh check[--json]`
и один фиктивный `ktalk` в `mktemp -d`, тот же порядок стоимости, что у `test-session-only-
auth.sh`, — не `fast:`).

**Контракт имени JSON-поля не зафиксирован SA.** ADR-029 фиксирует решение «не устранять», не
имя нового булева поля `report()`; сам текст требования («Brief for SA») лишь ПОРУЧАЕТ SA
назвать поле — фактически названо не было. Стабы поэтому не хардкодят один буквальный литерал:
ассерты матчат JSON-ключ, содержащий (регистронезависимо) `retired` ИЛИ `personal_key`, со
значением `true`/`false` — наблюдаемое поведение контракта (отдельное булево поле, переключающееся
по факту), не имя конкретного поля. **Dev-хинт:** если реализация назовёт поле без обеих
подстрок, стаб не увидит его — расширь регэксп `RETIRED_TRUE_RE`/`RETIRED_FALSE_RE`
(`scripts/test-retired-mode-detection.sh`) в том же коммите, где называешь поле.

## Сегодняшний вердикт (дерево до Dev)

`bash scripts/test-retired-mode-detection.sh` → **PASS=6 FAIL=18 SKIP=0**, код возврата 1.
`cmd_check` сегодня не знает о `KTALK_PERSONAL_API_KEY` вовсе (единственное упоминание в
`scripts/ktalk-onboard.sh:311` — `unset` внутри `run_clean`, не в проверке) и кода 14 не
существует нигде в дереве — красный ожидаем структурно, не по случайности среды. Каждый PASS
объясняется ниже — ни один не «проверка ничего не проверяет»:

| AC | Вердикт | Почему |
|---|---|---|
| AC-1a | FAIL | нет поля факта в `--json` вовсе |
| AC-1b | FAIL | нет поля факта, хотя исход принудительно НЕ-ok |
| AC-1b (boundary) | PASS (легитимно) | код возврата и так остаётся 11 сегодня — предмет ещё не существует, вытеснять нечем; после Dev эта проверка становится настоящим регресс-guard'ом приоритета |
| AC-1c / AC-1c-txt | PASS (легитимно) | значение переменной и сегодня не печатается — `check` вообще не читает эту переменную; регресс-guard на будущее (Dev не должен начать печатать значение, добавляя диагностику) |
| AC-1d | PASS (легитимно) | поле `true` и не может встретиться — поля нет вовсе; регресс-guard на будущую реализацию, не подтверждение корректности сегодня |
| AC-2a | FAIL | нет поля факта |

| AC-2c | FAIL | нет поля факта |
| AC-2d | FAIL | нет поля факта |
| AC-3a/c/d | FAIL | код возврата сегодня 0 (`ok`) при любом значении переменной — код 14 не существует |
| AC-3b | FAIL | `status` сегодня буквально `"ok"` при заданной переменной — ровно то, что Requirement 2 запрещает |
| AC-4-`<op>` ×5, AC-4-json | FAIL | сообщение не называет ни одну из пяти операций — текста находки нет вовсе |

Итог: все 6 `#### Scenario:` несут ≥1 красный ассерт, вызванный отсутствием кода 14 и поля
факта, кроме AC-1 (malformed/masked часть) и AC-6, где PASS сегодня легитимен как guard на
будущую регрессию, а не как подтверждение уже исполненного контракта — обоснование см. таблицу
выше и разделы Boundary/Error ниже.

## Boundary cases

- AC-1b: приоритет готовности пакета над находкой (инвариант Requirement 2, не отдельный
  `#### Scenario:`, но явно зафиксирован текстом требования: «Наличие находки не мешает check
  вернуть коды 10–13/20/30–34») — при принудительном `outdated` (фиктивный `ktalk` на `PATH`) с
  одновременно заданной переменной код возврата обязан остаться **11**, не переключиться на 14.
- AC-2d: пустое, но экспортированное значение (`KTALK_PERSONAL_API_KEY=""`) — тот же приём
  `EMPTY_FIXTURE=""` из `content/30-requirements/2026-09-07-session-only-auth/at-design.md`
  (AC11-2), фикстура — именованная переменная, не литерал присваивания в команде.
- AC-1a — базовая машина этого дерева уже совпадает с пином (`compat.json`: `ktalk-cli 2.1.0`,
  установленный `ktalk --version` печатает то же) — сегодняшний ok-исход используется как база
  для «поле `false`», не требует подмены `PATH`.

## Error cases

**Malformed/mistyped input** (искажённый идентификатор/значение от целевого пользователя —
оператора, задающего переменные окружения своей оболочки):

- AC-1c — значение переменной со спецсимволами оболочки (кавычки, `$(...)`, обратные кавычки)
  никогда не попадает в вывод — ни `--json`, ни текст.
- AC-2c — опечатка в имени переменной (`KTALK_PERSONAL_APIKEY`, без подчёркивания перед `KEY`)
  не принимается за находку: близкое, но не то же самое имя — легитимный «нулевой» результат.
- AC-3c — искажённое значение переменной по-прежнему классифицируется тем же предупреждающим
  кодом 14, не иначе (не «непонятное значение» → внутренняя ошибка 20).
- AC-4, AC-5, AC-6 — **N/A**. Эти три сценария не обрабатывают пользовательский ввод: они
  печатают фиксированный текст (список из пяти операций спеки, команду `unset`, оговорку о
  файле) независимо от конкретного значения переменной. Класс «исковерканный идентификатор от
  пользователя» здесь не применим по предмету — явно, не тихим пропуском.

**Masked failure** (система молча принимает вход, перенаправляет или подменяет дефолтом вместо
наблюдаемой ошибки):

- AC-1d — поле факта не «залипает» в `true`: на ok-исходе без переменной регэксп `true`
  отсутствует (guard против реализации, которая всегда отвечает «обнаружено», не отражая
  реальное состояние окружения).
- AC-2b — `check` не подставляет `.env` рабочего каталога вместо чтения окружения процесса:
  переменная, лежащая только в `.env`, не засчитывается, даже если файл физически рядом (cwd
  вызова = каталог с `.env`).
- AC-3d — текстовый (не только `--json`) режим `check` тоже возвращает 14: guard против
  реализации, которая корректно метит находку в JSON, но по забывчивости оставляет старый `exit
  0` в человекочитаемой ветке.
- AC-4-json — поле `message` `--json` называет операции так же конкретно, как текстовый вывод:
  guard против реализации, которая пишет специфичный текст только для человека, а машинному
  потребителю оставляет обобщённую фразу.
- AC-5b — сообщение не выдаёт разовую команду за постоянное решение молчаливым умолчанием
  (отсутствием оговорки о новой оболочке): без явной оговорки оператор мог бы принять `unset` за
  окончательное устранение, что прямо противоречит ADR-029 Д1/Д2.
- AC-6a — сообщение не подставляет угаданный дефолтный путь (`~/.zshenv` и подобные) вместо
  честного «файл автозапуска, чьё расположение мне не известно»: называть конкретный файл,
  которого `check` не читал, было бы худшей формой маскировки, чем молчание — уверенно неверная
  информация.

## Not covered (out of scope)

- Правка/`unset` внутри самого `check` — вне периметра требования (ADR-029 Д1/Д2), стабы не
  проверяют «`check` не выполняет unset» напрямую: подпроцессная изоляция делает это
  ненаблюдаемым с этой стороны (родительская оболочка не может увидеть `unset`, выполненный в
  дочернем процессе, независимо от корректности реализации) — наблюдаемый прокси взят через
  AC-6b (файл не редактируется).
- Обработка кода 14 в `agents/ktalk-processor.md`/`agents/ktalk-evaluator.md` («не прерывать
  сессию, показать находку») — задача SA/Dev следующего шага по тексту требования, не
  зафиксирована отдельным `#### Scenario:` капабилити и не входит в периметр этого QA-цикла.
- Новый раздел «Code 14» `references/onboarding.md` — стаб не проверяет его текст напрямую
  (документ ещё не существует до Dev); наблюдаемое поведение проверяется через живой вывод
  `check`, не через файл документации.
