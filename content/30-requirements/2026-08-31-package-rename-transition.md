(`ktalk-onboard.sh check`), а не тихим отказом команды `ktalk`, чтобы миграция была управляемым
событием, а не случайной поломкой.

Когда наступает момент публикации `ktalk-cli` 1.0.0 или финальной версии-указателя
`ktalk-mcp`, я (владелец пакета) хочу явно и по имени санкционировать именно это действие,
потому что публикация в PyPI необратима для индекса (PEP 592: yank не удаляет версию, точный
пин продолжает её резолвить), и ни автоматизация, ни агент не должны совершить её без меня.

**Discovery path.** Новых точек входа нет. Расхождение проявляется через уже существующие
каналы: `scripts/ktalk-onboard.sh check`/`install` (текст сообщения о несовместимости и команда
ремонта), вывод `uv tool install`/`uv tool list` при попытке поставить второй пакет поверх
первого, и сам факт — команда `ktalk` в PATH работает или не работает — без какого-либо нового
меню, URL или подкоманды.

## Область

Пять свойств одного эпика, следующего за уже принятыми решениями (переименование на месте,
финальная версия-указатель, порядок пакет→плагин, имя исполняемого файла не меняется):

1. **Сохранение имени команды `ktalk`** через границу переименования пакета — наблюдаемое
   поведение промт-слоя и PATH, а не техника ренейминга модулей.
2. **Порядок публикации для НОВОГО имени пакета** — обобщение уже принятого ADR-022 сценария
   («плагин не публикуется раньше версии пакета») на случай, когда меняется не версия, а сама
   идентичность пакета.
3. **Поведение финальной версии-указателя `ktalk-mcp`** — что видит тот, кто её ставит, и тот,
   кто уже имеет более раннюю версию `ktalk-mcp`.
4. **Коллизия слота `uv tool install`** между двумя разными именами пакетов, когда оба
   притязают на точку входа `ktalk` — наблюдаемое поведение на трёх границах (см. ниже).
   Финальная версия-указатель `ktalk-mcp` эту точку входа сознательно не объявляет (решение
   владельца пакета, ADR-022 дерева пакета, Д6) — коллизия остаётся предметом только для машин
   с уже установленной ПРЕДШЕСТВУЮЩЕЙ (не финальной) версией `ktalk-mcp`.
5. **Санкция публикации** как процессный инвариант, отдельный от санкций онбординга
   (`allow_install`/`allow_update`, ADR-014 пакета) — те защищают локальный слот машины
   оператора, эта — общий и постоянный индекс PyPI.

**Вне области.** Техническое разрешение коллизии слота (принудительный `--force` в онбординге,
дополнительный шаг деинсталляции старого пакета, схема ключа в `compat.json` под новое имя
пакета) — решение SA. Механика переименования модулей внутри пакета (`ktalk_mcp` → `ktalk_cli`
в 75 файлах `src/`/`tests/`, восемь capability-спек пакета, снятие `fastmcp`) — дерево пакета,
не эта статья. Резервирование имён `ktalk-cli`/`ktalk` на PyPI до выхода кода — предложение
координатора владельцу, не решение этой статьи (см. «Brief for SA»). Проверка цепочки поставки
по хэшам уже выведена из области соседним требованием (`cli-only-boundary`) и не переоткрывается
здесь.

## Почему это второе ломающее изменение подряд, а не расширение первого

ADR-022 Д3 уже рассматривал коллизию «один `ktalk` на машину через `uv tool install`» — но
только между **версиями одного и того же** пакета (`ktalk-mcp` новее пина, поставленный кем-то
ради не связанной с плагином задачи). Диагностика там — сравнение строки версии
(`version_eq()`), полностью на стороне онбординг-скрипта, до и без обращения к `uv`.

Нынешний случай устроен иначе: два **разных** имени пакета в PyPI (`ktalk-mcp` и `ktalk-cli`)
объявляют одну и ту же точку входа `ktalk`. Здесь сравнивать нечего — `ktalk_mcp_version`
(или его наследник в `compat.json`) ничего не знает про факт существования второго пакета, а
конфликт возникает не в логике онбординг-скрипта, а на уровне самого `uv tool install`, в
момент установки. Это ровно та ситуация, которую ADR-022 Д3 не разбирал, а не её вариация.

## Что показал прогон `uv tool install` — граница измерена, не выдумана

Два синтетических пакета (`demo-pkg-a`, `demo-pkg-b`), каждый объявляет `[project.scripts]`
с одинаковым именем команды, установлены через `uv tool install` с изолированными
`UV_TOOL_DIR`/`UV_TOOL_BIN_DIR` (uv 0.12.5, 2026-08-31, вне рабочего дерева). Реальные пакеты
`ktalk-mcp`/`ktalk-cli` не привлекались — имя `ktalk-cli` ещё не опубликовано, повторная
проверка на настоящих именах остаётся открытым пунктом ниже.

Четыре наблюдения:

1. **Без `--force` — громкий, атрибутируемый отказ.** `uv tool install <второй пакет>` без
   флага завершается кодом 2 и сообщением `error: Executable already exists: <команда> (use
   --force to overwrite)`. Первый пакет продолжает работать без изменений; второй пакет не
   регистрируется в `uv tool list` вовсе — попытка полностью откатывается, не оставляя
   частичного состояния.
2. **С `--force` — команда переходит, регистрация — нет.** Бинарник второго пакета становится
   действующим (`ktalk` теперь запускает его код), но `uv tool list` после этого показывает
   **оба** пакета как владельцев одной и той же команды — список не отражает, какой из них
   реально исполняется.
3. **Деинсталляция «владеющего» пакета удаляет файл, а не переключает на второго владельца.**
   `uv tool uninstall <пакет с живым бинарником>` стирает исполняемый файл с диска полностью;
   запись второго пакета в `uv tool list` при этом остаётся (он по-прежнему значится
   «владеющим» той же командой), но вызов команды даёт `command not found` (код 127) — не
   откат к рабочей версии второго пакета.
4. **Механизм симметричен по порядку установки** — какой из двух пакетов ставится первым, а
   какой вторым, меняет только то, кто окажется «живым», а кто «висящим», но не саму
   механику отказа/переопределения.

Ответ на три конкретные границы:

- **Оператор с уже установленным `ktalk-mcp` ставит `ktalk-cli`.** По умолчанию (без
  `--force`) — громкий отказ, ноль потери данных, `ktalk-mcp` продолжает работать как раньше.
  Небезопасно только если онбординг-скрипт когда-либо добавит `--force` автоматически без
  предшествующего явного шага у оператора — тогда наблюдение 2 (список путает владение) и 3
  (деинсталляция стирает файл без отката) становятся реальным риском поломки без диагностики.
- **Обратный порядок (сначала `ktalk-cli`, затем откуда-то ставится `ktalk-mcp`)** — по
  наблюдению 4 механика та же самая, симметрично.
- **Плагин обновляет пин на `ktalk-cli==1.0.0` без переустановки оператором.** Это не
  двухпакетная коллизия `uv` — пакет на машине один (`ktalk-mcp`). Это уже покрытый случай
  соседней капабилити `cli-only-boundary` («версия отличается от пина»), но здесь отличие не
  только в версии, а в самой идентичности пакета: `ktalk --version` вернёт версию
  `ktalk-mcp`, а новый пин называет версию другого имени пакета — открытый вопрос ниже.

**Цена решения владельца пакета (ADR-022 дерева пакета, Д6) — признана явно, не спрятана.**
Финальная версия-указатель `ktalk-mcp` не объявляет `ktalk`: у неё единственная точка входа —
`ktalk-mcp`, печатающая на каждый вызов сообщение о переезде и код замены, и завершающаяся
ненулевым кодом. Обратная сторона того же решения — оператор, который апгрейднул уже
установленный `ktalk-mcp` на месте до этой версии (или поставил её свежей) и не установил
отдельно `ktalk-cli`, теряет голую команду `ktalk` целиком: прямой вызов в терминале, в обход
проверки плагина, получает обычный отказ шелла «команда не найдена» (код 127). Плагин обязан не
маскировать этот случай, а называть его отдельным, поимённым состоянием там, где оператор идёт
через `ktalk-onboard.sh check` — не тем же кодом, что «версия отстала», и не молчанием
(`ADR-024-package-rename-transition.md` Д2/Д5, статус несовпадения идентичности пакета).
Человек, зовущий `ktalk` руками мимо проверки плагина, эту диагностику не получает —
голый 127 в этом случае и есть принятая цена, а не дефект, который нужно скрыть.

**Не закрыто чтением, нужен прогон:** воспроизвести те же четыре наблюдения на настоящих
`ktalk-mcp`/`ktalk-cli` после публикации `ktalk-cli` 1.0.0 в PyPI — синтетические пакеты
подтверждают механику `uv`, но не гарантируют identичное поведение для реальных, что зависит
от uv, а не от содержимого пакета: правомерный, но не тождественный источник. Закрывается
дешёво — теми же четырьмя командами `uv tool install`/`uv tool uninstall`/`uv tool list` на
стенде, до финализации онбординг-скрипта (QA-author/Dev, не архитектурная задача).

**Решено SA, не этой статьёй:** `compat.json` сегодня хранит только версию
(`ktalk_mcp_version`), не имя пакета — различить «версия не та» от «пакет не тот» текущая
схема не умела. Схема идентичности пакета в пине и раздельное сравнение имени/версии решены
`ADR-024-package-rename-transition.md` Д1–Д2 этого дерева; здесь не переизлагается.

## Почему санкция на публикацию — отдельный инвариант, а не техническое решение

Публикация в PyPI необратима для намеченного смысла имени: PEP 592 описывает yank как
скрытие релиза из резолвинга по диапазону, но точный пин продолжает резолвить и устанавливать
yanked-версию — этим фактом уже пользуется существующий runbook (`AC-9`, различение «версии
нет» от «версия отозвана»). Из этого следует: опубликованное имя и опубликованная версия
навсегда занимают свой слот в индексе, независимо от последующих действий владельца.

У этого проекта уже есть парный прецедент того же по духу правила — «Запись в контур — только
по явной санкции оператора» (CLAUDE.md, для куда менее необратимого действия — создание или
отмена встречи, которую можно отменить обратно). Действие без отката вовсе заслуживает не
меньшей, а большей дисциплины: ни `ktalk-cli` 1.0.0, ни финальная версия-указатель
`ktalk-mcp` не публикуются автоматизацией или агентом без предшествующей явной, датированной
инструкции владельца, называющей пакет, версию и индекс (PyPI) по имени. Эта санкция —
отдельная от `allow_install`/`allow_update` онбординга (ADR-014 пакета): та защищает локальный
слот `uv tool` конкретной машины оператора, эта — общий и постоянный индекс, разделяемый всеми.

## Инварианты и защитные ограничения

**По существу:**
- Исполняемый файл, которым промт-слой плагина вызывает контур, остаётся `ktalk` — переименование
  пакета не меняет ни одной строки в `skills/`, `agents/`, `commands/` этого дерева (единственно
  допустимый дифф — `compat.json`, `README.md`, `references/onboarding.md`,
  `scripts/ktalk-onboard.sh`, `scripts/test-onboard.sh`, и текст `.claude-plugin/plugin.json`,
  называющий пакет по имени).
- Публикация плагина с пином на `ktalk-cli` не опережает публикацию версии `ktalk-cli`, на
  которую этот пин указывает — тот же принцип, что уже действует для версии (`cli-only-boundary`),
  распространённый на смену идентичности пакета.
- Ни установка, ни обновление одного пакета не переписывают состояние другого молча: коллизия
  слота `uv tool` обязана быть видимой и атрибутируемой оператору, а не тихо разрешённой в
  пользу одного из двух пакетов.
- Ни `ktalk-cli` 1.0.0, ни финальная версия-указатель `ktalk-mcp` не публикуются в PyPI без
  предшествующей явной санкции владельца, названной по пакету, версии и индексу.
- Потеря голой команды `ktalk` при апгрейде на версию-указатель `ktalk-mcp` — признанная,
  названная цена принятого решения (ADR-022 дерева пакета, Д6), а не дефект: ни один текст
  плагина не должен формулировать это состояние как «команда продолжает работать», и
  диагностика через `ktalk-onboard.sh check` обязана называть его отдельно от «версия отстала»,
  а не молчать о нём.

**Чувствительный контент:** N/A — требование не оперирует пользовательскими данными контура
(транскриптами, участниками, токенами); все числа получены на служебном дереве зависимостей
и на синтетических пакетах вне рабочего дерева.

## Brief for SA

**Требование:** этот файл
**Capability:** `openspec/specs/package-rename-transition/spec.md` — заведена этим же раундом
(норма зелёного дерева, C15, требует резолвящейся пары ровно тогда, когда требование её
объявляет). Спека несёт только наблюдаемые бизнес-правила (сохранение имени команды, явность
коллизии, поведение версии-указателя, санкция публикации) — техническое разрешение коллизии
слота `uv tool` и схема идентичности пакета в `compat.json` в неё намеренно не включены: это
решение SA, с этим же раундом зафиксированное `ADR-024-package-rename-transition.md` (Д1–Д4).

**Спроектировать:** форму разрешения коллизии слота `uv tool` (принудительный флаг в
онбординге, явный шаг деинсталляции старого пакета, порядок операций); схему идентичности
пакета в `compat.json` (нужно ли поле имени пакета отдельно от версии, или различение по
формату/диапазону версий двух пакетов); текст и код возврата, которым `ktalk-onboard.sh`
сообщает именно о коллизии между `ktalk-mcp` и `ktalk-cli`, отдельно от «версия не совпадает
с пином» одного и того же пакета.

**Известная граница, не гадать:** capability `cli-only-boundary` несёт сценарий «The plugin is
not released ahead of its pinned package version» для смены ВЕРСИИ одного и того же пакета —
он не редактируется этой задачей (одна капабилити не переопределяет чужой идентификатор).
`package-rename-transition` заводит для смены ИДЕНТИЧНОСТИ пакета собственное, отдельно
названное требование («The plugin is not released ahead of the renamed package's first
published version»), которое перестанет быть предметом контракта, как только `ktalk-mcp`
будет полностью выведена из обращения — в отличие от `cli-only-boundary`, чьи требования
описывают постоянное свойство границы.

**Бизнес-правила для валидаций** (`openspec/specs/package-rename-transition/spec.md`): «The
`ktalk` command name is preserved across the package rename», «The plugin is not released
ahead of the renamed package's first published version», «The retired `ktalk-mcp` package
announces its retirement loudly, not silently», «A command-name collision between the two
package identities is surfaced explicitly», «Neither package is published to PyPI without a
prior, explicit owner sanction». Второе требование переформулировано раундом BA-002 (QA-author
нашёл в тест-дизайне противоречие с ADR-022 дерева пакета Д6 — версия-указатель не объявляет
`ktalk`; исходная формулировка это отрицала, см. `content/lessons-learned.md`).

**Критерии приёмки архитектуры:** все `#### Scenario:` перечисленных выше требований той же
спеки.
