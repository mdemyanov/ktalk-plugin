# Тест-дизайн: единственный режим авторизации (токен браузерной сессии)

**Capability:** `openspec/specs/session-only-auth/spec.md`
**Требование:** [2026-09-07-session-only-auth.md](../2026-09-07-session-only-auth.md)
**ADR:** `content/00-project/adr/ADR-028-session-only-authorisation.md`

Предмет — 10 `#### Scenario:` capability `session-only-auth` (9 `### Requirement:`, первый несёт
два Scenario) плюс изменённый Scenario «No token value appears in what the plugin controls»
capability `plugin-onboarding-sanctioned-install` (ADR-028 сужает эту Requirement до собственного
предмета, содержание инструкции передано `session-only-auth`). Стабы живут в
`scripts/test-session-only-auth.sh` (проект хранит тесты в `scripts/`, каталога `tests/` нет —
идиома `test-dual-channel-delivery.sh`, `test-release-delivery-tails.sh`). Ни один блок не зовёт
`exit` до итогового — падение одного сценария не прерывает остальные.

**Периметр литерала `KTALK_PERSONAL_API_KEY`** (Д5 ADR-028, дословно = периметр Scenario «No
prompt-layer file names the retired mode as supported»): `README.md`, `references/`, `skills/`,
`agents/`, `commands/`. Вне периметра: `scripts/` (диагностика факта легитимна), `content/` и
`openspec/` (обязаны цитировать литерал как исторический факт о коде пакета). AC-1, AC-4 и AC-6
сканируют РОВНО этот периметр, не всё дерево — иначе стаб поймал бы собственные же артефакты
этого эпика (RES-001, требование, ADR).

## Boundary cases

- AC-3: файл и переменная — при истечении сессии файл ПЕРЕЗАПИСЫВАЕТСЯ той же командой, значит
  инструкция не может подать файл как разовую настройку — обе точки входа обязаны называть его
  как постоянный, наравне с переменной, механизм (не только «при первом запуске»).
- AC-7: `last_synced` — значение либо дата-строка (`"2026-08-27"`), либо `null`, ключ присутствует
  ВСЕГДА (RES-001, ADR-028); AC7-3 проверяет, что текст называет обе формы, не только одну —
  описание одной формы без другой создало бы у оператора неверное ожидание для случая, когда
  синхронизации ещё не было.
- AC-9: «голое упоминание» — тест реагирует именно на ОТСУТСТВИЕ слова «README» рядом со строкой,
  не на само упоминание `.ktalk.toml` (упоминание легитимно, реального объяснения файла в этом же
  месте не требуется, Requirement явно разрешает объяснение жить в другом месте).

## Error cases (два обязательных класса)

**Malformed/mistyped input** (искажённое значение от целевого пользователя — не отсутствие
значения и не выход за диапазон):

- AC4-1: единственный явный случай malformed input в узком смысле («DevOps/автор документации
  печатает несуществующее имя команды») — тест ловит буквальный `ktalk session` как опечатку
  реальной `ktalk token set -`, не как отсутствие команды вовсе.
- AC11-1a/b: фикстурное значение токена содержит кавычку, пробелы и `$(...)` — не «чистое»
  синтетическое значение, как в уже существующем `scripts/test-onboard.sh:26` (тот стаб проверяет
  только `install`/`install --json`). Значение оболочки со спецсимволами — тот класс входа,
  который реальный оператор способен положить в переменную случайно (скопировал лишний фрагмент
  из DevTools) — guard обязан не потерять и не сломаться на нём.
- **N/A для остальных девяти AC (AC-1, AC-2, AC-3, AC-5..AC-10).** Эти Scenario управляют
  СТАТИЧЕСКИМ текстом промт-слоя, не кодом, разбирающим идентификатор/URL-сегмент/поисковый
  запрос, набранный оператором. Самого входа, который оператор мог бы исказить в рамках ЭТИХ
  сценариев, не существует — искажать нечего, кроме случая AC-4 (уже покрыт) и AC-11 (уже
  покрыт). Явная фиксация, не тихий пропуск.

**Masked failure** (система тихо принимает, редиректит или откатывается к дефолту вместо
наблюдаемой ошибки):

- AC1-2, AC5-1/AC5-3: рекомендация личного ключа, переписанная описательной фразой без литерала,
  прошла бы мимо guard'а на голый литерал (Д5 ADR-028) — тест ловит фразу, не только литерал.
- AC2-2: секция могла бы лишиться ФРАЗЫ о приоритете, но сохранить структуру «два бюллета режима»
  — формально «правила приоритета нет», а по факту оба режима всё ещё названы. Тест считает
  бюллеты, не только присутствие фразы.
- AC3-3: файл токена, поданный оговоркой «если переменная не задана», — формально «назван», но
  подчинён переменной, а не наравне с ней, вопреки Requirement.
- AC4-3: onboarding.md может сослаться на README вместо того, чтобы назвать команду сам — секция
  выглядит «дополненной», а по факту точка входа «повторный онбординг» всё ещё не самодостаточна
  (Д2 ADR-028).
- AC6-3: near-miss написание (`list_archive`, `archive-list`) прошло бы мимо буквального guard'а
  на `list-archive`, если бы будущая правка ввела операцию под чуть другим именем.
- AC7-2: `last_synced`, вложенный внутрь `"stats": {...}` вместо верхнего уровня, содержал бы
  нужный литерал, но нарушал бы контракт («not only the first two», верхний уровень) — буквальный
  grep на присутствие литерала засчитал бы это как успех.
- AC8-2, AC9-2, AC10-2: расплывчатый указатель («см. README», «см. другие навыки») формально
  «указывает», но не даёт читателю конкретного места — тест (там, где уже есть что проверять)
  требует названного раздела/навыка/команды, не общей фразы.
- AC11-2: пустая строка в переменной токена, молчаливо засчитанная как «задано», — классический
  masked failure; сегодня недоказуемо (см. «Не покрывается»), но зафиксировано явно, не тихим
  пропуском.

Класс применим ко всем 11 AC либо явным тестом, либо явным `N/A` — ни один не отмечен молчаливым
пропуском.

## Не покрывается (out of scope этого дерева)

- **AC-7, AC-8, AC-10 — masked-failure/boundary половины (AC7-2/3, AC8-2, AC10-2).** Недоказуемо
  до появления самого текста (Dev ещё не написал `last_synced`/указатель/раздел новизны) — стаб
  зафиксирован как явный `SKIP` с причиной, не удалён и не превращён в вечный `PASS`; QA-runner
  обязан прогнать эти же блоки после Dev и получить содержательный вердикт, а не унаследованный
  SKIP.
- **AC-11, AC11-2 (пустая строка как «токен задан»).** `ktalk-onboard.sh check` сегодня вообще не
  содержит логики токена (только `install`/`grant`/`sanction`) — сам класс риска пока не имеет
  носителя в коде плагина; тест зафиксирован `SKIP`, не удалён, на случай если `check` когда-либо
  начнёт отчитываться о состоянии токена.
- **Реальное поведение LLM-агента, следующего инструкции.** Как и соседние тест-дизайны этого
  дерева (`test-release-delivery-tails.sh`, шапка), эта capability описывает ТЕКСТ промт-слоя
  (ADR-012: тонкая обёртка, прикладного кода нет) — можно проверить наличие и форму инструкции,
  не факт, что оператор или агент ей действительно последует. Полная поведенческая проверка не
  автоматизируется этим стабом.
- **Живое поведение `ktalk-cli` при конфликте двух реально заданных переменных.** RES-001/ADR-028
  явно фиксируют: пакет `2.1.0` продолжает читать `KTALK_PERSONAL_API_KEY` и отдавать ему
  приоритет независимо от текста плагина — это код зависимости (issue `ktalk-cli#10`), не предмет
  этого требования и не тестируется здесь (ADR-012, граница «тонкая обёртка»).
- **Судьба статьи `content/30-requirements/2026-08-18-onboarding-sanctioned-install.md` (FR-28).**
  ADR-028 Д4 передаёт решение о статусе (superseded/правка) на уровень SA/PM — вне мандата
  QA-author.
