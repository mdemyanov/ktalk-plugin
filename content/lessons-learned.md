# Lessons Learned

Append-only журнал уроков команды. Пишется по итогам задачи и только тогда, когда урок
переживает эпик; находки об инструментах и API живут в auto-memory, не здесь.

**Компакция.** Когда файл превышает 400 строк — записи старше трёх последних эпиков
переезжают дословно (без переформулировки) в `content/lessons-archive/<тема>.md`, а на месте
записи остаётся одна строка `YYYY-MM-DD — <заголовок> — см. content/lessons-archive/<файл>.md`.
Порог 400 — эвристика, не измерение контекстного бюджета: пересмотри его числом.

| 2026-08-31 | SA | ktalk-plugin-4nk, ADR-022 (снятие MCP-поверхности) | Объясняя в companion-статье, почему два retired MCP-имени запрещены гейтом состава, автор написал сам запрещённый литерал как иллюстрацию — и уронил тот же гейт, который описывал. Прогонять гейт после каждого черновика, где обсуждается сам запрет, а не только после финальной правки. |
| 2026-08-31 | QA-author | ktalk-plugin-4nk, QA-001 (порог → пин, `test-onboard.sh`) | Когда AC меняет направление проверки (порог «не ниже» → пин «ровно равно»), старые тесты, писавшие именно старую полярность («версия выше минимума → 0»), не становятся «ещё одним случаем» нового AC — они ему прямо противоречат. Оставленные как есть, они держат сьюту зелёной ложно: новая проверка появляется рядом, старая продолжает утверждать обратное и никто не замечает конфликт до Dev. Аналогично san­кция (`allow_update`) под порогом проверялась только в одной ветке («ниже») — при симметричном пине не проверяемая ветка («выше, без санкции») раньше вообще не существовала и молча вела себя как «всегда ок». | При развороте полярности AC — сначала найти тесты, писавшие старую полярность явно (`grep` по граничному значению/сообщению), и поменять их ожидание в том же PR, что добавляет стабы, а не оставлять рядом с новыми. Для симметризованного инварианта (было: одна ветка, стало: обе) — явно спросить «а раньше вторая ветка вообще проверялась» и завести стаб на неё, даже если раньше о её существовании никто не думал. |
| 2026-08-31 | DevOps | ktalk-plugin-4nk, OPS-001 (runbook выпуска, AC-9) | AC-9 («плагин не выпускается раньше пина») помечен QA-author как N/A для сьюты онбординга — сетевая проверка индекса пакета не место юнит-теста. N/A в тест-дизайне не значит «условие не проверяется вовсе»: единственный носитель сдвинулся в runbook, и шаг без команды с проверяемым кодом возврата (не абзац «убедитесь») там был бы точно такой же дырой, какой N/A был бы в сьюте. Заодно нашлось: PEP 592 (yank на PyPI) сохраняет резолвинг точного пина (`==<version>`) даже для отозванного релиза — «откат пакета» не защищает уже выданные операторам точные установки, но обязан ловиться повторным прогоном той же пред-релизной проверки на *следующий* пин. | Когда QA-author помечает сценарий N/A с указанием «где закрывается» (другая роль/другой пайплайн) — читать это как обязательство, не как закрытие вопроса: тот же стандарт (команда + проверяемый исход), только другой носитель. Перед тем как писать раздел «откат» для внешнего индекса пакетов (PyPI и подобных) — проверять фактическую семантику отзыва версии (yank ≠ delete), а не считать её базой данных с UPDATE/DELETE. |
| 2026-08-31 | DevOps | ktalk-plugin-4nk, OPS-001 (правка после ревью координатора) | `curl ... \| grep -q '"yanked": false'` выглядела как проверяемая команда с проверяемым исходом — она читалась, имела exit-код, была вставлена в runbook как рабочий шаг. Ни разу не выполненная на живом индексе, она молча зависела от форматирования чужого JSON (PyPI печатает `"yanked":false` без пробела) и давала `exit 1` на обоих концах теста, включая версию, которую была обязана пропустить. Написанная-как-проверяемая и проверенная — разные вещи, и разница не видна по тексту команды, только по факту запуска. | Команда в runbook — не готова к публикации, пока не прогнана на реальных данных на обоих концах различаемых исходов (успех и минимум один блокирующий случай), с приложенным выводом в теле задачи. «Команда с правдоподобным синтаксисом» — не критерий приёмки; критерий — стенограмма запуска. Для внешнего индекса (PyPI и подобных) разбирать ответ структурным парсером (`json`), не текстовым `grep` по чужому, ничем не гарантированному форматированию. |
| 2026-08-31 | DevOps | ktalk-plugin-4nk, OPS-001 (правка после code review, находки 3–4) | Два независимых дефекта одной природы: (1) `git revert --no-edit <sha>` без `-m` — синтаксически правдоподобная, документационно стандартная команда, которая гарантированно отказывает на merge-коммите, а `main` этого репозитория интегрируется именно ими; (2) шаг обновления пина трогал `compat.json`, но не `README.md`, хотя README называет тот же пин буквально — после следующего релиза документированная команда установки указывала бы на версию, которую `check` тут же назовёт несовместимой. Оба нашёл не автор рансбука, а ревьюер, читавший команды против реальной истории репозитория и реального README, а не против намерения. | Перед тем как писать шаг "отменить релизный коммит" для ветки с историей — проверить `git log --oneline --merges <ветка>`: если там не пусто, `revert` без учёта числа родителей коммита не готов к публикации. Когда пин версии живёт в двух файлах (`compat.json` для машины, `README.md` для человека) — искать оба грепом (`grep -rn <версия>`) при каждой правке пина, не полагаться на то, что "источник истины один", если человекочитаемая копия существует физически отдельным файлом. |
