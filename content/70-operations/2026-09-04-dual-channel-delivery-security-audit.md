# Аудит безопасности перед первой публикацией: двухканальная поставка (SEC-001)

**Capability:** `openspec/specs/dual-channel-delivery/spec.md`
**ADR:** `content/00-project/adr/ADR-027-github-mirror-channel.md`
**Architecture:** `content/40-architecture/2026-09-04-dual-channel-delivery.md`
**Соседний runbook:** `content/70-operations/2026-09-04-dual-channel-delivery-release-runbook.md`

## Вердикт

**ЗАБЛОКИРОВАНА** для тега `ktalk--v1.12.0` в его сегодняшнем виде. Список блокеров — раздел
«Блокеры» ниже. После их закрытия и выпуска **нового** тега (версия поднята, `claude plugin
tag` не даёт переиспользовать `ktalk--v1.12.0` без `--force` — проверено ниже) публикация
разрешена с условиями (раздел «Условия»).

## Scope

Предмет — не всё дерево, а план публикации: результат исполнения (не чтения)
`bash scripts/mirror-github.sh --tag ktalk--v1.12.0 --dry-run` на коммите `3de9eb5`
(тег `ktalk--v1.12.0`), плюс код `scripts/mirror-github.sh` и `.gitlab-ci.yml`, определяющие,
что этот payload делает при реальном `--push`. Рабочая копия (HEAD `6255a98`, на 10 коммитов
дальше тега) проверена отдельно и расходится с тегом — расхождение само по себе Находка 1.

## Находка 1 (Critical/Blocker) — внутренний домен в payload замороженного тега

Тег `ktalk--v1.12.0` (коммит `3de9eb5`) — это ровно то дерево, что уйдёт наружу командой из
задания. `README.md` входит в payload-манифест и в реальный archive тега. В нём, на строке 26
снятого с тега файла, стоит **целый, несклеенный литерал** внутреннего GitLab-адреса —
буквально того самого, что `CLAUDE.md`, «Справочные пути», называет по роли, не литералом.

Воспроизведение:
```
git show ktalk--v1.12.0:README.md | sed -n '26p'
```
Строка содержит команду `/plugin marketplace add https://<внутренний-GitLab>/tools-ai/ktalk-plugin.git`
с адресом, написанным целиком (не привожу его здесь буквально — красная линия этого же отчёта,
см. «Ловушка» ниже).

Коммит `00a7027` («dev(dual-channel-delivery): реализация ADR-027», DEV-001) заменил эту строку
плейсхолдером — но это коммит **после** тега (`git merge-base --is-ancestor ktalk--v1.12.0 HEAD`
→ true, тег — предок HEAD, 10 коммитов позади). Git-теги неизменны: правка на `main` не
переносится на уже созданный тег. Рабочая копия сегодня чиста —
`grep -n "<домен>" README.md` на HEAD пуст, — но это не защищает публикацию **этого тега**:
`git archive` берёт снимок дерева на момент тега, а не текущий `main`.

Ловушка задания (раздел 7) сработала бы здесь буквально: `check-plugin-composition.sh`
(включая его новую scoped-проверку Д4) гоняется в CI/pre-commit против **рабочего дерева**, а
не против содержимого уже существующих тегов — на HEAD гейт зелёный (проверено:
`bash scripts/check-plugin-composition.sh` → `OK`), и это создаёт ложное чувство «домен никогда
не утекал», хотя уже вырезанный тег его несёт. Ни один существующий гейт этого дерева не
сканирует исторические теги.

**Действие:** не пушить `ktalk--v1.12.0`. Поднять версию в `.claude-plugin/plugin.json` (сегодня
`1.12.0` и на HEAD, и на теге — `claude plugin tag --dry-run` уже отказывает: `Tag
"ktalk--v1.12.0" already exists locally. Bump the version...`, воспроизведено живым прогоном),
выпустить новый тег на коммите не раньше `00a7027`, зазеркалировать его. Отдельно — процессное
дополнение для DevOps/SA: перед первым `--push` любого будущего тега прогонять
`check_payload_domain`-эквивалент не по рабочему дереву, а по `git archive <тег>`, иначе тот же
класс дефекта (фикс на `main`, утечка на уже вырезанном теге) повторится и останется незамеченным
до самого push.

## Находка 2 (High) — Supply-chain: проверка паритета Д6 №2 структурно не может пройти

ADR-027 Д6 и одноимённый runbook задают три команды сверки паритета после каждого
зазеркаливания. Команда №2 (`Пин compat.json`) сравнивает
`git show gitlab/$TAG:compat.json` с `git show github/$TAG:compat.json`. Но `compat.json` не
входит в `.gitlab/payload-manifest.txt` (Д4) и, соответственно, никогда не копируется в payload
джобом зеркалирования (`scripts/mirror-github.sh`, сборка через `git archive $TAG -- $(cat
manifest)`).

Воспроизведение (безопасно, без сети — `compat.json` реально отслеживается в git на стороне
источника, что и требуется для левой половины команды):
```
git show HEAD:compat.json                                   # содержимое есть — сторона gitlab
grep -n compat.json .gitlab/payload-manifest.txt             # пусто — файла нет в манифесте
diff <(git show HEAD:compat.json) /dev/null; echo $?         # 1, непустой diff — сторона github
                                                              # эквивалентна "файла нет" всегда
```
Правая часть команды №2 (`github/$TAG:compat.json`) обязана давать `fatal: path 'compat.json'
does not exist` (пустой stdout) для **любого** тега, когда-либо зазеркаленного этим джобом,
потому что манифест никогда не включает этот путь. Diff непустого содержимого gitlab-стороны с
пустым github-стороны — не флуктуация, а гарантированный, невосстановимый «дефект», один и тот
же на каждом релизе. Guard резолвимости ref'ов (сам по себе корректный) эту ситуацию не ловит —
он проверяет резолвимость **тега**, не резолвимость **пути внутри** тега.

Раздел «Known problems» runbook'а называет похожий по форме, но структурно другой ложноположительный
случай (признак №3, состав payload, из-за дрейфа манифеста во времени) и никак не упоминает, что
признак №2 не пройдёт **никогда** — я не нашёл этой оговорки ни в ADR-027, ни в architecture
companion, ни в runbook'е.

**Действие (решение — SA/DevOps, не эта роль):** либо добавить `compat.json` в
`.gitlab/payload-manifest.txt` (тогда признак №2 становится осмысленным — заодно закрывает
Находку 3 ниже), либо явно вычеркнуть признак №2 из Д6 отдельным ADR-решением и заменить его
проверкой, не требующей присутствия файла на зеркале. Оставлять как есть — значит обучить
дежурного игнорировать постоянно красный признак, что маскирует настоящее расхождение, если оно
когда-нибудь появится на двух других признаках.

## Находка 3 (High) — Supply-chain: документированный путь восстановления не работает на GitHub-канале

README, раздел «Если что-то не работает» (строки 179–187), — единственная документированная
инструкция на случай «плагин говорит, что пакет не найден или устарел»: она отсылает к
`compat.json` как источнику точного пина и предписывает `bash <путь к плагину>/scripts/
ktalk-onboard.sh check`. Этот скрипт **входит** в payload (`scripts/` в манифесте), но
`compat.json`, который он читает по абсолютному пути `$PLUGIN_ROOT/compat.json`, **не входит**
(та же причина, что в Находке 2).

Воспроизведено на реально собранном payload тега (не на рабочей копии):
```
git archive ktalk--v1.12.0 -- $(cat .gitlab/payload-manifest.txt | grep -v '^$') | tar -x -C /tmp/payload
cd /tmp/payload && bash scripts/ktalk-onboard.sh check
```
Вывод: `Не прочитан compat.json плагина — переустановите плагин.`, код возврата `20`
(`E_INTERNAL`). Отказ громкий (не тихая порча состояния) — это хорошо, но совет «переустановите
плагин» вводит в заблуждение: переустановка не создаст `compat.json`, потому что он структурно
не публикуется в этот канал. Для потребителя, установившего плагин **только** с
GitHub-зеркала, единственный документированный путь диагностики несовместимости пакета
недоступен.

**Действие:** та же развилка, что в Находке 2 (добавить `compat.json` в манифест — закрывает
обе находки одним движением — либо явно описать в README ограничение «эта команда работает
только при установке с внутреннего канала»). Решение — SA/BA, не эта роль; довожу как факт,
не предписываю.

## Находка 4 (Medium) — LICENSE и `.github/*` не закоммичены, публикация пройдёт без них молча

`LICENSE` и три файла `.github/` (`CONTRIBUTING.md`, `ISSUE_TEMPLATE/bug_report.md`,
`PULL_REQUEST_TEMPLATE.md`) физически лежат в рабочей копии, их содержимое я прочитал и оно
чистое (без домена, без секретов, без PII — MIT-текст и текст источника истины/ручного триажа,
согласованный с Д5). Но ни один из них не отслежен git:

```
git ls-files LICENSE .github/CONTRIBUTING.md .github/ISSUE_TEMPLATE/bug_report.md \
  .github/PULL_REQUEST_TEMPLATE.md
# пусто — ни один файл не в индексе
```

`scripts/mirror-github.sh` на путь из манифеста, отсутствующий на теге, печатает `WARN` в
stderr и **продолжает работу** (не поднимает `fail`, код возврата не меняется) — подтверждено
дословно в выводе `--dry-run`:
```
WARN: путь 'LICENSE' из манифеста отсутствует на теге ktalk--v1.12.0 — пропущен
WARN: путь '.github/' из манифеста отсутствует на теге ktalk--v1.12.0 — пропущен
```
Итог: реальный `--push` сегодня опубликует репозиторий без файла лицензии и без шаблонов
issue/PR — тихо в смысле кода возврата (WARN не FAIL), хотя ADR-027 Consequences прямо называет
это открытым пунктом брифа Dev («LICENSE в дереве сегодня нет — Dev обязан завести его до первой
публикации»). Публичный репозиторий без `LICENSE` по умолчанию читается как «все права
защищены» — это не то же самое, что «не решили пока».

**Действие:** `git add LICENSE .github/ && git commit` до создания нового тега. Отдельно, для
DevOps/SA: рассмотреть, не должен ли `mirror-github.sh` завершаться `FAIL`, а не `WARN`, на
отсутствии путей, санкционированных оператором как обязательные (`LICENSE`, `.github/`), в
отличие от путей, которые могут легитимно отсутствовать на части тегов.

## Находка 5 (High, требует подтверждения DevOps — эта роль не вправе выполнять `git push`) — push ветки `main` без `--force`

`scripts/mirror-github.sh`, блок реального push (строки 134–145): на **каждый** вызов создаётся
новый пустой git-репозиторий (`mktemp -d` + `git init`) с ровно одним коммитом payload'а,
формируется ветка `mirror-tmp`, и она пушится как `git push origin "mirror-tmp:main" "$TAG"`
**без `--force`**. У этого коммита нет общего предка ни с одним предыдущим состоянием `main` на
GitHub (каждый прогон начинается с `git init` в новом временном каталоге). Стандартное
поведение `git push` без `--force` при отсутствии общего предка — отказ (`non-fast-forward`),
кроме самого первого пуша, когда `main` на GitHub ещё не существует.

Это означает: первая публикация в `mirror-github` пройдёт, но **каждая последующая** обязана
упасть на этом шаге, пока кто-то не добавит `--force` в команду. Я не проверил это исполнением —
роль `nauta:devsecops-agent` не имеет полномочия O4 на `git push` (в том числе на локальный
scratch-репозиторий для теста, подтверждено отказом системы разрешений в этой сессии) — довожу
как рассуждение по документированной семантике git, не как замеренный факт, и прошу DevOps
подтвердить второй тестовый прогон `mirror-github.sh --push` до включения его в постоянный
процесс релиза.

**Действие:** DevOps проверяет на втором релизе (или на форкнутом тестовом remote); если
подтверждается — добавить `--force` именно к обновлению `main` (не к тегу — тег осознанно
неперемещаем, ADR-025 Д1/ADR-027 Д2, и это правильно).

## Внутренняя инфраструктура

- Основная находка — №1 выше.
- Приём разделения литерала на части (`part1`/`part2`, `scripts/check-plugin-composition.sh`,
  строки ~80-82) публикуется в payload (`scripts/` в манифесте, файл реально присутствует в
  архиве тега). Приём достаточен ровно для одной цели — не совпасть с собственным regex'ом
  проверки (самосовпадение, тот же класс, что и `--exclude=check-plugin-composition.sh` строкой
  выше). Он **не** является мерой конфиденциальности: читатель публичного репозитория видит обе
  половины на соседних строках одного файла и восстанавливает адрес взглядом без единого
  дополнительного действия — ровно то предупреждение, которое ставит формулировка задания. Это
  расходится с намерением, заявленным в этом же решении (Д3: заменить литерал в README
  плейсхолдером именно затем, чтобы адрес не был публичным), — Д4 добивается противоположного
  результата тем же файлом, который сам себя от прямого совпадения защищает. Severity — Medium
  (сам факт публикации регекспа для домена не равен публикации домена в открытую, но эффект для
  человека — тот же).
- Паттерн жёстко зашитой раскладки vault'а хозяина (`check-plugin-composition.sh:52`) — по
  payload 0 совпадений вне самой строки проверки, то есть раскладка хозяина в публикуемых
  файлах не встречается.
- Паттерн абсолютного пути домашнего каталога разработчика (`check-plugin-composition.sh:56`) —
  2 совпадения, оба внутри комментария и самого паттерна этой же проверки, не факт утечки
  реального пути машины.

## История

`scripts/mirror-github.sh` не публикует git-историю источника. Реальный push (строки 134-145)
создаёт **новый**, не связанный с исходным репозиторием git-каталог (`mktemp -d` → `git init`),
коммитит собранное payload-дерево одним коммитом (`mirror: $TAG`) и пушит только эту ветку и
тег. Ни `git log`, ни reflog, ни коммиты вне снимка тега наружу не идут — подтверждено чтением
кода, других путей push в скрипте нет. `.gitlab/payload-manifest.txt` и `.gitlab-ci.yml`
подтверждённо отсутствуют на любом собранном дереве (проверено исполнением: оба
`git ls-tree ktalk--v1.12.0 -- .gitlab-ci.yml` и по HEAD дают пустой вывод; `.gitlab-ci.yml`
как таковой сегодня трекается в git начиная с `00a7027`, но не входит в манифест ни разу).
Единственный найденный дефект того же механизма — не история, а Находка 5 (push без `--force`).

## Supply-chain

- Прикладного пакетного менеджера в дереве плагина нет — это markdown+bash-плагин (ADR-012),
  единственная внешняя зависимость — `ktalk-cli`, версионируется отдельно и пинуется
  `compat.json` (`package_name`/`package_version`, ровно, не порог). Лок-файлов
  (`package-lock.json` и т.п.) в этом дереве корректно нет — их и не должно быть.
- SAST-инструменты `semgrep`/`bandit` в этом окружении недоступны (`command not found` для
  обоих) — не прогнаны, называю как класс, не проверенный автоматическим тулом. Компенсирующая
  мера: ручной обзор шести `.py`-скриптов payload (5061 строк) на характерные паттерны
  (`subprocess`/`os.system` с `shell=True`, `eval`/`pickle`, небезопасный `yaml.load`) — 0
  совпадений; весь YAML читается через `yaml.safe_load`. `eval "$cmd"` в `scripts/check.sh`
  оперирует строками, объявленными внутри самого скрипта (имена гейтов), не внешним/недоверенным
  вводом — не инъекционный вектор.
- `uv tool install ktalk-cli==2.0.0` (README, шаг 1) — точный пин версии из публичного индекса
  PyPI, без `curl | sh`/`curl | bash`, без скачивания произвольного кода по неверифицированному
  URL.
- Находки 2, 3, 5 — структурные дефекты пайплайна поставки (не CVE в зависимости, но тот же
  вектор ответственности: гарантия, что то, что установит потребитель, — то, что было
  санкционировано).

## Обратный канал

`.github/` (untracked, содержимое проверено — раздел «Находка 4») явным текстом декларирует
отсутствие автоматизации: ни бота, ни CI-джоба, ни workflow, реагирующего на issue/PR. Проверено
не на слово: в payload нет каталога `.github/workflows/` вовсе (ни в манифесте, ни в архиве
тега), а `.gitlab-ci.yml` — единственный существующий CI-файл дерева — заводит ровно один джоб
(`mirror-github`) с условием `rules: if $CI_COMMIT_TAG =~ /^ktalk--v/`, то есть срабатывает
только на защищённый релизный тег, не на событие issue/PR/comment. `pull_request_target` не
встречается нигде в дереве (`grep -rn pull_request_target .` — пусто). Утверждение Д5 «автоматизации
нет вовсе» подтверждено фактом отсутствия триггеров, а не только текстом намерения.

## Условия (для нового тега после устранения блокера)

1. Находка 4 — закоммитить `LICENSE` и `.github/*` до тега.
2. Находка 2 и 3 — решить (SA/BA) судьбу `compat.json` в манифесте и/или переписать признак №2
   Д6 и раздел README «Если что-то не работает» под фактическое покрытие GitHub-канала.
3. Находка 5 — DevOps подтверждает или опровергает поведение `git push` на втором релизе и
   чинит `mirror-github.sh` при подтверждении.
4. Процессное дополнение к Находке 1 — сканировать домен по `git archive <тег>`, не только по
   рабочему дереву, перед каждым `--push`.
