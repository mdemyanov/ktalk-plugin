# Runbook: двухканальная поставка — первая публикация GitHub-зеркала и регулярный релиз

**Capability:** `openspec/specs/dual-channel-delivery/spec.md`
**ADR:** `content/00-project/adr/ADR-027-github-mirror-channel.md`
**Architecture:** `content/40-architecture/2026-09-04-dual-channel-delivery.md` (раздел
«Brief for DevOps» — техзадание этого runbook'а)
**Соседние рансбуки:** `content/70-operations/2026-09-03-release-delivery-tails-release-runbook.md`,
`content/70-operations/2026-08-31-package-rename-transition-release-runbook.md` — форма тега
(`claude plugin tag`, ADR-025 Д1) и структура пред-релизного гейта унаследованы оттуда без
повторения; этот файл добавляет то, чего в них нет — второй канал поставки payload.

## Purpose

ADR-027 вводит второй, публичный канал поставки — GitHub-зеркало payload — рядом с внутренним
GitLab-маркетплейсом (источник истины, без обратной автосинхронизации). Используй этот runbook:
один раз — при первой публикации зеркала (репозиторий `mdemyanov/ktalk-plugin` на GitHub на
момент написания не существует, проверено ниже); затем — при каждом обычном релизе, чтобы
дождаться зеркалирования и сверить паритет каналов.

## Preconditions

- `git status --short` — рабочее дерево чистое на коммите, который становится релизом.
- Пред-релизный гейт зелёный **до** тега — GO-критерий `CLAUDE.md`, обязателен перед merge:
  ```bash
  bash scripts/check.sh --full
  ```
  Успех: `✓ check.sh --full — passed`, код возврата `0`. Живая проверка этой задачей (2026-09-04,
  ветка `epic-dual-delivery`): `PASS=38 FAIL=0 SKIP=0` для `scripts/test-dual-channel-delivery.sh`
  внутри общего прогона, финальная строка `✓ check.sh --full — passed`. Ненулевой код — тег не
  создаётся, дальше по шагам не идти (тот же принцип, что оба соседних runbook'а).
- `scripts/check-plugin-composition.sh` зелёный отдельно (входит в `--full`, но у этого решения
  есть собственная scoped-проверка внутреннего домена GitLab, ADR-027 Д4 — см. «Известные
  проблемы» ниже про её область действия):
  ```bash
  bash scripts/check-plugin-composition.sh
  ```
  Живая проверка (2026-09-04): `Проверка состава плагина: OK`, код `0`.
- Доступ на push и право тегировать в репозитории плагина на GitLab (тот же принцип, что у
  соседних runbook'ов). Доступ к публичному GitHub-репозиторию `mdemyanov/ktalk-plugin` нужен
  только для одноразовой процедуры ниже — регулярный релиз зеркалирует CI-джоб, не
  релиз-инженер лично.
- `git`, `jq`, `python3`, `gh` в PATH машины релиз-инженера.
- `GITHUB_MIRROR_TOKEN` — секрет джоба `mirror-github`, не этой роли. Форма секрета (protected,
  masked, область — запись в один репозиторий) описана ниже в разделе «Секрет» ссылкой на её
  единственный источник (Brief for DevOps, ADR-027 Д2) — не переопределяется здесь второй раз.

## Форма тега — `claude plugin tag`, не `git tag`

Тег релиза — форма `<plugin>--v<version>` (ADR-025 Д1), условие запуска джоба `mirror-github`
(`.gitlab-ci.yml`, `rules: if $CI_COMMIT_TAG =~ /^ktalk--v/`). Ручной `git tag` не создаёт тег
в этой форме и не подтверждает согласие `plugin.json` с записью маркетплейса — используй только
`claude plugin tag`, тот же приём, что уже задокументирован соседним runbook'ом:

```bash
claude plugin tag --dry-run
```

Живая проверка (2026-09-04, эта worktree, `plugin.json` версии `1.12.0`, тег `ktalk--v1.12.0`
уже существует — самый свежий релиз этого дерева):

```
⚠ CLAUDE.md: CLAUDE.md at the plugin root is not loaded as project context. ...
✘ Tag "ktalk--v1.12.0" already exists locally. Bump the version in plugin.json, or re-run with --force to move the tag.
```

Это ожидаемый ответ на уже выпущенную версию, не дефект: подтверждает, что команда видит
существующий тег и не создаёт дубликат молча. Для **следующего** релиза — после того как
`plugin.json.version` поднят Dev'ом — тот же `--dry-run` печатает `Tag: ktalk--v<новая-версия>`
(форма подтверждена также в ADR-027, Context, на `1.12.0`: `claude plugin tag --dry-run --force`
→ `Tag: ktalk--v1.12.0`). Реальное создание — после того как пред-релизный гейт вернул `0` и
релизный коммит слит в `main`, не раньше:

```bash
claude plugin tag --push --remote origin
```

Успех: `git ls-remote --tags origin | grep ktalk--v<version>` находит тег на GitLab-стороне
(`origin` этого дерева — внутренний GitLab, `git remote -v` подтверждает это на любой машине
релиз-инженера).

## Первая публикация зеркала (одноразовая процедура)

Репозиторий `github.com/mdemyanov/ktalk-plugin` **не существует** на момент написания —
перепроверено этой задачей:

```bash
gh repo view mdemyanov/ktalk-plugin
```
```
GraphQL: Could not resolve to a Repository with the name 'mdemyanov/ktalk-plugin'. (repository)
```

Эта процедура выполняется **один раз**, до первого успешного прогона джоба `mirror-github`, и
только по санкции оператора — сам репозиторий эта задача не создаёт (мандат — процедура, не
исполнение; координатор проводит эти шаги по отдельной санкции).

1. **Создать публичный репозиторий** — не исполнено этой задачей, исполняет координатор/DevOps
   по санкции оператора:
   ```bash
   gh repo create mdemyanov/ktalk-plugin --public --license MIT \
     --description "ktalk — Claude Code plugin for Kontur Talk meeting recordings (public mirror; source of truth is the internal GitLab)"
   ```
   Проверка после создания: `gh repo view mdemyanov/ktalk-plugin --json visibility,licenseInfo`
   → ожидание `"visibility":"PUBLIC"`, `"licenseInfo":{"key":"mit", ...}` — тот же приём, каким
   ADR-027 Context уже проверило прецедент лицензии на `mdemyanov/ktalk-cli`
   (`gh repo view mdemyanov/ktalk-cli --json visibility,licenseInfo` → `PUBLIC`/`MIT`).
2. **Первый push** — не выполняется вручную командой `git push` в обход джоба: та же
   `mirror-github.sh`, что обслуживает регулярный релиз (см. ниже), собирает payload-дерево по
   манифесту и пушит его на только что созданный репозиторий. Первый прогон отличается от
   регулярного только тем, что целевой репозиторий пуст (нет предыдущей истории, конфликтов
   push быть не может):
   ```bash
   GITHUB_MIRROR_TOKEN=<токен-из-защищённого-хранилища> \
     bash scripts/mirror-github.sh --tag ktalk--v<текущая-версия> --push
   ```
   Живая проверка **без** `--push` этой задачей (2026-09-04, `--dry-run`, реальный push не
   выполнен — вне мандата документационной задачи), на теге `ktalk--v1.12.0`:
   ```
   План зеркалирования:
     тег:            ktalk--v1.12.0
     remote:         https://github.com/mdemyanov/ktalk-plugin.git
     ...
     marketplace.json.name (пропатчено): ktalk-plugins-mirror
     файлы:
       .claude-plugin/marketplace.json
       .claude-plugin/plugin.json
       .github/CONTRIBUTING.md
       .github/ISSUE_TEMPLATE/bug_report.md
       .github/PULL_REQUEST_TEMPLATE.md
       LICENSE
       README.md
       agents/... commands/... references/... scripts/... skills/...

   DRY-RUN: push не выполнен. Для реального push — флаг --push и переменная GITHUB_MIRROR_TOKEN.
   ```
   Список файлов совпадает построчно с `.gitlab/payload-manifest.txt`, разложенным по дереву
   тега — включая пропатченный `marketplace.json.name`. Реальный `--push` — за пределами
   мандата этой задачи; исполняет координатор/DevOps после появления репозитория (шаг 1),
   разово.
3. **Проверка после первого push** — тег и ветка появились на зеркале:
   ```bash
   git ls-remote https://github.com/mdemyanov/ktalk-plugin.git | grep ktalk--v<версия>
   ```
   Непусто — тег присутствует, первая публикация состоялась. С этого момента вступает в силу
   регулярная процедура ниже — CI-джоб `mirror-github`, не ручной `mirror-github.sh --push`.

## Регулярный релиз

После того как зеркало опубликовано впервые (раздел выше), каждый следующий релиз
зеркалируется джобом `mirror-github` автоматически по тегу:

1. Создать тег обычным путём (раздел «Форма тега» выше), дождаться, пока GitLab-пайплайн
   отработает джоб `mirror-github` (`.gitlab-ci.yml`, stage `mirror`) — статус смотреть в
   штатном UI пайплайна GitLab, новый канал алертинга не заводится (см. «Мониторинг»).
2. **Джоб зелёный.** Тег появился на GitHub-зеркале — переходить к разделу «Сверка паритета».
3. **Джоб красный.** Релиз GitLab **не откатывается** — состояние источника истины push на
   GitHub не меняет (ADR-027 Д2). Разобрать причину по логу джоба (обычно: `GITHUB_MIRROR_TOKEN`
   истёк/отозван, сетевая ошибка push, путь манифеста исчез из дерева тега), затем повторить
   вручную кнопкой `Retry` в пайплайне — тот же джоб, тот же тег, автоматического цикла нет
   (ADR-027 Д2: «Повторный запуск — вручную»). Если причина требует правки самого
   `scripts/mirror-github.sh`/`.gitlab-ci.yml` — это отдельная задача Dev, не повторный `Retry`
   с тем же кодом.
   Ручной эквивалент, если `Retry` недоступен (раннер снят, доступ к пайплайну потерян) —
   тот же скрипт, что и джоб исполняет внутри себя, вручную с той же машины релиз-инженера:
   ```bash
   GITHUB_MIRROR_TOKEN=<токен-из-защищённого-хранилища> \
     bash scripts/mirror-github.sh --tag ktalk--v<version> --push
   ```

## Сверка паритета (после каждого успешного зеркалирования)

Guard резолвимости обоих ref'ов **обязателен перед тремя командами**, не опционален — без него
опечатанный или ещё не подтянутый тег даёт пустой `diff` с обеих сторон, неотличимый от
подтверждённого паритета (ADR-027 Д6, находка QA, учтена до принятия решения). `gitlab`/`github`
— именованные remote одного локального клона релиз-инженера/DevOps (не `origin` — заведи их
явно, если ещё не заведены):

```bash
git remote add gitlab https://<внутренний GitLab-адрес — см. CLAUDE.md, «Справочные пути»>/tools-ai/ktalk-plugin.git   # один раз
git remote add github https://github.com/mdemyanov/ktalk-plugin.git                                                      # один раз
git fetch gitlab --tags && git fetch github --tags
```

**Guard — один на все три команды, буквально (ADR-027 Д6):**

```bash
TAG=ktalk--v<version>
for ref in gitlab/$TAG github/$TAG; do git rev-parse --verify -q "$ref" >/dev/null || { echo "ПАРИТЕТ НЕ ПРОВЕРЕН: ref '$ref' не резолвится"; exit 1; }; done
```

Живая проверка этой задачей (2026-09-04, эта worktree, remote `gitlab`/`github` ещё не заведены
— штатное состояние до первой публикации зеркала):

```
ПАРИТЕТ НЕ ПРОВЕРЕН: ref 'gitlab/ktalk--v1.12.0' не резолвится
```

Guard корректно останавливается на первом нерезолвящемся ref'е и не идёт к трём командам ниже —
это ожидаемый сегодняшний результат (зеркало ещё не существует), не дефект guard'а.

**Три команды паритета (ADR-027 Д6-таблица), выполняются только после того, как guard выше
прошёл без сообщения `ПАРИТЕТ НЕ ПРОВЕРЕН`:**

| # | Признак | Команда |
|---|---|---|
| 1 | Версия плагина | `diff <(git show gitlab/$TAG:.claude-plugin/plugin.json \| python3 -c "import json,sys;print(json.load(sys.stdin)['version'])") <(git show github/$TAG:.claude-plugin/plugin.json \| python3 -c "import json,sys;print(json.load(sys.stdin)['version'])")` |
| 2 | Пин `compat.json` | `diff <(git show gitlab/$TAG:compat.json) <(git show github/$TAG:compat.json)` |
| 3 | Состав payload | `diff <(git ls-tree -r --name-only gitlab/$TAG -- $(cat .gitlab/payload-manifest.txt)) <(git ls-tree -r --name-only github/$TAG)` |

Пустой вывод всех трёх — паритет подтверждён. Непустой вывод любой из трёх — **дефект
зеркалирования**, не «версия для другой аудитории» (BA-001): не публиковать это как штатное
расхождение, разбирать как инцидент зеркалирования (см. «Известные проблемы»).
`marketplace.json` намеренно не входит ни в один из трёх признаков — его различающееся поле
`name` (`ktalk-plugins` / `ktalk-plugins-mirror`, ADR-027 Д1) не дефект, а сама точка различия
каналов; проверка №3 сравнивает состав файлов, не их содержимое, поэтому с Д1 не конфликтует.

## Rollback

**Откатывается:** декларация релиза на внутреннем GitLab (тег, `compat.json`, `plugin.json`) —
механика полностью описана соседним runbook'ом (`2026-09-03-release-delivery-tails-release-
runbook.md`, «Откат тега» / «Откат релизного коммита») и не повторяется здесь текстом: тот же
приём (`git revert -m 1` на merge-коммите, число родителей решает форму команды) верен для
любого релиза этого репозитория.

**Не откатывается — тег на GitHub-зеркале.** ADR-025 Д1 (перенесено ADR-027 без изменений):
уже опубликованный тег не переписывается и не удаляется — форсированное перемещение молча
подменяет то, что чей-то клон уже мог резолвить по этому имени. Это касается **обоих** remote
одинаково: откат тега на GitLab-стороне (см. соседний runbook) не обязан и не должен
сопровождаться `git push github :refs/tags/<tag>` или `--force`-перемещением того же тега на
зеркале.

**Что тогда значит «откат зеркала».** Не удаление/перемещение тега, а **следующий, новый тег** с
исправлением — та же логика, что PEP 592/yank у пакетных индексов в соседних runbook'ах: индекс
не позволяет стереть версию, только опубликовать следующую. Если дефект найден в уже
зазеркаленном релизе (например, паритет не сошёлся, или payload зеркала содержит то, чего не
должно):

1. Исправить причину на GitLab-стороне (правка манифеста/скрипта/README — обычный коммит,
   обычный PR/MR, вне мандата этого runbook'а).
2. Выпустить **следующую** версию плагина обычным путём (раздел «Форма тега» выше) — новый тег
   `ktalk--v<version+1>` пройдёт джоб `mirror-github` заново и появится на зеркале рядом со
   старым, дефектным тегом, не вместо него.
3. Сверить паритет нового тега (раздел «Сверка паритета» выше). Старый, дефектный тег на обоих
   remote остаётся в истории — это принятая цена (тот же принцип, что ADR-025 Д1 уже применяет к
   шести тегам старой формы, соседний runbook, «Риск, названный явно»), не открытая задача
   «подчистить теги» без нового решения SA.
4. Если дефектный тег на GitHub-зеркале несёт то, что нельзя оставлять публичным (например,
   утечка внутреннего домена мимо scoped-гейта, а не просто рассинхронизацию версии) —
   это инцидент, не рутинный откат: удаление уже опубликованного публичного артефакта на
   стороне GitHub — операция владельца репозитория (`gh repo view`/`Settings` → `Tags`/`Releases`
   на стороне GitHub, ручной UI-шаг, CLI-эквивалента для точечного удаления тега без
   `--force`-перемещения нет; проверено `gh release --help`/`gh api --help` на дату этой задачи,
   2026-09-04) — не автоматизируется этим runbook'ом, эскалация ниже.

## Мониторинг

Тот же принцип, что у обоих соседних runbook'ов — нет сетевых сервисов и очередей этого плагина
кроме исходящего `git push` на GitHub; новый канал алертинга не заводится (ADR-027 Д2, Brief for
DevOps).

- **Метрика: статус джоба `mirror-github` в пайплайне GitLab.** Норма — зелёный после каждого
  тега `ktalk--v*`. Красный — стоп-условие только для зеркала, не для релиза GitLab (см.
  «Регулярный релиз», п.3); сигнал смотрится в штатном UI пайплайна GitLab, отдельного дашборда
  не заводится.
- **Метрика: guard резолвимости ref'ов (раздел «Сверка паритета»).** Норма — оба ref'а
  резолвятся в пределах разумного окна после зелёного джоба (минуты, не часы — единственная
  операция джоба — один `git push`). Ref не резолвится дольше окна ожидания — не «подождать ещё»,
  а проверить статус джоба заново: либо джоб ещё не запускался (тег не той формы,
  `$CI_COMMIT_TAG` не совпал с `^ktalk--v`), либо запускался и упал (см. «Регулярный релиз»,
  п.3).
- **Метрика: три команды паритета (Д6).** Норма — пустой вывод всех трёх. Непустой — дефект
  зеркалирования, не алерт на дежурного вне рабочего времени (нет пользовательского трафика,
  которому это угрожает немедленно) — разобрать в рабочем порядке, следующий тег с починкой
  (см. «Rollback»).
- **Дашборд.** Источники истины — тег на GitLab (`origin` этого дерева) и тот же тег на
  `github.com/mdemyanov/ktalk-plugin`; отдельного мониторингового сервиса нет.

## Escalation

- **Кто дежурит.** Роль `/nauta:devops` эпика, тот же принцип, что у обоих соседних runbook'ов —
  без отдельного круглосуточного дежурства.
- **Когда эскалировать.** `GITHUB_MIRROR_TOKEN` истёк/отозван (джоб красный на шаге push с
  ошибкой авторизации) — эскалация владельцу токена (та же роль, что провиженирует секрет,
  «Секрет» ниже), не решается локальной правкой скрипта. Guard паритета не резолвит `github/<tag>`
  дольше окна ожидания при зелёном джобе пайплайна — расхождение состояния пайплайна и
  реального remote, эскалация владельцу GitLab CI runner'а. Подозрение, что зазеркаленный
  payload содержит то, чего не должно (внутренний домен, секрет, PII) — это находка гейта Д4 в
  штатном режиме (см. «Предусловия»), но если она обнаружена **после** того, как тег уже ушёл
  на публичный GitHub — это инцидент публичной утечки, не рутинный дефект: DevOps ведёт
  оперативный тайм-лайн (когда замечено, какой тег, что сделано), корневую причину и
  пост-мортем — DevSecOps (вне мандата этого runbook'а; этот раздел называет только точку
  передачи, не сам разбор).

## Секрет — `GITHUB_MIRROR_TOKEN`

Форма секрета — **единственный источник**, Brief for DevOps (`content/40-architecture/2026-09-04-
dual-channel-delivery.md`, «Brief for DevOps») и ADR-027 Д2: CI/CD-переменная **protected**
(доступна только защищённым тегам — тег `ktalk--v*` обязан быть отмечен protected в настройках
репозитория GitLab) и **masked** (не печатается в логах джоба); область токена на стороне
GitHub — запись в один репозиторий `mdemyanov/ktalk-plugin`, не шире (Personal Access Token с
fine-grained scope на этот единственный репозиторий, либо GitHub App с тем же ограничением —
конкретный механизм провиженирования не предмет этого runbook'а). Этот раздел **не переопределяет
и не расширяет** форму секрета — ссылается на неё; в проекте сегодня нет отдельного
DevSecOps-документа по управлению секретами (роль не активирована этим эпиком) — единственный
источник требования к форме токена на сегодня — приведённая выше архитектурная статья, и её же
цитирует этот runbook, не второй раз формулирует условия провиженирования своими словами.

**Ни одного реального значения токена в этом файле** — красная линия проекта (`CLAUDE.md`,
«Красные линии проекта»). Провиженирование — CI/CD Variables репозитория плагина на GitLab
(UI-шаг: `Settings → CI/CD → Variables → Add variable`, флаги `Protect variable`/`Mask variable`
— CLI-эквивалента через `glab` для установки masked/protected переменной в этом дереве не
проверялось на дату этой задачи, 2026-09-04; если он появится — обновить эту строку, не
описывать его как проверенный факт заранее).

## Known problems

- **`claude plugin tag --dry-run` печатает `Tag "ktalk--v<version>" already exists locally`**
  → версия в `plugin.json` не поднята Dev'ом перед релизом, либо тег уже создан этим же
  раундом → поднять версию в `plugin.json` (не эта роль — Dev), повторить `--dry-run`; не
  использовать `--force` для перемещения существующего тега (ADR-025 Д1, тот же принцип, что
  ниже для GitHub).
- **Guard паритета печатает `ПАРИТЕТ НЕ ПРОВЕРЕН: ref '<remote>/<tag>' не резолвится`, хотя
  джоб `mirror-github` в пайплайне зелёный** → локальный клон релиз-инженера не подтянул новые
  теги remote'а → `git fetch gitlab --tags && git fetch github --tags`, повторить guard; если
  после fetch ref всё ещё не резолвится — реальное расхождение, эскалация (см. «Escalation»).
- **Три команды паритета (Д6) дают непустой `diff` только на признаке №3 (состав payload)** →
  чаще всего манифест `.gitlab/payload-manifest.txt` изменён после того, как предыдущий тег уже
  был зазеркален (новый путь добавлен в манифест, но джоб для старого тега собирал payload по
  старой версии манифеста) → ожидаемо для тега, зазеркаленного **до** правки манифеста; не
  дефект этого тега — сверять манифест на состояние **того же коммита**, что и сам тег
  (`git show <tag>:.gitlab/payload-manifest.txt`), не текущий манифест `main`.
- **`gh repo view mdemyanov/ktalk-plugin` внезапно снова отвечает «repository not found» после
  того, как первая публикация уже состоялась** → скорее всего репозиторий переименован/удалён
  вручную на стороне GitHub, вне процесса этого runbook'а → эскалация владельцу GitHub-аккаунта,
  не автоматическое пересоздание этим или любым скриптом (пересоздание репозитория с тем же
  именем не восстанавливает историю тегов молча).
- **`scripts/mirror-github.sh --push` завершается `FAIL: --push требует настоящего тега (форма
  ktalk--vX.Y.Z) — HEAD не тег`** → джоб или ручной вызов выполнен на коммите, где `git describe
  --tags --exact-match` не находит ровно один тег (HEAD ушёл дальше тега, или тег ещё не создан
  на этом коммите) → создать тег (раздел «Форма тега») **до** запуска push, не передавать `--tag
  HEAD` вручную ради обхода проверки — сама проверка существует именно для того, чтобы не
  зазеркалить нетегированный коммит на публичный канал.
