# Runbook: выпуск на два репозитория (`ktalk-mcp` → `ktalk`)

**Capability:** `openspec/specs/cli-only-boundary/spec.md`
**ADR:** `content/00-project/adr/ADR-022-cli-only-boundary.md`
**Architecture:** `content/40-architecture/2026-08-31-cli-only-boundary.md`

## Purpose

Плагин `ktalk` объявляет в `compat.json` **точную** версию пакета `ktalk-mcp` (пин, не
порог, ADR-022 Д3). Пин, указывающий на версию, которой ещё нет в индексе пакета, ставит
оператора в тупик: `ktalk-onboard.sh check` сообщит `outdated`/`missing_cli` и напечатает
команду ремонта, которая ничего не установит (`uv tool install ktalk-mcp==<pin>` с
несуществующим `<pin>`). Используй этот runbook при каждом выпуске плагина, меняющем пин, и
при откате уже выпущенной пары версий.

## Preconditions

- Доступ на push в оба репозитория (`ktalk-plugin`, `ktalk-mcp`) и право создавать теги.
- Пакет `ktalk-mcp` версии `<PIN>` **уже выпущен** в своём репозитории: тег создан, сборка
  опубликована в PyPI под именем `ktalk-mcp` — это отдельная процедура репозитория пакета, не
  этого дерева (SA companion, раздел «Context»). Без выполненного этого условия шаг 2 ниже не
  пройдёт по построению.
- `uv`, `curl`, `git` есть в PATH машины, с которой запускается релиз.
- Секреты токена оператора (`KTALK_SESSION_TOKEN`, `KTALK_PERSONAL_API_KEY`,
  `KTALK_BASE_URL`) в релизном окружении не нужны и не должны быть выставлены — политика
  снятия секретов из окружения подпроцесса (`run_clean`, NFR-19) уже реализована в
  `scripts/ktalk-onboard.sh`; секреты в CI-переменных релизного пайплайна регулирует
  DevSecOps, здесь не переопределяется.

## Steps

Порядок необратим в обе стороны: пакет публикуется первым, плагин — вторым. Между ними стоит
пред-релизная проверка (шаг 2) — единственный носитель AC-9 capability-спеки, помеченного
QA-author как N/A для сьюты онбординга (`at-design.md`, «AC-9 … не покрывается стабом этого
дерева»).

1. **Обновить пин в дереве плагина** (после того, как `<PIN>` подтверждён опубликованным в
   репозитории `ktalk-mcp`). Правится не только `compat.json` — `README.md` называет
   сегодняшний пин буквально в шаге «Быстрый старт» (`uv tool install ktalk-mcp==<OLD_PIN>` и
   комментарий `# ровно <OLD_PIN>`); не обновлённый вместе с пином README на следующем релизе
   документирует команду, которую `check` тут же назовёт несовместимой —
   ```bash
   OLD_PIN="$(grep -Eo '"ktalk_mcp_version"[[:space:]]*:[[:space:]]*"[^"]+"' compat.json \
              | head -1 | sed -E 's/.*"([^"]+)"[[:space:]]*$/\1/')"
   sed -i '' "s/\"ktalk_mcp_version\": \".*\"/\"ktalk_mcp_version\": \"<PIN>\"/" compat.json
   sed -i '' "s/${OLD_PIN//./\\.}/<PIN>/g" README.md
   ```
   Успех: `cat compat.json` показывает ровно `<PIN>`, без второго ключа рядом; `grep -n
   "<PIN>" README.md` находит обе строки шага «Быстрый старт» (команда установки и
   комментарий `# ровно`), а `grep -n "<OLD_PIN>" README.md` не находит ничего.
   Живая проверка (2026-08-31, копии `compat.json`/`README.md` в изолированном
   scratch-каталоге, не рабочее дерево): `OLD_PIN` считан как `0.10.0`; после команд
   `compat.json` содержит `"ktalk_mcp_version": "0.11.0"`, а `README.md` — строки `uv tool
   install ktalk-mcp==0.11.0` и `ktalk --version       # ровно 0.11.0 — …`; ни одного
   оставшегося вхождения `0.10.0` в README. Реальные файлы репозитория не трогались — правка
   `README.md` этим раундом закрывает Dev, здесь только доказан синтаксис команды рансбука.

2. **Пред-релизная проверка — AC-9.** Убеждается, что `<PIN>` не просто существует в индексе,
   а установим (не yanked). Разбор ответа PyPI — парсером (`python3`/`json`), не текстовым
   `grep` по сырому JSON: PyPI сериализует поля без пробела после `:` (`"yanked":false`), и
   паттерн с пробелом (`"yanked": false`) не совпадает никогда — этот вариант команды был
   проверен на живом индексе и **не прошёл** ни на одном конце (см. «Живая проверка» ниже).
   Шаг обязан различать три исхода, не два: версии нет в индексе (HTTP 404) — блок; версия
   есть, но отозвана (`info.yanked == true`) — блок; версия есть и жива — пропуск; сообщение
   называет, какой именно —
   ```bash
   PIN="$(grep -Eo '"ktalk_mcp_version"[[:space:]]*:[[:space:]]*"[^"]+"' compat.json \
          | head -1 | sed -E 's/.*"([^"]+)"[[:space:]]*$/\1/')"
   HTTP_CODE="$(curl -sS -o /tmp/pypi-pin.json -w '%{http_code}' \
                "https://pypi.org/pypi/ktalk-mcp/${PIN}/json")"
   python3 - "$HTTP_CODE" "$PIN" /tmp/pypi-pin.json <<'PY'
   import json, sys
   code, pin, path = sys.argv[1], sys.argv[2], sys.argv[3]
   if code == "404":
       print(f"BLOCK: {pin} not found in index (HTTP 404)")
       sys.exit(1)
   if code != "200":
       print(f"BLOCK: unexpected HTTP {code} for {pin}")
       sys.exit(1)
   with open(path) as f:
       data = json.load(f)
   if data.get("info", {}).get("yanked"):
       print(f"BLOCK: {pin} is yanked ({data['info'].get('yanked_reason')})")
       sys.exit(1)
   print(f"OK: {pin} published and not yanked")
   sys.exit(0)
   PY
   echo "AC-9 gate: $?"
   rm -f /tmp/pypi-pin.json
   ```
   Успех: печатает `OK: <PIN> published and not yanked` и `AC-9 gate: 0`. Любой другой исход
   печатает, какой именно («not found in index» / «is yanked (<причина>)» / «unexpected
   HTTP») и возвращает `1` — **останавливает релиз плагина** до шага 3; тег плагина не
   создаётся, пока этот шаг не вернёт `0`. Это блокирующее условие релизного пайплайна, то
   же самое по духу, что `check-plugin-composition.sh` уже применяет к составу дерева
   (ADR-022 companion, «Форма пред-релизного условия») — ненулевой код останавливает
   публикацию до оператора, не является рекомендацией.

   **Живая проверка команды (2026-08-31, оба конца исхода):**
   - `PIN=0.10.0` (сегодняшний пин, реально опубликован, не отозван) →
     `OK: 0.10.0 published and not yanked`, `AC-9 gate: 0`.
   - `PIN=99.0.0` (заведомо отсутствует в индексе) →
     `BLOCK: 99.0.0 not found in index (HTTP 404)`, `AC-9 gate: 1`.
   - Ветка `yanked` не имеет живого прецедента у `ktalk-mcp` (ни один релиз пакета пока не
     отзывался) — проверена на синтетическом JSON-фикстуре с `"info": {"yanked": true,
     "yanked_reason": "test reason"}`, подставленной вместо ответа сервера: `BLOCK: 9.9.9-fake
     is yanked (test reason)`, exit `1`. Первая версия команды (`grep '"yanked": false'` с
     пробелом) была прогнана на тех же двух живых концах ДО этой правки и вернула `exit 1`
     на обоих — включая опубликованный `0.10.0`, для которого гейт обязан был пропустить, а не
     блокировать; это и есть дефект, который правка устраняет.

3. **Прогнать полный набор гейтов дерева** —
   `bash scripts/check-plugin-composition.sh && bash scripts/check-prompt-language.sh && uv run python scripts/validate-content.py && bash scripts/check.sh --full`
   Успех: все четыре — нулевой код возврата; `validate-content.py` печатает `Errors: 0`;
   `check.sh --full` печатает `passed`.
   Живая проверка (2026-08-31, рабочее дерево этого репозитория): все четыре команды
   прогнаны по-настоящему при подготовке этого runbook'а — `check-plugin-composition.sh`
   → `OK`; `check-prompt-language.sh` → `OK (17 файлов проверено)`; `validate-content.py`
   → `content/: OK (31 файлов проверены)`, `Errors: 0 | Warnings: 0`; `check.sh --full`
   → `✓ check.sh --full — passed`. Все четыре — exit `0`.

4. **Закоммитить пин и версию плагина, отметить тег** —
   ```bash
   git add compat.json .claude-plugin/plugin.json README.md
   git commit -m "compat: pin ktalk-mcp <PIN>"
   git tag v<PLUGIN_VERSION>
   git push origin main --tags
   ```
   Успех: `git ls-remote --tags origin | grep v<PLUGIN_VERSION>` находит тег на удалённой
   стороне.
   Живая проверка механики команд (2026-08-31, изолированный scratch-репозиторий, не этот
   репозиторий — реальный `git push` на `main` этой задачей не выполнялся, так как создал
   бы настоящий релизный коммит/тег в общем дереве вне мандата документационной задачи):
   `git add`/`git commit -m "..."`/`git tag vX.Y.Z` последовательно отработали на
   изолированном репозитории — коммит и тег созданы, `git log --oneline` и `git tag -l`
   подтверждают. `git push ... --tags` не проверялся против настоящего `origin` (нет
   тестового remote) — синтаксис стандартный, семантика не отличается от уже
   применяемого в этом дереве `git push origin main --tags`.

5. **Health check после публикации** — маркетплейс раздаёт `main` без фиксации на теге
   (`.claude-plugin/marketplace.json`, `"source": "./"`), поэтому первый настоящий
   потребитель конфигурации — свежая установка пакета плюс онбординг-скрипт, не сам git —
   ```bash
   uv tool install "ktalk-mcp==<PIN>" \
     && bash scripts/ktalk-onboard.sh check --json
   ```
   Успех: JSON содержит `"status":"ok"` и `"installed_version":"<PIN>"`. Прогон в чистом
   окружении (контейнер/venv без ранее установленного `ktalk-mcp`) — установленная версия не
   должна оказаться артефактом машины релиз-инженера.
   Живая проверка (2026-08-31, эта машина, `ktalk-mcp` уже стоял версии `0.10.0` — не чистое
   окружение, поэтому это проверка команды, не проверка «холодной» установки): `uv tool
   install "ktalk-mcp==0.10.0"` — `Installed 2 executables: ktalk, ktalk-mcp`; следом
   `bash scripts/ktalk-onboard.sh check --json` вернул
   `{"status":"ok","installed_version":"0.10.0","min_version":"0.10.0",...}`, exit `0`.

## Rollback

Откат плагина и откат пакета — разные процедуры на разных репозиториях; не путать одно с
другим, они не откатываются одной командой.

### Откат плагина

Применяется, когда дефект найден в самом плагине (промт, скрипт, состав дерева) уже после
пуша тега на `main`.

1. Найти коммит(ы) релиза — `git log --oneline -5`.
2. **Отменить их на `main` — с учётом того, что `main` этого репозитория интегрируется
   merge-коммитами (`git log --oneline --merges main`), а не fast-forward: голый `git revert
   --no-edit <sha>` на merge-коммите отказывает («commit is a merge but no -m option was
   given») — единственный путь назад не отрабатывает ровно на типичном коммите этой ветки.**
   Число родителей отличает один случай от другого и решает, нужен ли `-m 1`:
   ```bash
   SHA=<merge-or-release-commit-sha>
   PARENTS="$(git log -1 --format='%P' "$SHA" | wc -w | tr -d ' ')"
   if [ "$PARENTS" -gt 1 ]; then
     echo "merge-коммит ($PARENTS родителя) — revert -m 1"
     git revert --no-edit -m 1 "$SHA"
   else
     echo "обычный коммит ($PARENTS родитель) — revert без -m"
     git revert --no-edit "$SHA"
   fi
   ```
   Успех: вывод называет тип коммита («merge-коммит» / «обычный коммит») и `git revert`
   завершается новым коммитом отмены (`git log --oneline -1` показывает `Revert "..."`).

   **Живая проверка (2026-08-31, две изолированные disposable-копии этого же репозитория —
   `git clone` в scratch-каталог, не рабочее дерево, `git merge` этой роли запрещён ADR-036
   Д5/Д6 и не понадобился: оба коммита уже существуют в реальной истории `main`):**
   - Реальный merge-коммит `c70bc14` («Merge branch 'issue-4-en-prompt-layer' into 'main'»):
     `PARENTS=2` → ветка `-m 1` → `git revert --no-edit -m 1 c70bc14` завершился коммитом
     `f41b8a6 Revert "Merge branch 'issue-4-en-prompt-layer' into 'main'"`, exit `0`.
   - Тот же `c70bc14` голым `git revert --no-edit c70bc14` (старая форма команды, без
     определения родителей) — `error: commit ... is a merge but no -m option was given.`,
     `fatal: revert failed`, exit `128`: старая форма подтверждённо не работает на этом
     коммите, что и было находкой ревью.
   - Обычный (не merge) коммит `7fbdc0d` из той же истории: `PARENTS=1` → ветка без `-m` →
     `git revert --no-edit 7fbdc0d` завершился коммитом `97055f5 Revert "compat: пол
     ktalk_mcp_min_version 0.10.0 (issue #3)"`, exit `0`.
3. Если тег уже пушнут и указывает на дефектный коммит — снять его:
   `git push origin :refs/tags/v<BAD_VERSION> && git tag -d v<BAD_VERSION>`.
4. Запушить откат — `git push origin main`.
5. Проверка отката: `git show origin/main:.claude-plugin/plugin.json | grep version`
   показывает версию **до** дефектного релиза; `bash scripts/check.sh --full` зелёный на
   откаченном состоянии.
6. Довести до операторов — `/plugin marketplace update ktalk-plugins` (команда Claude Code,
   не shell; исполняется в сессии оператора тем же синтаксисом, что и в README «Быстрый
   старт», UI-эквивалента нет и не нужен — команда уже текстовая). Успех виден оператору по
   версии в выводе установки плагина.

### Откат пакета

PyPI не допускает перезаписи или удаления уже опубликованной версии — «откат» пакета не
переписывает файл на месте, а либо отзывает релиз (yank), либо публикует новую
исправленную версию.

1. Отозвать дефектную версию — **UI-шаг, эквивалента CLI нет**: страница управления
   релизом на pypi.org (`Manage → Release → Options → Yank`), путь и механизм проверены
   2026-08-31 на публичном PyPI. Yank не удаляет файлы и не ломает уже выданные точные пины
   (PEP 592: `==<version>` продолжает резолвиться даже для yanked-релиза) — существующие
   установки оператора через `uv tool install ktalk-mcp==<pin>` не пострадают, но шаг 2
   пред-релизного гейта (AC-9) на этот `<pin>` теперь возвращает ненулевой код для *новых*
   релизов плагина — это и есть замысел: yanked-версия не проходит AC-9 повторно.
2. Опубликовать исправленную версию `<PIN_FIXED>` в репозитории `ktalk-mcp` — процедура
   того репозитория, не этого дерева.
3. Провести релиз плагина заново с новым пином — весь раздел «Steps» целиком, с `<PIN>` =
   `<PIN_FIXED>`. Не пропускать шаг 2 (AC-9) — именно он ловит случай «плагин уже
   выпущен на дефектный пин, пакет только что отозван»: без повторного прогона AC-9 на
   `<PIN_FIXED>` риск воспроизводится один в один.
4. Если плагин уже разошёлся операторам с отозванным `<PIN>` до обнаружения дефекта —
   это экстренный вариант шага 3, не отдельная процедура: тот же порядок, с приоритетом
   (пропустить очередь обычных изменений), не с другим набором команд.

## Диагностика у оператора

Коды возврата `scripts/ktalk-onboard.sh check`/`install` (не меняются этим runbook'ом,
приведены для диагностики релиз-инженером и на линии поддержки):

| Код | Статус | Причина | Команда-лечение |
|---|---|---|---|
| `0` | `ok` | версия совпадает с пином | — |
| `10` | `missing_cli` | пакет не установлен, `ktalk` не резолвится | `bash scripts/ktalk-onboard.sh install` (санкция `allow_install`, код `30`, если санкции нет) |
| `11` | `outdated` | установленная версия отличается от пина — в любую сторону | `bash scripts/ktalk-onboard.sh grant update && bash scripts/ktalk-onboard.sh install` |
| `12` | `missing_uv` | `uv` не найден в PATH | установить `uv`, затем повторить `check` |
| `20` | `error` | `compat.json` не читается или не содержит ключ `ktalk_mcp_version` | переустановить плагин (файл — часть дерева плагина, не машины оператора) |
| `30` | `no_sanction` | пакета нет, санкции `allow_install` нет | `bash scripts/ktalk-onboard.sh grant install` |
| `31` | `install_failed` | команда ремонта завершилась ненулевым кодом | смотреть `uv_output`/`return_code` в `--json`, состояние машины не менялось |
| `32` | `no_update_sanction` | версия не совпадает с пином, санкции `allow_update` нет | `bash scripts/ktalk-onboard.sh grant update` |
| `33` | `no_tty` | `grant`/`revoke` вызваны не из интерактивной сессии | повторить из TTY-сессии оператора |

**Частный случай кода `32` — версия установлена НОВЕЕ пина.** До ADR-022 такое расхождение
было безусловным `ok` (порог, не пин); теперь требует той же санкции `allow_update`, что и
версия старше пина (ADR-022 Д2, Д3). Если новая версия установлена ради другой, не связанной
с этим плагином задачи на той же машине (`uv tool` — один глобальный слот, ADR-014 §3), выдача
`grant update` откатит эту чужую версию до пина — не сосуществование, а замена. Если откат
нежелателен: не давать `grant update`, а поставить нужную для сторонней задачи версию через
изолированное окружение, не через `uv tool` (например `uvx --from "ktalk-mcp==<нужная
версия>" <команда>` разово, или отдельный venv) — тогда машинно-глобальный слот `uv tool`
остаётся на пине плагина, а сторонняя задача не конкурирует с ним за один и тот же слот.

## Ломающее изменение: снятие MCP-поверхности

С релиза, закрывшего DEV-002, плагин не объявляет MCP-сервер: `.mcp.json` удалён,
`mcp__ktalk__*` не появляется в сессии оператора как побочный эффект установки плагина
(AC-5/AC-6 capability-спеки).

- **Как объявляется.** В этом репозитории — через Conventional Commits: коммит релиза несёт
  `!` в типе (`feat(boundary)!:`) и футер `BREAKING CHANGE:` с точным списком того, что
  исчезает (прецедент — коммит `69ef207`, `git log --grep="BREAKING CHANGE"` находит его).
  Отдельного `CHANGELOG.md` в дереве нет — коммит релизного merge — единственный источник
  объявления; при следующем ломающем изменении граница объявления та же, не переоткрывать
  вопрос «где писать» заново.
- **Где оператор читает CLI-эквиваленты.** `references/onboarding.md`, раздел
  «Retired MCP tools — CLI equivalents» — таблица трёх инструментов, чьё CLI-имя отличается
  от MCP-имени. Первые две строки таблицы названы по роли, не по литеральному
  MCP-идентификатору инструмента — тот запрещён во всём дереве плагина проверкой
  `check-plugin-composition.sh` («MCP-имя операции встреч вместо CLI»), включая объяснительный
  текст; это ограничение формы, не пропуск (ADR-022 companion, «Boundaries»).
- **Регресс, который ловит гейт.** Возврат `.mcp.json` или появление ключа `ktalk` внутри
  `mcpServers` — `check_no_mcp_server()` в `scripts/check-plugin-composition.sh` (шаг 3 этого
  runbook уже прогоняет его на каждом релизе).

## Monitoring

Сетевых сервисов и очередей у этого плагина нет — деплой сводится к git-репозиторию плагина и
PyPI-пакету, метрики уровня «латентность»/«RPS» неприменимы. Наблюдаемые сигналы:

- **Метрика: код возврата шага 2 (AC-9 gate) на попытке релиза.** Норма — `0`. Ненулевой —
  релиз плагина не должен продолжиться; это не алерт дежурному, а стоп-условие самого
  пайплайна (см. Steps, шаг 2).
- **Метрика: расхождение `compat.json` пина и факта индекса пакета вне момента релиза.**
  Проверяется вручную командой шага 2 при подозрении на дрейф (например, кто-то откатил
  версию пакета после того, как плагин уже был выпущён) — постоянного расписания нет, триггер
  ручной или по инциденту.
- **Дашборд.** Отдельного дашборда нет — источник истины: тег `v<PLUGIN_VERSION>` в
  git-репозитории плагина и страница релизов пакета `ktalk-mcp` на PyPI
  (`https://pypi.org/project/ktalk-mcp/#history`).

## Escalation

- **Кто дежурит.** Роль `/nauta:devops` эпика (координируется через `/nauta:pm`) — отдельного
  круглосуточного дежурства для плагина без пользовательской нагрузки на инфраструктуру не
  заведено.
- **Когда эскалировать.** Шаг 2 (AC-9) падает на уже подтверждённом релиз-инженером `<PIN>`
  (индекс пакета вернул не то, что ожидалось) — эскалация на владельца репозитория
  `ktalk-mcp`, не решается локально правкой пина наугад. Подозрение на компрометацию канала
  распространения пакета (пин существует, но контент не тот, что собрал релиз-инженер) —
  эскалация DevSecOps (supply-chain, вне мандата DevOps; BA-001 явно вывела проверку по
  хэшам за пределы этой задачи).

## Known problems

- **Онбординг сообщает `outdated` сразу после релиза плагина, хотя пакет только что
  поставлен** → шаг 2 (AC-9) был пропущен или прогнан на неверном `<PIN>` → перепроверить
  `compat.json` командой шага 1 и повторить шаг 2 вручную; если `AC-9 gate: 0` — проблема на
  машине оператора (кэш `uv`, устаревший `~/.local/bin` в PATH), не в релизе.
- **`finish_install` возвращает `outdated` после видимо успешной команды ремонта** →
  менеджер пакетов вернул код `0`, но резолвнутая версия не равна пину (индекс отдал не тот
  артефакт, либо кэш `uv` держит старую версию) → `uv cache clean ktalk-mcp` и повторить
  `bash scripts/ktalk-onboard.sh install`.
- **Оператор с уже установленной более новой версией получает `no_update_sanction` (код `32`)
  там, где раньше (до этого релиза) получал тихий `ok`** → ожидаемое поведение точного пина
  (ADR-022 Д2/Д3), не дефект → см. «Диагностика у оператора», частный случай кода `32`.
