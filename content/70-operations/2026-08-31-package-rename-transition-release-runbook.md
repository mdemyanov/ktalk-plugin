# Runbook: переход `ktalk-mcp` → `ktalk-cli` — три публикации, гейт, откат по идентичности

**Capability:** `openspec/specs/package-rename-transition/spec.md`
**ADR:** `content/00-project/adr/ADR-024-package-rename-transition.md`
**Architecture:** `content/40-architecture/2026-08-31-package-rename-transition.md`
**Соседний runbook:** `content/70-operations/2026-08-31-cli-only-boundary-release-runbook.md` —
описывает **уже состоявшийся** релиз 0.11.0/1.7.0 (снятие MCP-поверхности, два репозитория).
Тот документ не переписан этим раундом и продолжает описывать тот релиз буквально: его пример
живой проверки AC-9 (`PIN=0.10.0`), его форензика `git revert` на конкретных sha
(`c70bc14`/`f41b8a6`/`7fbdc0d`/`97055f5`) и его раздел «Ломающее изменение: снятие
MCP-поверхности» остаются точным отчётом о том релизе. Этот runbook — для **следующего**,
структурно другого релиза: трёх публикаций вместо двух, новой схемы пина
(`package_name`+`package_version` вместо `ktalk_mcp_version`, ADR-024 Д1) и отката по
идентичности пакета, а не только по версии. Он ссылается на приёмы соседнего документа вместо
того, чтобы повторять их (техника `git revert -m 1` на merge-коммите, структурный JSON-парсер
вместо `grep` по чужому форматированию, PEP 592) — см. «Почему новый файл, а не правка
существующего» ниже.

## Purpose

Пакет `ktalk-mcp`, от которого зависит плагин, переименовывается в `ktalk-cli`. Переход
состоит из трёх публикаций в строгом порядке (`ktalk-cli` 1.0.0 → финальная версия-указатель
`ktalk-mcp` 0.11.0 → плагин 1.8.0), и порядок — условие приёмки, не пожелание: плагин с пином
на неопубликованный `ktalk-cli` ставит оператора в тупик так же, как ставил бы пин на
неопубликованную версию (`cli-only-boundary`, AC-9), только с добавленным риском —
`compat.json` теперь несёт ДВА поля идентичности (`package_name`, `package_version`), и
рассинхронизация может случиться по каждому из них независимо. Используй этот runbook при
публикации `ktalk-cli` 1.0.0, финальной версии-указателя `ktalk-mcp` 0.11.0 и релиза плагина
1.8.0, и при откате любой из трёх публикаций.

**Почему новый файл, а не правка существующего.** Цена переписывания `2026-08-31-cli-only-
boundary-release-runbook.md` на месте — тот документ перестаёт быть точным отчётом о релизе
0.11.0/1.7.0: его форензика (реальные sha ревертов, реальный прогон AC-9 на `PIN=0.10.0`,
разбор дефекта `git revert` без `-m 1` на merge-коммите этой ветки) осмысленна только в
привязке к тому релизу, и переписывание либо потеряло бы её, либо потребовало нести обе
истории в одном файле языком дельты («было … стало …»), что CLAUDE.md прямо запрещает для
постоянных документов. У этого решения есть цена — два документа с частично пересекающейся
структурой (Preconditions/Steps/Rollback/Диагностика), риск дрейфа между ними на общих
местах. Мера против дрейфа — этот файл не повторяет собственными словами то, что уже верно
сказано соседним документом (git-revert-на-merge-коммите, PEP 592, структурный парсер вместо
`grep`), а прямой ссылкой на него; общие места, которые здесь всё же присутствуют (структурный
парсер индекса), параметризованы под новое имя пакета, а не пересочинены.

Дополнительная, отдельная от объёма причина не править файл на месте: схема `compat.json`
меняется необратимо (`ktalk_mcp_version` → пара `package_name`/`package_version`, ADR-024 Д1) —
шаг 1 старого runbook'а (`sed` по ключу `ktalk_mcp_version`) синтаксически перестаёт
соответствовать файлу уже после этого перехода, независимо от решения о переписывании; это
означает, что старый файл в любом случае не годится как процедура для релизов ПОСЛЕ этого
перехода — довод для нового файла, а не аргумент оставить старый как есть.

## Preconditions

- Доступ на push и право тегировать в **трёх** местах: репозиторий пакета (публикует
  `ktalk-cli` и финальный `ktalk-mcp`), репозиторий плагина `ktalk-plugin` (тег `v1.8.0`).
  Публикацию в PyPI выполняет владелец пакета или CI того репозитория — не эта роль и не эта
  задача (см. «Санкция публикации» ниже).
- **Санкция публикации получена и зафиксирована** для каждой из двух публикаций пакета
  (`ktalk-cli` 1.0.0, `ktalk-mcp` 0.11.0) отдельно — см. раздел ниже. Без неё шаг 1 и шаг 2 не
  начинаются, независимо от готовности кода.
- `compat.json` этого дерева уже несёт схему `package_name`/`package_version` (ADR-024 Д1,
  реализация Dev) — команды шага 4 ниже пишут в эти два ключа, не в `ktalk_mcp_version`.
  Проверка перед стартом: `python3 -c "import json; d=json.load(open('compat.json')); assert
  set(d) == {'package_name','package_version'}, d; print('schema OK:', d)"`.
  Живая проверка (2026-09-01, рабочее дерево этого репозитория, только чтение):
  ```
  $ python3 -c "import json; d=json.load(open('compat.json')); assert set(d) == {'package_name','package_version'}, d; print('schema OK:', d)"
  schema OK: {'package_name': 'ktalk-cli', 'package_version': '1.0.0'}
  ```
  Схема уже мигрирована, значения — уже целевые (`ktalk-cli`/`1.0.0`); это опережающее
  состояние дерева относительно факта публикации — то самое условие, которое гейт шага между
  публикациями 1 и 3 обязан поймать, если тег `v1.8.0` попытаются создать раньше публикации.
- `uv`, `curl`, `git`, `python3` есть в PATH машины релиз-инженера.
- Секреты токена оператора контура (`KTALK_SESSION_TOKEN` и т.д.) в релизном окружении не
  нужны — тот же принцип, что в соседнем runbook'е (`run_clean`, NFR-19); здесь не
  переопределяется.

## Санкция публикации

Требование (`openspec/specs/package-rename-transition/spec.md`, «Neither package is published
to PyPI without a prior, explicit owner sanction») запрещает публиковать `ktalk-cli` 1.0.0 или
финальную версию-указатель `ktalk-mcp` 0.11.0 автоматизацией или агентом без предшествующей
явной, датированной инструкции владельца, называющей пакет, версию и индекс. В этом дереве нет
CI-пайплайна публикации (Brief for DevOps, companion-статья) — санкция сегодня процедурная, не
файл и не гейт этого репозитория; будущий публикационный CI (в любом из двух репозиториев)
обязан читать её тем же fail-closed приёмом, каким `onboarding.toml` читает
`allow_install`/`allow_update` (ADR-014 пакета §2) — отсутствие записи блокирует, не пропускает.

**Форма.** Одна строка на публикацию, с тремя обязательными полями — пакет, версия, индекс —
и датой:

```
Sanction: publish ktalk-cli==1.0.0 to PyPI — <владелец>, 2026-MM-DD
Sanction: publish ktalk-mcp==0.11.0 to PyPI — <владелец>, 2026-MM-DD
```

**Где фиксируется.** Трейлером в коммите релиз-инженера того репозитория, который выполняет
публикацию (тот же класс механизма, что уже занят футером `BREAKING CHANGE:` в этом дереве,
прецедент — коммит `69ef207`, `git log --grep="BREAKING CHANGE"`): коммит, готовящий релиз
пакета, несёт футер `Sanction: publish <package>==<version> to PyPI — <owner>, <date>`. Это
даёт постоянный, greppable, переживающий закрытие эпика след в истории git — не файл
конфигурации этого дерева и не запись в сторе задач эпика (santкция необратимого действия не
исчезает вместе с закрытием эпика, «Правило трёх домов», CLAUDE.md). Проверка перед
публикацией — команда с проверяемым исходом, не абзац «убедитесь»:

```bash
SHA="<коммит релиза пакета>"
git -C <путь-к-репозиторию-пакета> log -1 --format=%B "$SHA" \
  | grep -Eq '^Sanction: publish ktalk-cli==1\.0\.0 to PyPI — .+, [0-9]{4}-[0-9]{2}-[0-9]{2}$' \
  && echo "sanction OK" || { echo "BLOCK: no dated sanction trailer for this exact package/version"; exit 1; }
```

**Непроверено этой задачей** — команда требует реального коммита в репозитории пакета
(`ktalk-mcp`/`ktalk-cli`), в который эта роль не пишет (мандат задачи: только
`content/70-operations/`, дерево пакета — read-only). Проверить перед первым использованием:
на любом коммите с настоящим футером `Sanction: publish <pkg>==<ver> to PyPI — <owner>, <date>`
и на коммите без него — команда обязана вернуть `0` и `1` соответственно; синтаксис `grep -E`
идентичен уже проверенному в этом дереве шаблону (соседний runbook, шаг «Обновить пин»).

Публикацию — включая тестовую, включая с фиктивным пином — эта задача (DevOps, OPS-001) не
выполняет и не будет выполнять: ни один шаг ниже с реальным обращением к индексу публикации не
запущен этой ролью.

## Steps

Порядок необратим: `ktalk-cli` 1.0.0 первой, финальная версия-указатель `ktalk-mcp` 0.11.0
второй, плагин 1.8.0 последним. Между публикацией пакета и тегом плагина стоит обязательный
гейт (шаг 3) — единственный носитель требования «The plugin is not released ahead of the
renamed package's first published version» на стороне этого дерева.

1. **Публикация `ktalk-cli` 1.0.0 в PyPI** — выполняется в репозитории пакета, не в этом
   дереве (та же граница, что уже действует для `ktalk-mcp` в соседнем runbook'е,
   Preconditions). Прекондиция — санкция выше. Команда публикации (`uv build && uv publish`
   или эквивалент CI пакета) вне мандата этой роли и не приводится здесь текстом ради
   правдоподобия — она принадлежит процессу того репозитория.
   Успех проверяется отсюда, без доступа к секретам публикации, структурным парсером
   ответа индекса, не `grep` по сырому JSON (прецедент дефекта — `content/lessons-learned.md`,
   запись DevOps/2026-08-31, «правка после ревью координатора»):
   ```bash
   pypi_gate() { # pypi_gate <пакет> <версия> — 0 = опубликован и не отозван, 1 = блок
     local PKG="$1" PIN="$2" HTTP_CODE
     HTTP_CODE="$(curl -sS -o /tmp/pypi-gate.json -w '%{http_code}' \
                  "https://pypi.org/pypi/${PKG}/${PIN}/json")"
     python3 - "$HTTP_CODE" "$PKG" "$PIN" /tmp/pypi-gate.json <<'PY'
import json, sys
code, pkg, pin, path = sys.argv[1], sys.argv[2], sys.argv[3], sys.argv[4]
if code == "404":
    print(f"BLOCK: {pkg}=={pin} not found in index (HTTP 404)")
    sys.exit(1)
if code != "200":
    print(f"BLOCK: unexpected HTTP {code} for {pkg}=={pin}")
    sys.exit(1)
with open(path) as f:
    data = json.load(f)
if data.get("info", {}).get("yanked"):
    print(f"BLOCK: {pkg}=={pin} is yanked ({data['info'].get('yanked_reason')})")
    sys.exit(1)
print(f"OK: {pkg}=={pin} published and not yanked")
sys.exit(0)
PY
     local RC=$?
     rm -f /tmp/pypi-gate.json
     return "$RC"
   }
   pypi_gate ktalk-cli 1.0.0; echo "publish check: $?"
   ```
   Успех: `OK: ktalk-cli==1.0.0 published and not yanked`, код `0`.

   **Живая проверка (2026-09-01, реальный публичный индекс PyPI, публикация не выполнялась —
   только чтение):**
   - `pypi_gate ktalk-cli 1.0.0` на сегодняшнем состоянии индекса (публикации ещё не было) →
     `BLOCK: ktalk-cli==1.0.0 not found in index (HTTP 404)`, код `1` — гейт корректно
     блокирует, потому что публикации в реальности ещё не произошло; это ожидаемый и
     единственно верный сегодняшний исход, не дефект команды.
   - `pypi_gate ktalk-mcp 0.10.0` (реальный, уже опубликованный релиз, не отозван) →
     `OK: ktalk-mcp==0.10.0 published and not yanked`, код `0` — доказывает ветку «опубликован
     и жив» на реальных данных того же индекса, того же парсера, другого имени пакета
     (`ktalk-cli` своего живого прецедента этой ветки ещё не имеет — имя не зарезервировано:
     `curl -sS https://pypi.org/pypi/ktalk-cli/json` тоже отвечает `404` на весь пакет
     целиком, не только на версию `1.0.0`).
   - Ветка `yanked` — синтетическая фикстура (ни у `ktalk-mcp`, ни тем более у ещё не
     существующего `ktalk-cli` нет отозванных релизов): подставленный вместо ответа сервера
     JSON `{"info": {"yanked": true, "yanked_reason": "critical bug in publish sequence"}}` →
     `BLOCK: ktalk-cli==9.9.9-fake is yanked (critical bug in publish sequence)`, код `1`.

   **Исполнено 2026-09-02 (публикация выполнена по санкции владельца).** Оба пакета в индексе,
   `pypi_gate` вернул `0` по `ktalk-cli 1.0.0` и по `ktalk-mcp 0.11.0`. Два замера, которые
   меняют текст самого рунбука на будущее:

   - **`uv publish` не читает `~/.pypirc`** (в его `--help` слова `pypirc` нет), поэтому
     требует токен строкой или в переменной окружения. `twine` читает — и публикация прошла
     через `uvx --from twine twine upload --non-interactive`, чтобы секрет не разглашался.
     Установленный в системе `twine` 6.2.0 при этом отвергает артефакты hatchling
     (`InvalidDistribution: '2.5' is not a valid metadata version` — старый `packaging` 25.0);
     свежий twine через `uvx` даёт `PASSED`. Это дефект проверяющего, не артефакта.
   - **Зелёный `pypi_gate` не означает «уже ставится».** Сразу после загрузки указателя
     JSON API отвечал `OK: ktalk-mcp==0.11.0 published and not yanked` (код `0`), а
     `pip install ktalk-mcp==0.11.0` в ту же секунду — `No matching distribution`
     (простой индекс ещё перечислял версии по `0.10.0`). Повтор десятками секунд позже
     прошёл с первого раза. Гейт по JSON API — условие необходимое, но не достаточное:
     если следующий шаг ставит пакет, закладывай retry-цикл, а достаточным доказательством
     считай установку в чистый venv из живого индекса.

2. **Публикация финальной версии-указателя `ktalk-mcp` 0.11.0 в PyPI** — тот же принцип шага 1
   (репозиторий пакета, отдельная санкция, не выполняется этой ролью). Контракт версии
   (Requirement «The retired `ktalk-mcp` package announces its retirement loudly, not
   silently»): единственная точка входа — команда `ktalk-mcp`, не объявляет `ktalk`; печатает
   в stderr имя замены и команду установки; код возврата ненулевой на каждом вызове.
   Проверка публикации — тот же `pypi_gate`:
   ```bash
   pypi_gate ktalk-mcp 0.11.0; echo "publish check: $?"
   ```
   Проверка контракта поведения (после публикации, в чистом окружении):
   ```bash
   uv tool install "ktalk-mcp==0.11.0" \
     && { ktalk-mcp 2>/tmp/ktalk-mcp-stderr.txt; echo "exit=$?"; } \
     && grep -qi 'ktalk-cli' /tmp/ktalk-mcp-stderr.txt \
     && echo "PASS: называет замену и завершается ненулевым кодом" \
     || echo "FAIL: контракт версии-указателя не выполнен"
   ```
   Успех: `pypi_gate` — `0`; вторая команда — `exit=<ненулевой>`, `PASS`.

   **Непроверено этой задачей** — версии `ktalk-mcp==0.11.0` в индексе ещё нет (см. живую
   проверку шага 1: `pypi_gate ktalk-mcp 0.11.0` вернул бы `BLOCK: ... not found`, тот же
   код, что уже показан для `ktalk-cli` выше; повторный прогон не добавляет новой ветки).
   Проверить перед первым использованием: после реальной публикации 0.11.0 — на чистой машине
   или в контейнере без ранее установленного `ktalk-mcp`.

3. **Гейт перед релизом плагина — обязателен, блокирующий.** Плагин не тегируется, пока
   `ktalk-cli==1.0.0` не резолвится из индекса и не отозван. Это та же функция `pypi_gate` шага
   1, вызванная непосредственно перед шагом 4, а не переиспользование её более раннего
   результата — состояние индекса могло измениться между шагом 1 и этим моментом (публикация
   могла быть отозвана, например, если дефект найден за время подготовки шага 2):
   ```bash
   pypi_gate ktalk-cli 1.0.0
   GATE_RC=$?
   echo "AC (release-not-ahead-of-package): $GATE_RC"
   [ "$GATE_RC" -eq 0 ] || { echo "STOP: тег v1.8.0 не создаётся"; exit 1; }
   ```
   Успех: `AC (release-not-ahead-of-package): 0`, продолжение к шагу 4. Ненулевой код —
   стоп-условие пайплайна, тег не создаётся, дальнейшие шаги не выполняются — тот же принцип,
   каким `check-plugin-composition.sh` уже управляет составом дерева (соседний runbook,
   «Форма пред-релизного условия»).

   **Живая проверка (2026-09-01, реальный индекс, тот же вызов, что в шаге 1):**
   `pypi_gate ktalk-cli 1.0.0` → `BLOCK: ktalk-cli==1.0.0 not found in index (HTTP 404)`,
   `AC (release-not-ahead-of-package): 1` — на сегодняшний момент этот гейт **обязан**
   останавливать релиз плагина, и он это делает: публикации ещё не было. Как только шаг 1
   реально пройдёт (публикация состоится), тот же вызов вернёт `0` — доказано на `ktalk-mcp
   0.10.0` в шаге 1.

4. **Прогнать полный набор гейтов дерева** —
   `bash scripts/check-plugin-composition.sh && bash scripts/check-prompt-language.sh && uv run python scripts/validate-content.py && bash scripts/check.sh --full`
   Успех: все четыре — нулевой код возврата.
   Живая проверка (2026-09-01, рабочее дерево этого репозитория, без правок дерева плагина
   этой ролью — только чтение состояния, добавлена одна статья и одна ссылка в
   `content/70-operations/_index.md`, в мандате этой задачи):
   `bash scripts/check.sh --full` → `PASS=24 FAIL=0` self-test harness, `✓ check.sh --full —
   passed`, exit `0`; `check-plugin-composition.sh`/`check-prompt-language.sh`/
   `validate-content.py` не перезапускались отдельно этим раундом сверх того, что уже входит в
   `--full` — раздел «Проверка» задачи запускает `--full` целиком.

5. **Обновить пин, версию плагина, отметить тег** (после того как шаг 3 вернул `0`) —
   ```bash
   git add compat.json .claude-plugin/plugin.json README.md references/onboarding.md
   git commit -m "compat: pin ktalk-cli 1.0.0 (package rename)"
   git tag v1.8.0
   git push origin main --tags
   ```
   Синтаксис идентичен уже применяемому соседним runbook'ом для смены пина (шаги «Обновить
   пин» / «Закоммитить пин и версию») — не повторяется здесь текстом инструкции по каждому
   файлу; отличие только в новых ключах `compat.json` (`package_name`/`package_version`) и в
   том, что диф этой правки ограничен шестью точками, которые сама требование-статья BA
   называет по имени (`compat.json`, `README.md`, `references/onboarding.md`,
   `scripts/ktalk-onboard.sh`, `scripts/test-onboard.sh`, текст имени пакета в
   `.claude-plugin/plugin.json`) — диф `skills/`/`agents/`/`commands/` обязан остаться пустым
   (проверяется тем же приёмом, что и раньше — `git diff --stat main..v1.8.0 -- skills/
   agents/ commands/` пуст).
   Успех: `git ls-remote --tags origin | grep v1.8.0` находит тег на удалённой стороне.
   **Непроверено этой задачей** — команда пишет в `compat.json`/`plugin.json`/`README.md`/
   `references/onboarding.md`, все четыре — вне мандата этой роли этим раундом (параллельно
   работает Dev) и не в чистом виде готовы к тегированию (шаги 1–3 ещё не пройдены в
   реальности). Синтаксис `git add`/`commit`/`tag`/`push --tags` тот же, что уже проверен
   соседним runbook'ом на изолированном scratch-репозитории.

6. **Health check после публикации плагина** —
   ```bash
   uv tool install "ktalk-cli==1.0.0" \
     && bash scripts/ktalk-onboard.sh check --json
   ```
   Успех: JSON содержит `"status":"ok"`, `"installed_package":"ktalk-cli"`,
   `"installed_version":"1.0.0"` — новые поля идентичности рядом с уже существующими
   `installed_version`/`min_version` (аддитивно, без переименования, architecture companion,
   «NFR Mapping», строка «Positive»/«Mitigations» ADR-024).
   **Непроверено этой задачей** — требует опубликованного `ktalk-cli==1.0.0` (нет в индексе
   сегодня, см. шаг 1) и обновлённого `scripts/ktalk-onboard.sh` с полями `pin_name`/
   `installed_identity` (реализация Dev, в процессе этим же эпиком, файл в списке
   запрещённых для правки этой ролью). Проверить перед первым использованием: в чистом
   контейнере/venv без установленного `ktalk-mcp`/`ktalk-cli`, сразу после публикации и
   релиза плагина.

## Rollback

Три публикации — три разные процедуры отката, и ключевое ограничение одно на все три:
**PyPI не допускает удаления или перезаписи уже опубликованной версии** — «откат» пакета
всегда означает либо yank (скрытие из резолвинга по диапазону), либо публикацию новой версии,
никогда не редактирование уже вышедшей (PEP 592; тот же факт, на котором уже стоит AC-9
соседнего runbook'а — не переизлагается здесь второй раз, только применяется к двум именам
вместо одного).

### Откат `ktalk-cli` 1.0.0

**Что откатывается.** Резолвинг по диапазону — `pip install ktalk-cli` (без точной версии)
перестаёт предлагать 1.0.0 после yank.

**Что не откатывается в принципе.** Точный пин `ktalk-cli==1.0.0` продолжает резолвиться и
устанавливаться и после yank (PEP 592) — плагин 1.8.0, уже разошедшийся операторам с этим
пином, не перестаёт работать и не защищён отзывом версии пакета. Файл самой версии 1.0.0 в
индексе остаётся навсегда.

**Что делать оператору владельцу пакета.**
1. Отозвать версию — UI-шаг на pypi.org (`Manage → Release → Options → Yank`), CLI-эквивалента
   нет; путь и механизм проверены на публичном PyPI соседним runbook'ом (2026-08-31), тот же
   путь верен для любого имени пакета в том же индексе.
2. Опубликовать исправленную `ktalk-cli==1.0.1` под новой, отдельной санкцией (см. «Санкция
   публикации» — санкция называет версию явно, санкция на 1.0.0 не покрывает 1.0.1).
3. Повторить шаг 3 «Steps» (гейт) на новом пине перед любым следующим релизом плагина —
   `pypi_gate ktalk-cli 1.0.1`. Пропуск этого прогона воспроизводит именно тот риск, который
   гейт создан ловить (плагин на дефектный, теперь отозванный пин).

**Что делать оператору, у которого уже сломалось** (машина, где уже стоит дефектная 1.0.0, или
где `ktalk-cli` конфликтует со всё ещё установленным `ktalk-mcp` за слот `ktalk`) — раздел
«Диагностика у оператора» ниже плюс процедура принудительной идентичности:
```bash
uv tool install ktalk-cli==1.0.1 --force
command -v ktalk && ktalk --version   # ожидание: первый токен "ktalk-cli", второй "1.0.1"
uv tool uninstall ktalk-mcp           # только после подтверждения строкой выше
```
Порядок этих трёх команд — не произвольный, а прямое следствие замеренной (не этой задачей,
координатором на синтетических пакетах) коллизии слота `uv tool`: `uninstall` пакета, чей
бинарник ещё жив, стирает файл с диска, а зависшая регистрация второго пакета в `uv tool list`
не «оживает» — вызов даёт код `127`. Обратный порядок («сначала уберите новый пакет —
`ktalk-mcp` вернётся») выглядит интуитивно, но воспроизводимо ведёт именно к этому `127`
(ADR-024 Д4). `uv tool list` в этой процедуре не используется как проверка результата —
список подтверждённо показывает обоих владельцами одной команды после `--force` и не отражает,
кто реально исполняется (то же измерение); проверка — только живое разрешение (`command -v` +
`ktalk --version`).

### Откат финальной версии-указателя `ktalk-mcp` 0.11.0

**Что откатывается.** Та же схема, что у `ktalk-cli`: yank версии 0.11.0 убирает её из
резолвинга по диапазону; точный пин `ktalk-mcp==0.11.0` продолжает резолвиться (PEP 592).
Дефект в самом тексте/коде возврата версии-указателя (например, сообщение не называет
`ktalk-cli`, или код возврата случайно нулевой) чинится публикацией `ktalk-mcp==0.11.1` —
**не** `--force`-переустановкой другого пакета: это тот же самый пакет, другая версия, обычный
случай "outdated", ветка `slot_collision` здесь не участвует.

**Что не откатывается в принципе.** Оператор, который уже апгрейднул установленный `ktalk-mcp`
на месте до 0.11.0 (или поставил её свежей) без отдельной установки `ktalk-cli`, уже потерял
голую команду `ktalk` — это необратимая, признанная цена решения (Requirement «A bare `ktalk`
invocation is not found after adopting the pointer», ADR-024 Д5), не дефект, который откат
версии-указателя способен вернуть. Yank 0.11.0 не восстанавливает `ktalk` этому оператору —
единственный путь назад для него — установить `ktalk-cli` отдельно (см. «Диагностика у
оператора», состояние «только новый пакет отсутствует после апгрейда указателя»,
которое на практике для этого оператора читается как «отсутствуют оба»).

**Что делать оператору, у которого уже сломалось.** Установить `ktalk-cli` явно, тем же
приёмом, что и предполагает штатный сценарий этой миграции — версия-указатель не пытается
вернуть `ktalk` сама, потому что по контракту не объявляет эту команду вовсе:
```bash
uv tool install ktalk-cli==1.0.0
command -v ktalk && ktalk --version   # ожидание: "ktalk-cli 1.0.0"
```
Здесь нет коллизии слота (версия-указатель `ktalk-mcp` не регистрирует `ktalk` — Д5 ADR-024) —
`--force` не требуется и не должен использоваться.

### Откат плагина 1.8.0

**Что откатывается.** Декларация плагина — тег, `compat.json`, README, `references/
onboarding.md`. Механика (какой коммит отменять, revert с `-m 1` на merge-коммите, снятие тега)
— полностью описана соседним runbook'ом («Откат плагина», шаги 1–6) и не повторяется здесь
текстом: тот же приём верен для любой версии плагина этого репозитория, потому что зависит от
формы истории git (`main` интегрируется merge-коммитами), не от содержимого релиза.

**Что не откатывается в принципе.** Пакет `ktalk-cli==1.0.0`, уже установленный на машинах
операторов, которые успели поставить плагин 1.8.0 до отката, не удаляется откатом плагина —
git revert меняет декларацию (`compat.json`), не состояние чужих машин. Оператор с уже
установленным `ktalk-cli` и откаченным на предыдущий пин плагином получит `wrong_package`
(если предыдущий пин называет `ktalk-mcp`) или `outdated` (если предыдущий пин — более ранняя
`ktalk-cli`) при следующем `check` — ожидаемо, не тихо.

**Что делать оператору, у которого уже сломалось** (обновил плагин, машина уже перешла на
`ktalk-cli`, откат плагина требует вернуться на пин `ktalk-mcp`) — та же процедура
принудительной идентичности, что в «Откат `ktalk-cli` 1.0.0» выше, с обратным направлением
(целевая идентичность — `ktalk-mcp`, оставленная — `ktalk-cli`):
```bash
uv tool install ktalk-mcp==<откатной-пин> --force
command -v ktalk && ktalk --version   # ожидание: первый токен "ktalk-mcp"
uv tool uninstall ktalk-cli
```

## Диагностика у оператора

Три состояния — какой пакет фактически владеет командой `ktalk`, не какой пакет установлен
(разница существенна: `uv tool list` может числить пакет «владельцем», не будучи фактическим
исполнителем, если поверх него когда-либо выполнялся ручной `--force` — измерение
координатора). Различение — раздельным сравнением имени и версии пина
(`installed_identity()`, ADR-024 Д2, architecture companion «Data flow» п.3), новые статусы и
коды `E_WRONG_PACKAGE=13`/`E_SLOT_COLLISION=34` рядом с уже существующими из соседнего
runbook'а (`E_MISSING_CLI=10`, `E_OUTDATED=11` и т.д. — таблица там не дублируется здесь).

| Состояние | Как отличить | Диагностика `ktalk-onboard.sh check --json` | Что делать |
|---|---|---|---|
| **Только старый пакет** (`ktalk-mcp` любой версии, включая финальную 0.11.0), пин плагина — `ktalk-cli` | `command -v ktalk` резолвится (если версия не 0.11.0 — у неё нет `ktalk`), `ktalk --version` называет `ktalk-mcp` первым токеном | `"status":"wrong_package"`, `"installed_package":"ktalk-mcp"`, `"pinned_package":"ktalk-cli"` | `bash scripts/ktalk-onboard.sh grant update && bash scripts/ktalk-onboard.sh install` — санкция `allow_update` уже покрывает смену идентичности, новый ключ не заводится (ADR-024 Д3) |
| **Только новый пакет** (`ktalk-cli`), пин плагина совпадает | `command -v ktalk` резолвится, `ktalk --version` называет `ktalk-cli` и версию, равную пину | `"status":"ok"`, `"installed_package":"ktalk-cli"` | ничего — целевое состояние |
| **Оба сразу** (обычно след ручного `--force` в прошлом, или переходное состояние во время миграции машины) | `uv tool list` показывает строки для обоих имён (`ktalk-mcp`, `ktalk-cli`); которая из них реально исполняется, решает только `command -v ktalk` + `ktalk --version`, не список | `registered_both: true` — диагностический признак в JSON рядом со статусом, вычисленным по факту исполнения (не отказ сам по себе — architecture companion, «Data flow» п.2) | Ничего не делать автоматически. Если действующий пакет соответствует пину — оставить, зависшую регистрацию снять `uv tool uninstall <неактивный>` только после подтверждения `command -v`/`ktalk --version`, не раньше (тот же порядок, что «Откат», предупреждение о коде 127) |

**Частный случай — оператор, у которого `ktalk` не резолвится вовсе (код `127` при прямом
вызове).** Может означать любое из: (а) ни один из двух пакетов не установлен (штатный
`missing_cli`), (б) владеющий бинарником пакет был деинсталлирован, пока второй остаётся
зарегистрированным, но не действующим владельцем (замеренная третья строка коллизии слота —
`uv tool uninstall` того, чей бинарник жив, стирает файл, запись второго не «оживает»), (в)
единственный установленный пакет — финальная версия-указатель `ktalk-mcp` 0.11.0, которая
по контракту не объявляет `ktalk` вовсе (не дефект, ожидаемая цена решения, см. «Ломающее
изменение» ниже). Различение (а)/(б)/(в) — `bash scripts/ktalk-onboard.sh check --json`:
`missing_cli` без `registered_both` — (а); `missing_cli` с `registered_both: true` — (б);
`installed_package` называет `ktalk-mcp` с версией `0.11.0` явно — (в). Прямой вызов `ktalk` в
терминале, в обход проверки плагина, во всех трёх случаях просто вернёт `127` — эта
недифференцированность прямого вызова признана и не маскируется (Requirement «A bare `ktalk`
invocation is not found after adopting the pointer»).

## Ломающее изменение: второе подряд, потеря `ktalk` при апгрейде указателя

Это уже второе ломающее изменение подряд в этом плагине (первое — снятие MCP-поверхности,
описано соседним runbook'ом, «Ломающее изменение: снятие MCP-поверхности», коммит `69ef207`).
Тот же механизм объявления — Conventional Commits, коммит релиза несёт `!` в типе и футер
`BREAKING CHANGE:` с точным списком того, что меняется; не переоткрывается здесь заново
(соседний runbook, тот же раздел, «Как объявляется»).

- **Цена, признанная явно, не спрятанная.** Оператор, который апгрейднул уже установленный
  `ktalk-mcp` на месте до финальной версии-указателя 0.11.0, или поставил её свежей, без
  отдельной установки `ktalk-cli`, теряет голую команду `ktalk` целиком — прямой вызов в
  обход проверки плагина получает обычный отказ шелла (код `127`), не диагностику. Это принятая
  цена решения владельца пакета (`ktalk-mcp`, дерево пакета, Д6-эквивалент того ADR),
  зафиксированная требованием этого дерева («The retired `ktalk-mcp` package announces its
  retirement loudly, not silently») — ни один текст плагина не формулирует это состояние как
  «команда продолжает работать».
- **Где оператор читает миграцию.** `references/onboarding.md` (правка Dev, вне мандата этой
  роли этим раундом) — тот же файл, что уже несёт таблицу «Retired MCP tools — CLI
  equivalents» после первого ломающего изменения; для второго ожидается аналогичный раздел
  «Package rename — `ktalk-mcp` → `ktalk-cli`», не спроектированный этой статьёй (Dev/SA
  companion уже определили состав правки: `README.md`, `references/onboarding.md`,
  `scripts/ktalk-onboard.sh`, `scripts/test-onboard.sh`).
- **Регресс, который ловит гейт.** Возврат литерала `"ktalk-mcp"` в текст сообщений/команд
  ремонта после релиза на `ktalk-cli` (architecture companion, «Точка правки: литералы
  ktalk-mcp внутри функций», четыре места кода) — тест на «имя пакета не хардкожено» обязан
  быть мутационным, не сравнением с текущим значением источника (`content/lessons-learned.md`,
  запись QA-author/2026-09-01, `ktalk-plugin-foz.17`; тот же урок применён здесь без повторного
  вывода). Этот гейт — контракт QA-author/`scripts/test-onboard.sh`, не этой роли; здесь только
  зафиксирована граница ответственности, чтобы известная находка не потерялась между ролями.
- **Отличие от первого ломающего изменения по масштабу цены.** Первое (снятие MCP-поверхности)
  не убирало ничего из уже работающего CLI-пути оператора — только внутренний MCP-канал,
  которым управляли не операторы напрямую. Второе способно забрать команду `ktalk` целиком у
  оператора, который ничего не менял сам (просто получил апгрейд пакета) — это качественно
  другая цена, и диагностика (см. выше) обязана называть её отдельным, не общим с «версия
  устарела» статусом именно по этой причине.

## Monitoring

Те же основания, что у соседнего runbook'а (нет сетевых сервисов и очередей этого плагина —
не переизлагаются), плюс сигналы, специфичные для перехода по идентичности:

- **Метрика: код возврата гейта шага 3 (`pypi_gate ktalk-cli <pin>`) на попытке релиза
  плагина.** Норма — `0`. Ненулевой — стоп-условие пайплайна, не алерт дежурному.
- **Метрика: `registered_both` в выводе `check --json` по флоту операторов, если он агрегируется
  (не заведено этой задачей — процедурный сигнал на будущее).** Ненулевая доля означает, что
  ручной `--force` где-то применялся вне процедуры — не авария сама по себе, повод свериться,
  что действующий пакет соответствует текущему пину.
- **Дашборд.** Источники истины — тег `v1.8.0` в репозитории плагина, страница релизов
  `https://pypi.org/project/ktalk-cli/#history` и `https://pypi.org/project/ktalk-mcp/#history`
  (теперь два индекса пакета вместо одного, оба — предмет одного и того же гейта, разными
  именами).

## Escalation

- **Кто дежурит.** Та же роль, тот же принцип, что у соседнего runbook'а — `/nauta:devops`
  эпика, без отдельного круглосуточного дежурства.
- **Когда эскалировать.** Гейт шага 3 падает на пине, уже подтверждённом релиз-инженером
  опубликованным ранее (шаг 1) — индекс изменился между публикацией и релизом плагина (кто-то
  отозвал версию) — эскалация владельцу пакета, не правка пина наугад. Санкция публикации
  отсутствует или не датирована/не называет пакет и версию точно — эскалация владельцу
  плагина/пакета до публикации, не решается локально агентом или автоматизацией (сам предмет
  требования). Подозрение на компрометацию канала распространения (пин существует, но контент
  не тот, что собрал релиз-инженер) — DevSecOps (supply-chain, вне мандата DevOps, тот же
  принцип, что уже действует в соседнем runbook'е).

## Known problems

- **`uv tool install ktalk-cli==1.0.0` отказывает кодом 2, сообщением `Executable already
  exists`** → на машине уже установлен `ktalk-mcp`, владеющий тем же именем команды →
  ожидаемое, атрибутируемое поведение (`slot_collision`, `E_SLOT_COLLISION=34`), не
  `install_failed` общего вида; онбординг-скрипт не повторяет попытку с `--force`
  автоматически ни при какой санкции (ADR-024 Д3) — ручной override см. «Диагностика у
  оператора» и «Откат».
- **`ktalk-mcp` больше не резолвится (код 127), хотя `uv tool list` всё ещё числит его
  владельцем `ktalk`** → кто-то деинсталлировал реально владеющий бинарником пакет
  (`ktalk-cli`, если он был поставлен через `--force` поверх `ktalk-mcp`), запись второго
  пакета не «оживает» → переустановить целевую идентичность явно (`uv tool install
  <нужный-пакет>==<пин> --force`), подтвердить `command -v`/`ktalk --version`, только
  затем снять зависшую регистрацию — «Откат», не «удалить новый и ждать возврата старого».
- **Оператор, апгрейднувший `ktalk-mcp` на месте до 0.11.0, сообщает «команда `ktalk` пропала»**
  → ожидаемое, названное поведение финальной версии-указателя (не дефект) → установить
  `ktalk-cli` отдельно, диагностика — «Ломающее изменение» выше.
- **`bash scripts/ktalk-onboard.sh check` сообщает `wrong_package` сразу после релиза плагина,
  хотя `ktalk-cli` только что установлен вручную** → гейт шага 3 был пропущен или пин в
  `compat.json` не тот, что реально установлен на машине проверки → перепроверить `compat.json`
  (`python3 -c "import json;print(json.load(open('compat.json')))"`) и повторить `pypi_gate`
  вручную; если гейт зелёный — проблема на машине оператора (кэш `uv`, `hash -r` не выполнен
  после install в той же сессии шелла — architecture companion, edge case «`hash -r` в
  `cmd_check`»), не в релизе.
