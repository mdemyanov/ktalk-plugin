# Runbook: релиз 1.15.0 — единственный режим авторизации (session-only)

**Capability:** `openspec/specs/session-only-auth/spec.md`
**ADR:** `content/00-project/adr/ADR-028-session-only-authorisation.md`
**Requirement:** `content/30-requirements/2026-09-07-session-only-auth.md`
**Security audit:** `content/70-operations/2026-09-08-session-only-auth-security-audit.md`
(вердикт — не блокирует релиз; Находка 2 «сьюта не в GO-гейте» уже закрыта коммитом
`2792a77` до этой задачи — `.nauta-gates.yaml`, `projectGates.full`, несёт
`scripts/test-session-only-auth.sh`).
**Соседние рансбуки:** `2026-09-04-dual-channel-delivery-release-runbook.md` — форма тега
(`claude plugin tag`, не `git tag`) и механика GitHub-зеркала (`scripts/mirror-github.sh`,

## Purpose

Релиз 1.15.0 сужает промт-слой плагина до одного документированного режима авторизации —
токена браузерной сессии (ADR-028): снимает `KTALK_PERSONAL_API_KEY` из числа
поддерживаемых/рекомендуемых, называет файл токена наравне с переменной окружения, чинит
четыре находки боевой сессии 07.09.2026 (несуществующая команда `ktalk session`, разорванная
таблица команд `ktalk-meetings`, неполная ссылка на `.ktalk.toml`, отсутствующий раздел о
новизне пина `2.1.0`) и закрывает заявку GitLab `#8` (неполное описание ключей
`dashboard --json`). `compat.json` не двигается — пин `ktalk-cli` остаётся `2.1.0`. Используй
этот runbook при публикации 1.15.0 и при откате любой её части.

## Steps

Порядок: гейт → тег → GitHub-зеркало (регулярный релиз, механика соседнего runbook'а) →
закрытие заявки → health check. Тег создаётся только после того, как гейт вернул `0`.

1. **Пред-релизный гейт** — команда и живая проверка приведены в «Preconditions» выше;
   повторить на актуальном коммите слияния перед тегом, не полагаться на прогон этой задачи
   без повтора.

2. **Тег релиза — `claude plugin tag`, не `git tag`** (`CONTRIBUTING.md`, «Версия плагина и тег
   релиза»). Сначала `--dry-run`, прочитать форму тега и коммит:
   ```bash
   git checkout main && git pull --ff-only
   claude plugin tag --dry-run
   ```
   Живая проверка этой задачей (2026-09-08, эта рабочая копия, до слияния `ops-001` в `main`,
   `plugin.json` версии `1.15.0`):
   ```
   Plugin:  ktalk
   Version: 1.15.0 (from plugin.json)
   Tag:     ktalk--v1.15.0
   ✔ Dry run — would create tag ktalk--v1.15.0 at HEAD in <рабочая копия релиз-инженера>
     git -C ... tag -a ktalk--v1.15.0 -m "ktalk 1.15.0"
     git -C ... push origin refs/tags/ktalk--v1.15.0
   ```
   Самый свежий существующий тег на дату этой задачи — `ktalk--v1.14.0`
   (`git tag -l "ktalk--v*" | sort -V | tail -1`) — следующий по порядку номер совпадает с
   выводом dry-run, коллизии нет. Реальное создание — **после** того, как релизный коммит слит
   в `main`, не раньше:
   ```bash
   claude plugin tag
   ```
   Успех: `git ls-remote --tags origin | grep ktalk--v1.15.0` находит тег на удалённой стороне.

3. **GitHub-зеркало — регулярный релиз, без изменений в манифесте payload.** Механика
   полностью описана `2026-09-04-dual-channel-delivery-release-runbook.md`, разделы
   «Регулярный релиз» и «Сверка паритета» — не повторяется здесь текстом, тот же джоб
   `mirror-github`, тот же guard резолвимости ref'ов, те же три команды сверки. Специфика этого
   релиза — состав payload не менялся: манифест `.gitlab/payload-manifest.txt` называет только
   директории верхнего уровня (`.claude-plugin/`, `agents/`, `commands/`, `skills/`,
   `references/`, `scripts/`, `README.md`, `LICENSE`, `.github/`, `compat.json`), новый файл
   этого эпика (`scripts/test-session-only-auth.sh`) уже попадает под глоб `scripts/` без правки
   манифеста — живая проверка:
   ```bash
   git diff --stat main..HEAD | grep -c '^ \.gitlab/payload-manifest.txt'
   ```
   Живая проверка (2026-09-08): `0` — манифест не в диффе эпика, правка не нужна. После тега —
   дождаться зелёного джоба `mirror-github`, затем сверка паритета (три команды соседнего
   runbook'а) на `TAG=ktalk--v1.15.0`.

4. **Закрытие заявки GitLab `#8`.** Живая проверка открытых issue этой задачей (2026-09-08):
   ```bash
   glab issue list --repo tools-ai/ktalk-plugin
   ```
   ```
   #9  Автообновление плагина должно синхронизировать версию ktalk-cli на машине
   #8  ktalk-registry: SKILL.md описывает ответ dashboard --json без last_synced
   ```
   `#8` закрывается этим релизом (`skills/ktalk-registry/SKILL.md:114` теперь называет все три
   ключа верхнего уровня, включая `last_synced`); `#9` — вне периметра этого эпика (заявка BA-001
   «не входит в периметр»), не трогать.
   ```bash
   glab issue close 8 --repo tools-ai/ktalk-plugin -m "Закрыто релизом 1.15.0 (ADR-028): SKILL.md называет все три ключа dashboard --json, включая last_synced. Тег: ktalk--v1.15.0."
   ```
   Проверка после закрытия — не доверять формулировке коммита, проверить состояние:
   ```bash
   glab issue view 8 --repo tools-ai/ktalk-plugin | grep -q '^state:.*closed' && echo "issue #8: closed" || echo "issue #8: ещё open — проверить вручную"
   ```

5. **Health check после публикации** — тот же структурный JSON-парсер, что
   `2026-09-03-release-delivery-tails-release-runbook.md` вводит для AC-3e, применённый к
   версии `1.15.0`:
   ```bash
   check_installed_version() { # 0 = user-scope запись уже на ожидаемой версии, 1 = ещё нет
     local WANT="$1" PATH_JSON="$HOME/.claude/plugins/installed_plugins.json"
     python3 - "$WANT" "$PATH_JSON" <<'PY'
import json, sys
want, path = sys.argv[1], sys.argv[2]
with open(path) as f:
    data = json.load(f)
entries = data.get("plugins", {}).get("ktalk@ktalk-plugins", [])
user_entries = [e for e in entries if e.get("scope") == "user"]
if not user_entries:
    print("BLOCK: no user-scope installed_plugins.json entry for ktalk@ktalk-plugins")
    sys.exit(1)
got = user_entries[0].get("version")
if got == want:
    print(f"OK: installed_plugins.json (scope=user) already at {got}")
    sys.exit(0)
print(f"BLOCK: installed_plugins.json (scope=user) still at {got}, expected {want}")
sys.exit(1)
PY
   }
   claude plugin marketplace update ktalk-plugins
   claude plugin update ktalk@ktalk-plugins
   check_installed_version 1.15.0; echo "health-check gate: $?"
   ```
   Успех: `OK: installed_plugins.json (scope=user) already at 1.15.0`, `health-check gate: 0`,
   плюс перезапуск сессии (платформа печатает «Restart to apply changes»).

## Ломающее изменение

Раздел обязателен; `N/A` недопустим (тот же принцип, что уже применён требованием BA-001,
раздел «Ломающее изменение» его исходного файла — здесь называется операционная цена того же
решения, не повторяется его анализ).

**Цена 1 — личный API-ключ больше не назван поддерживаемым режимом, но код пакета продолжает
его читать.**

- *Симптом.* Оператор, у которого в окружении с прежних времён задана
  `KTALK_PERSONAL_API_KEY` (в `.zshrc`/`.zshenv`/`.bash_profile` или экспортирована иначе),
  продолжает авторизовываться по ключу — установленный пакет `ktalk-cli` 2.1.0 отдаёт этой
  переменной приоритет над файлом сессионного токена (`config.py:93-131`, RES-001 §1) и
  продолжит это делать, пока не выйдет версия по заявке
  `https://github.com/mdemyanov/ktalk-cli/issues/10` (открыта на дату этой задачи, вне
  периметра этого эпика — плагин не правит код зависимости, ADR-012). Инструкция плагина
  больше не называет этот путь и не подсказывает его при отказе — расхождение между тем, что
  говорит текст, и тем, что делает установленный код, сознательное и не маскируется.
- *Причина.* Решение владельца сузить поверхность, которую промт-слой предлагает оператору, до
  одного режима (ADR-028 Д1).
- *Что теряет оператор.* Формально — постоянный (не истекающий) путь авторизации: личный ключ
  не имел короткого TTL сессионного токена. Владелец плагина заявил (сессия 2026-09-07), что
  личный ключ на его собственном контуре фактически не работает — это **заявление владельца о
  своём контуре, не измерение координатора по всем контурам-хозяевам**; для оператора, у
  которого ключ действительно валиден и настроен, реальная утраченная возможность —
  документированный, рекомендованный путь без ручного обновления.
- *Что не изменилось.* `compat.json` не двигается (`2.1.0`); ни одна операция, ранее
  требовавшая личного ключа как единственного пути (`list-archive`, отчёт по участникам), не
  была документирована промт-слоем и до этого решения (ADR-028 Д3) — обещание не отзывается,
  потому что не давалось.

**Цена 2 — постоянная работа теперь требует ручного обновления токена сессии по истечении, без
проактивного сигнала.**

- *Симптом.* Оператор, который раньше не думал о протухании (личный ключ не истекал), теперь
  обязан заметить отказ и вручную повторить два шага (скопировать значение из DevTools,
  `ktalk token set -`).
- *Причина.* У сессионного токена в коде пакета нет ни поля, ни константы срока жизни (RES-001
  §4) — единственный сигнал реактивный: первый провалившийся сетевой вызов возвращает `401`.
  Плагин не может предупредить заранее о том, чего не знает установленный код.
- *Что не изменилось.* Команда исправления — та же, что при первой настройке (`ktalk token set
  -`), не новая. README называет её дважды: как первый шаг настройки (раздел «Положите токен»)
  и как реакцию на отказ (та же секция, «Токен браузерной сессии живёт недолго…»).

## Шаг для потребителя

После обновления плагина до 1.15.0 (`claude plugin update ktalk@ktalk-plugins` + перезапуск
сессии) оператору, у которого личный ключ мог остаться в окружении с прежних времён, сделать
у себя три вещи.

1. **Снять переменную личного ключа** — на текущий шелл и на будущее (файл профиля, если
   переменная там персистентна):
   ```bash
   unset KTALK_PERSONAL_API_KEY
   grep -l "KTALK_PERSONAL_API_KEY" ~/.zshrc ~/.zshenv ~/.bashrc ~/.bash_profile ~/.profile 2>/dev/null
   ```
   Живая проверка этой задачей (2026-09-08, эта машина) — `grep -l` действительно нашёл
   совпадение в `~/.zshenv` (путь файла, не значение переменной — команда `-l` печатает только
   имя файла, не строку и не содержимое), подтверждая, что сценарий этого раздела реален, не
   гипотетичен. Если `grep -l` что-то печатает — удалить строку, называющую переменную, из
   найденного файла (`sed -i '' '/KTALK_PERSONAL_API_KEY/d' <файл>` на macOS; на Linux — тот же
   `sed` без пустого аргумента после `-i`), затем открыть новый шелл и проверить:
   ```bash
   env | grep -c KTALK_PERSONAL_API_KEY
   ```
   Ожидание — `0`.
2. **Проверить файл токена сессии:**
   ```bash
   ktalk token status
   ```
   Живая проверка этой задачей (2026-09-08, эта машина, установленная `ktalk-cli 2.1.0`):
   ```
   Файл: ~/.config/ktalk-mcp/token
   present: True, права 0600
   usable: True, ****************XXXX (N символов)
   ```
   Значение замаскировано командой — вывод не содержит токена целиком. Если `present: False`
   или `usable: False` — перейти к шагу 3 README («Положите токен»).
3. **Проверить живость авторизации реальным запросом:**
   ```bash
   ktalk auth-status
   ```
   Команда существует и задокументирована (`ktalk auth-status --help`, живая проверка этой
   задачей: `usage: ktalk auth-status [-h] [--json]`) — не выполнена этой задачей вживую с
   реальным сетевым запросом к боевому контуру Толка без отдельной санкции оператора на этот
   вызов (красная линия проекта — запись/обращение к контуру только по санкции; чтение статуса
   не запись, но эта задача не располагает подтверждённой санкцией на сетевой вызов от имени
   конкретного оператора). Ожидание при живой авторизации — код `0` и текст, подтверждающий
   активную сессию, без печати значения токена (`references/onboarding.md:149` — тот же
   принцип для `--json`-формы). Отказ `401`/сообщение о протухшей авторизации — вернуться к
   шагу 1 README («Положите токен»): `ktalk token set -` тем же способом, каким токен клался
   в первый раз. Команда `ktalk session` **не существует** — не пытаться её вызывать (issue
   `#8`-класс, находка №2 BA-001: несуществующая команда, названная старым текстом).

## Rollback

**Откатывается:** тег и релизный merge-коммит в `main` — тот же приём, что
`2026-09-03-release-delivery-tails-release-runbook.md` уже документирует, применённый к этому
релизу без изменений:

```bash
SHA=<sha релизного merge-коммита в main>
PARENTS="$(git log -1 --format='%P' "$SHA" | wc -w | tr -d ' ')"
if [ "$PARENTS" -gt 1 ]; then
  git revert --no-edit -m 1 "$SHA"
else
  git revert --no-edit "$SHA"
fi
```

Тег GitHub-зеркала **не откатывается** — тот же принцип ADR-025 Д1/ADR-027, что соседний
runbook уже применяет: не удалять и не форсированно перемещать уже опубликованный тег;
дефектный релиз закрывается следующим тегом с починкой, не переписыванием истории.

**Что происходит с документацией и сторожем при откате.** Ревёрт релизного merge-коммита
откатывает одним движением три взаимосвязанные части этого же эпика — не только текст:

1. **README/`references/onboarding.md`** возвращаются к редакции с двумя режимами и с
   рекомендацией личного ключа «для постоянной работы» — literal `KTALK_PERSONAL_API_KEY`
   снова появляется в этих файлах.
2. **Сторож `check_no_retired_auth_literal`** (`scripts/check-plugin-composition.sh`, введён
   этим же эпиком, DEV-002) откатывается вместе с текстом — после ревёрта его в дереве нет,
   поэтому возврат литерала в README/`onboarding.md` не ловится им заново и не красит гейт: до
   этого эпика литерал был штатным содержимым тех же файлов, сторож на него не претендовал.
   Проверка после отката:
   ```bash
   grep -n "check_no_retired_auth_literal" scripts/check-plugin-composition.sh
   ```
   Ожидание — пусто (функция отсутствует), а не «есть, но красная» — иначе `check.sh --full`
   после отката будет ложно падать на файлах, которые откат сам же вернул к старой редакции.
3. **`scripts/test-session-only-auth.sh` и его регистрация в `.nauta-gates.yaml`**
   (`projectGates.full`) откатываются тем же ревёртом — сьюта, проверяющая 11 Requirement
   capability `session-only-auth`, перестаёт исполняться `check.sh --full`, потому что предмет
   проверки (единственный режим) сам откатился к состоянию до эпика.
4. **`compat.json` не меняется откатом** — не был в диффе релиза, реверту нечего в нём
   возвращать.

Проверка успешного отката — гейт зелёный на откатанном дереве:
```bash
bash scripts/check.sh --full
```
Ожидание — `✓ check.sh --full — passed`, без упоминания `test-session-only-auth.sh` в списке
исполненных гейтов (тот же принцип «зелёный гейт ≠ проверена вся поверхность», что security
audit уже называет Находкой 2 для прямого направления, здесь — симметричное следствие для
обратного).

## Monitoring

Тот же принцип, что у обоих соседних runbook'ов — нет сетевых сервисов и очередей этого
плагина; новых сигналов алертинга этот релиз не заводит.

- **Метрика: код возврата пред-релизного гейта (`check.sh --full`).** Норма — `0`. Ненулевой —
  стоп-условие публикации, не алерт дежурному.
- **Метрика: `check_no_retired_auth_literal` в составе `projectGates.fast`.** Норма — молчит
  (не находит литерал в периметре README/`references`/`skills`/`agents`/`commands`). Найденный
  литерал после этого релиза — регресс текста инструкции, разбирать как дефект, не как штатное
  исключение.
- **Метрика: `test-session-only-auth.sh` в составе `projectGates.full`.** Норма —
  `PASS=37 FAIL=0 SKIP=1` (`SKIP` — легитимный AC11-2, не считать регрессом сам по себе).
  Появление новых `FAIL` — регресс поверхности авторизации, разбирать до следующего релиза.
- **Метрика: health-check gate (шаг 5).** Норма — `0` после документированного пути
  обновления. Ненулевой сразу после публикации — путь обновления снова неполон, эскалация ниже.
- **Дашборд.** Источники истины — тег `ktalk--v1.15.0` в репозитории плагина, `.nauta-gates.yaml`
  (состав `projectGates`) и issue-трекер `tools-ai/ktalk-plugin` (закрытие `#8`); отдельного
  мониторингового сервиса нет.

## Escalation

- **Кто дежурит.** Роль `/nauta:devops` эпика — без отдельного круглосуточного дежурства, тот
  же принцип, что у соседних runbook'ов.
- **Когда эскалировать.** Пред-релизный гейт падает не на `test-session-only-auth.sh` и не на
  ранее известных позициях (`check-hooks-path.sh` в изолированной рабочей копии) — расследовать
  саму позицию. Health-check (шаг 5) возвращает `BLOCK` после обеих команд README и перезапуска
  сессии — эскалация на владельца платформенной команды `claude plugin update`, документированный
  путь здесь полон. `glab issue close 8` падает авторизацией — переавторизоваться
  (`glab auth login`), не закрывать issue вручную через веб-интерфейс без записи команды.
  Массовый поток жалоб на протухшую авторизацию сразу после релиза, не объяснимый обычной
  частотой протухания сессии, — это не операционный инцидент этого runbook'а: RES-001 §4 уже
  зафиксировала, что частота протухания не измерена и не нормируется, у DevOps нет базовой
  линии, с которой сравнивать «сразу после» с «как обычно» — эскалация SA/BA для замера, не
  тушится этим runbook'ом как регрессия конкретного релиза.
- **Секьюрити-инцидент.** Утечка значения токена (не файла, не имени переменной) через любой
  канал этого релиза — DevOps ведёт оперативный тайм-лайн (когда замечено, какой канал, что
  сделано), корневую причину и пост-мортем — DevSecOps (вне мандата этого runbook'а).

## Known problems

- **`claude plugin tag --dry-run` печатает `Tag "ktalk--v1.15.0" already exists locally`** →
  тег уже создан этим же раундом, либо версия не поднята повторно после отката → проверить
  `git tag -l "ktalk--v*" | sort -V | tail -1`; не использовать `--force` для перемещения
  существующего тега (ADR-025 Д1).
- **`ktalk auth-status` возвращает `401`/сообщение об истёкшей авторизации сразу после
  `ktalk token set -`** → значение из буфера обмена скопировано не полностью, либо `.zshenv`/
  переменная окружения того же процесса переопределяет файл значением из другого источника
  (порядок приоритета RES-001 §1: `KTALK_PERSONAL_API_KEY` → `KTALK_SESSION_TOKEN` → файл) →
  проверить `env | grep -c KTALK_PERSONAL_API_KEY` и `env | grep -c KTALK_SESSION_TOKEN` в том
  же шелле, где вызывается `ktalk` — непустой результат одной из них объясняет, почему файл
  токена молча не используется.
- **`glab issue close 8` формально закрыт, но оператор всё ещё видит старое описание
  `dashboard --json` в развёрнутом у себя плагине** → тот же класс, что известная проблема
  `2026-09-03-release-delivery-tails-release-runbook.md` для `#6`: закрытие issue не равно
  обновлению установленной у оператора копии плагина → повторить шаг 5 (health check) на
  машине оператора, не считать закрытие issue доказательством обновления.
- **После отката `check.sh --full` красный на позиции, не связанной с `test-session-only-auth.sh`
  или `check_no_retired_auth_literal`** → ревёрт затронул файл, изменённый параллельно другой
  задачей после релиза 1.15.0 (конфликт слияния истории, не дефект этого runbook'а) →
  разрешать конфликт вручную по обычной процедуре `git revert`, не форсировать откат поверх
  неразрешённого конфликта.
