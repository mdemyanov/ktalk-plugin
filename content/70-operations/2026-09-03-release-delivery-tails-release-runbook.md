# Runbook: релиз 1.10.0 — тег платформы, гейт GO-критериев, границы оркестратора

**Capability:** `openspec/specs/release-delivery-tails/spec.md`
**ADR:** `content/00-project/adr/ADR-025-release-delivery-surface.md`,
`content/00-project/adr/ADR-026-orchestrator-processor-boundary.md`
**Architecture:** `content/40-architecture/2026-09-03-release-delivery-tails.md`,
`content/40-architecture/2026-09-03-orchestrator-processor-boundary.md`
**Соседние рансбуки:** `content/70-operations/2026-08-31-cli-only-boundary-release-runbook.md`,
`content/70-operations/2026-08-31-package-rename-transition-release-runbook.md` — оба описывают
**уже состоявшиеся** релизы (0.11.0/1.7.0 и 1.0.0/0.11.0/1.8.0). Ни один не переписан этим
раундом: их форензика (реальные sha ревертов, реальные прогоны AC-9/`pypi_gate`, разделы
«Ломающее изменение» тех релизов) остаётся точным отчётом о них. Этот файл — для **следующего**,
структурно другого релиза, меняющего саму процедуру: форму тега (`claude plugin tag`, не
`git tag`), пред-релизный гейт (`check.sh --full` теперь сам исполняет GO-критерии `CLAUDE.md`,
не только `check-plugin-composition.sh` вручную) и границу оркестратора/обработчика
(`project-curator` больше не вызывается напрямую). Он ссылается на приёмы соседних документов
вместо того, чтобы повторять их (структурный JSON-парсер вместо `grep`, `git revert -m 1` на
merge-коммите, PEP 592 для отката пакета — этот релиз пакет не публикует, но откат плагина
использует тот же приём) — тот же довод «новый файл, а не правка существующего», что уже
объяснён в `2026-08-31-package-rename-transition-release-runbook.md`, разделе «Почему новый файл,
а не правка существующего».

## Purpose

Релиз 1.10.0 закрывает восемь свойств волны «хвосты релиза 1.9.0» (BA-001, ADR-025, ADR-026):
форма тега, `description` манифеста маркетплейса, полный документированный путь обновления,
справочники-не-агенты, retired-имя пакета в метаданных, делегирование `project-curator` через
оркестратор, проверка личности транскрипта, автоматическое исполнение GO-критериев `CLAUDE.md`.
Используй этот runbook при публикации 1.10.0 и при откате любой её части.

## Preconditions

- Доступ на push в репозиторий плагина (`ktalk-plugin`) и право создавать теги. Публикации
  пакета в этом релизе нет — `compat.json` называет `ktalk-cli` 1.0.0 и не меняется (см.
  «Пин пакета — сверка, не правка» ниже).
- `claude` CLI в PATH (`claude --version` — проверено вживую этой задачей: `2.1.258 (Claude
  Code)`), `git`, `python3`, `gh`, `glab` — для шага переноса issue.
- Секреты токена оператора контура (`KTALK_SESSION_TOKEN` и т.д.) в релизном окружении не
  нужны — тот же принцип `run_clean`/NFR-19, что в обоих соседних runbook'ах.
- Рабочее дерево чистое (`git status --short` — пусто) на коммите, который становится релизом.

## Steps

Порядок: пред-релизный гейт → тег платформы → фиксация ломающего изменения в коммите → судьба
issue → health check доставки (AC-3e). Тег создаётся только после того, как гейт вернул `0` —
тот же принцип «гейт останавливает пайплайн», что уже действует в обоих соседних runbook'ах
(AC-9/`pypi_gate`), применённый здесь не к индексу пакета, а к составу и языку промт-слоя.

1. **Пред-релизный гейт — GO-критерий CLAUDE.md, теперь исполняемый одной командой** (ADR-025
   Д7). `check.sh --full` подключает `projectGates` — 12 позиций, включая
   `check-plugin-composition.sh`/`check-prompt-language.sh` (в `fast:`) и
   `test-onboard.sh`/`test-release-delivery-tails.sh` (в `full:`, дороже на два порядка):
   ```bash
   bash scripts/check.sh --full
   ```
   Успех: печатает `✓ check.sh --full — passed`, код возврата `0`. Ненулевой код — тег не
   создаётся, дальше по шагам не идти.

   **Живая проверка (2026-09-03, эта задача, ветка `ops-001`, HEAD `3fa5c30`):** первый прогон
   в этой рабочей копии-worktree дал `✗ check.sh --full — FAILED` на позиции
   `check-hooks-path.sh` — `core.hooksPath` общего конфига указывал на каталог хуков ГЛАВНОГО
   рабочего дерева репозитория (абсолютный путь домашнего каталога машины релиз-инженера), а
   не этой изолированной копии;
   документированный, признанный (ADR-081 Д7/SA-097 §3.7) симптом абсолютной формы ключа —
   гейт сам печатает ремонт: `bash scripts/install-hooks.sh`. Прогнал ремонт (переустанавливает
   `core.hooksPath` в ОТНОСИТЕЛЬНОЙ форме — резолвится по-своему в каждой рабочей копии, не
   трогает содержимое `scripts/`), повторный прогон:
   ```
   ✓ check.sh --full — passed
   bash scripts/check.sh --full  14.66s user 12.81s system 33% cpu 1:20.81 total
   ```
   12 гейтов (`▶`-строк) в выводе, `RC=0`, 1:20.81 реального времени — в пределах диапазона,
   который QA-002 (`content/60-implementation/test-reports/004-2026-09-03.md`) измерил дважды
   (1:45.12/1:49). Если `check-hooks-path.sh` падает на другой изолированной копии — тот же
   ремонт, не расследование заново: причина одна и та же (общий `core.hooksPath`, разный
   `$TOPLEVEL`).

2. **Тег релиза — `claude plugin tag`, не `git tag`** (ADR-025 Д1). Команда формирует строку
   `<plugin>--v<version>`, которую платформа резолвит при разрешении версионных зависимостей
   других плагинов против этого, и попутно валидирует согласие `plugin.json` с записью
   маркетплейса (`--help`: «validating that plugin.json and any enclosing marketplace entry
   agree») — это свойство самой команды, не отдельная проверка, которую нужно вызывать до неё.
   Сухой прогон перед реальным:
   ```bash
   claude plugin tag --dry-run
   ```
   Успех: печатает `Tag: <plugin>--v<version>` для сегодняшнего `plugin.json`.

   **Живая проверка (2026-09-03, эта задача, дерево этой worktree):**
   ```
   Plugin:  ktalk
   Version: 1.10.0 (from plugin.json)
   Marketplace entry: plugins[0] in .../ktalk-plugin/.claude-plugin/marketplace.json
   Tag:     ktalk--v1.10.0
   ✔ Dry run — would create tag ktalk--v1.10.0 at HEAD in ...
     git ... tag -a ktalk--v1.10.0 -m "ktalk 1.10.0"
     git ... push origin refs/tags/ktalk--v1.10.0
   ```
   Форма подтверждена: `ktalk--v1.10.0`, не `v1.10.0`. Реальное создание (после пред-релизного
   гейта, шаг 1, и слияния релизного коммита в `main` — не раньше):
   ```bash
   claude plugin tag --push --remote origin
   ```
   Успех: `git ls-remote --tags origin | grep ktalk--v1.10.0` находит тег на удалённой стороне.

   **Риск, названный явно (ADR-025 Д1).** Шесть уже опубликованных тегов (`v1.3.0`…`v1.9.0`,
   старая форма) **не переписываются и не удаляются** этим или любым следующим релизом —
   форсированное перемещение тега, уже разрешённого чьим-то клоном, молча подменяет то, что
   резолвится по этому имени. Следствие: до появления первого потребителя, реально резолвящего
   версионное ограничение против `ktalk`, у репозитория сосуществуют две формы тега (`vX.Y.Z`
   для шести старых релизов, `ktalk--vX.Y.Z` начиная с 1.10.0) — это принятая, не временная
   цена (ADR-025 Д1, «Отклонено: переименовать шесть существующих тегов»), не дефект этого
   runbook'а. Не заводить задачу «привести теги к одной форме» без нового решения SA.

3. **Коммит релиза несёт `BREAKING CHANGE:` — третье подряд ломающее изменение этого плагина.**
   Тот же механизм, что уже применён дважды (соседние runbook'и, коммиты `69ef207` и переход
   `ktalk-mcp`→`ktalk-cli`): коммит несёт `!` в типе Conventional Commits и футер
   `BREAKING CHANGE:` с точным списком того, что меняется в наблюдаемом поведении. Полный
   разбор — раздел «Ломающее изменение» ниже; здесь — форма объявления:
   ```bash
   git log -1 --format=%B <SHA-релизного-коммита> | grep -c '^BREAKING CHANGE:'
   ```
   Успех: `1` — футер присутствует ровно один раз, не ноль.

4. **Судьба открытых issue** — три открытых в `tools-ai/ktalk-plugin`, три разных исхода.
   Полная процедура — раздел «Судьба открытых issue» ниже; здесь — сводка команд:
   ```bash
   glab issue close 6 --repo tools-ai/ktalk-plugin
   gh issue create --repo mdemyanov/ktalk-cli --title "<см. раздел ниже>" --body "<см. раздел ниже>"
   glab issue close 5 --repo tools-ai/ktalk-plugin
   gh issue create --repo mdemyanov/ktalk-cli --title "<см. раздел ниже>" --body "<см. раздел ниже>"
   glab issue close 7 --repo tools-ai/ktalk-plugin
   ```
   Не выполнять раньше, чем шаг 2 (тег) создан — иначе комментарий с ссылкой на коммит/тег
   ссылался бы на объект, которого ещё нет.

5. **Health check после публикации — AC-3e, носитель этого runbook'а.** Тест-репорт QA-002
   (`content/60-implementation/test-reports/004-2026-09-03.md`, «Покрытие сценариев») пометил
   поведенческую часть AC-3e именованным `SKIP` с носителем «шаг будущего релизного рансбука
   DevOps» — это он. Проверяется структурным JSON-парсером (не `grep` по чужому форматированию,
   тот же приём, что AC-9/`pypi_gate` соседних runbook'ов), что `installed_plugins.json`
   потребителя реально перешёл на новую версию после документированного пути обновления
   (`README.md`, «Быстрый старт», обе команды):
   ```bash
   check_installed_version() { # check_installed_version <ожидаемая-версия> — 0 = user-scope
                                # запись уже на ожидаемой версии, 1 = ещё нет
     local WANT="$1" PATH_JSON="$HOME/.claude/plugins/installed_plugins.json"
     python3 - "$WANT" "$PATH_JSON" <<'PY'
import json, sys
want, path = sys.argv[1], sys.argv[2]
with open(path) as f:
    data = json.load(f)
entries = data.get("plugins", {}).get("ktalk@ktalk-plugins", [])
user_entries = [e for e in entries if e.get("scope") == "user"]
if not user_entries:
    print("BLOCK: no user-scope installed_plugins.json entry for ktalk@ktalk-plugins")
    sys.exit(1)
got = user_entries[0].get("version")
if got == want:
    print(f"OK: installed_plugins.json (scope=user) already at {got}")
    sys.exit(0)
print(f"BLOCK: installed_plugins.json (scope=user) still at {got}, expected {want}")
sys.exit(1)
PY
   }
   claude plugin marketplace update ktalk-plugins
   claude plugin update ktalk@ktalk-plugins
   check_installed_version 1.10.0; echo "AC-3e gate: $?"
   ```
   Успех: `OK: installed_plugins.json (scope=user) already at 1.10.0`, `AC-3e gate: 0`, плюс
   перезапуск сессии (платформа печатает «Restart to apply changes» после `plugin update`).

   **Живая проверка (2026-09-03, эта машина, реальный `$HOME/.claude/plugins/installed_plugins.json`
   — публикация 1.10.0 ещё не состоялась, обе ветки исхода показаны на РЕАЛЬНЫХ данных):**
   ```
   $ python3 ... check_installed_version.py 1.10.0 $HOME/.../installed_plugins.json
   BLOCK: installed_plugins.json (scope=user) still at 1.9.0, expected 1.10.0
   AC-3e gate: 1
   $ python3 ... check_installed_version.py 1.9.0 $HOME/.../installed_plugins.json
   OK: installed_plugins.json (scope=user) already at 1.9.0
   AC-3e gate: 0
   ```
   Сегодняшняя реальная запись — `scope=user`, `version=1.9.0`, `lastUpdated:
   2026-09-02T21:10:11.591Z` (владелец плагина сам не на последней версии на момент подготовки
   этого runbook'а — тот же факт, который BA-001 уже назвал живым прогоном). `BLOCK`-ветка
   доказана на реальном несовпадении версий, `OK`-ветка — на реальном совпадении; обе — без
   синтетической фикстуры. После настоящей публикации и настоящего `plugin update` тот же
   вызов с `WANT=1.10.0` обязан вернуть `OK` — если возвращает `BLOCK`, путь обновления снова
   неполон, эскалация — «Escalation» ниже.

## Пин пакета — сверка, не правка

`compat.json` называет `ktalk-cli` 1.0.0 и не меняется этим релизом — сам пакет не публикуется.
Урок 2026-08-31 (DevOps): пин живёт в двух файлах (`compat.json` для машины, `README.md` для
человека) — при каждой правке пина искать оба грепом, даже когда правки пина в этом раунде нет,
потому что молчаливое расхождение возникает и без прямого редактирования (правка README другим
коммитом волны рядом). Проверка перед тегированием:
```bash
python3 -c "import json; d=json.load(open('compat.json')); print(d)"
grep -n 'ktalk-cli==1.0.0\|ktalk-cli 1.0.0' README.md
```
**Живая проверка (2026-09-03, дерево этой worktree):**
```
$ python3 -c "import json; d=json.load(open('compat.json')); print(d)"
{'package_name': 'ktalk-cli', 'package_version': '1.0.0'}
$ grep -n 'ktalk-cli==1.0.0\|ktalk-cli 1.0.0' README.md
15:uv tool install ktalk-cli==1.0.0
16:ktalk --version       # ровно ktalk-cli 1.0.0 — шаг 3 опирается на `ktalk token`
```
Оба файла согласны сегодня. Если грепы разойдутся — не тегировать, эскалация не нужна, чинится
на месте (правка README/`compat.json`, вне мандата этой роли — Dev).

## Ломающее изменение: третье подряд, оба конца измерены

Третье подряд ломающее изменение этого плагина (первые два — снятие MCP-поверхности и переход
`ktalk-mcp`→`ktalk-cli`, описаны соседними runbook'ами). Здесь их два, разной природы:

**Три имени пропадают из списка агентов сессии (ADR-025 Д5).**
`agents/references/two-pass-analysis.md`, `protocol-template.md`, `vault-update-and-report.md`
переехали в `references/ktalk-processor/` — вне каталога, который платформа сканирует как
источник агентов. Живая проверка этой задачей (2026-09-03, `claude plugin tag --dry-run
--force`, `--force` обходит только незакоммиченный `.nauta-authority-observations.jsonl`, не
логику тега): предупреждений «No frontmatter block found» по трём файлам-справочникам больше
нет, `agents/` содержит ровно два файла (`ktalk-evaluator.md`, `ktalk-processor.md`). Оператор,
листавший список агентов сессии до этого релиза, видел пять имён; после — два. Это не потеря
функциональности (три файла никогда не были самостоятельными ролями — платформа регистрировала
их по расположению, не по содержимому), но наблюдаемая перемена состава списка, которую стоит
объявить, если кто-то полагался на подсчёт имён как на признак версии.

**`ktalk-processor` больше не вызывает `project-curator` напрямую (ADR-026 Д1).**
`project-curator` — внешний агент, не часть этого плагина, устанавливаемый отдельно на стороне
хозяина проекта. До этого релиза (по намерению промта, невыполнимо технически — `tools:`
`ktalk-processor` никогда не нёс инструмента вызова субагентов) шаг «Final step» предписывал
вызов `project-curator` напрямую; 02.09.2026 все четыре параллельных прогона доложили о
невыполнимости и вместо него правили карточки проектов напрямую, в обход куратора. С этого
релиза `ktalk-processor` только отчитывается строкой `Проекты затронуты: {ids}` (`agents/
ktalk-processor.md`, «Final step — reporting affected projects»), а вызывает `project-curator`
оркестратор `ktalk-registry`, ровно один раз на прогон, после завершения всех обработчиков
(`skills/ktalk-registry/SKILL.md`, шаг 5.5). **Для хозяина, где `project-curator` установлен**,
это меняет наблюдаемое поведение: карточки проектов теперь обновляются одним централизованным
вызовом после прогона, а не (несостоявшимися) параллельными попытками во время него — временная
точка обновления сдвигается на момент завершения последнего агента прогона, не на момент
завершения каждого агента отдельно.

**Для хозяина без `project-curator`** разница другого рода, не отсутствие разницы. Строка лога
встречи в карточке проекта — `Automatic`-шаг самого `ktalk-processor`, не вызов куратора
(`references/ktalk-processor/vault-update-and-report.md:23-25`, «Add the meeting to the project
card's log»), и этот релиз её не трогает ни для одного хозяина: карточка по-прежнему получает
строку лога независимо от того, установлен ли `project-curator`. Что прекращается — правка
карточек сверх этой строки: 02.09.2026 все четыре прогона доложили о невыполнимости вызова
куратора и вместо него правили карточки проектов напрямую, сверх лога, в обход куратора; с
этого релиза «Final step» обработчика ограничен строкой отчёта `Проекты затронуты: {ids}`, и
никакой другой правки карточек сверх лога он больше не делает. Кросс-проверка консистентности
куратором для такого хозяина как не происходила до этого релиза (вызов был структурно
невыполним — `tools:` обработчика никогда не нёс инструмента вызова субагентов), так не
появляется и теперь; ADR-026, «Consequences», Negative, называет это прямо вне области решения.
Меняется форма пропуска, не его наличие: раньше он тонул в импровизации отдельных агентов,
теперь оркестратор ловит нерезолвящийся вызов централизованно, ровно один раз на прогон, и
явно называет его в сводке — шаг 5.5 ловит нерезолвящийся вызов и помечает пропуск в сводке
прогона (`project-curator не установлен — обновление карточек пропущено`), не падает.

**Как объявляется.** Тот же механизм, что в обоих предыдущих ломающих изменениях — Conventional
Commits, `!` в типе релизного коммита, футер `BREAKING CHANGE:` с обоими пунктами выше
буквально (см. шаг 3 «Steps»).

**Регресс, который ловит гейт.** Три файла-справочника снова в `agents/` без переезда —
`claude plugin tag --dry-run` даёт предупреждение о фронтматтере по каждому (не отказ
зарегистрировать — тот же симптом, что нашла ADR-025 Context, воспроизводится ровно так же).
Прямой вызов `project-curator` внутри `agents/ktalk-processor.md` — `grep -n
"project-curator" agents/ktalk-processor.md`; ожидаемый ноль совпадений (сегодня файл говорит

## Rollback

### Откат тега

Тег `ktalk--v1.10.0` не форсируется и не удаляется без крайней необходимости — тот же принцип,
что ADR-025 Д1 уже применяет к шести старым тегам: форсированное перемещение подменяет то, что
чей-то клон уже мог разрешить. Если дефект найден до того, как кто-либо внешний мог
резолвить тег (в пределах этого же релизного окна, без внешних потребителей версионных
ограничений сегодня):
```bash
git push origin :refs/tags/ktalk--v1.10.0 && git tag -d ktalk--v1.10.0
```
Проверка: `git ls-remote --tags origin | grep ktalk--v1.10.0` — пусто.

### Откат релизного коммита

`main` этого репозитория интегрируется merge-коммитами (`git log --oneline --merges main`,
проверено на актуальной истории — восемь merge-коммитов, включая `617e0a7`, самый свежий).
Голый `git revert --no-edit <sha>` на merge-коммите отказывает («commit is a merge but no -m
option was given») — тот же дефект, что урок 2026-08-31 уже поймал на более ранней истории
этой же ветки; число родителей отличает случаи и решает, нужен ли `-m 1`:
```bash
SHA=<merge-or-release-commit-sha>
PARENTS="$(git log -1 --format='%P' "$SHA" | wc -w | tr -d ' ')"
if [ "$PARENTS" -gt 1 ]; then
  echo "merge-коммит ($PARENTS родителя) — revert -m 1"
  git revert --no-edit -m 1 "$SHA"
else
  echo "обычный коммит ($PARENTS родитель) — revert без -m"
  git revert --no-edit "$SHA"
fi
```
Успех: вывод называет тип коммита, `git revert` завершается новым коммитом (`git log --oneline
-1` показывает `Revert "..."`).

**Живая проверка (2026-09-03, эта задача, disposable-клон этого репозитория в scratch-каталоге
— не рабочее дерево, `git merge` этой ролью не выполнялся и не понадобился, коммит уже в
реальной истории `main`):**
- `git log -1 --format='%P' 617e0a7` (самый свежий merge-коммит `main` на сегодня, «Merge
  branch 'epic-ktalk-cli' into main») → два родителя (`4861fb9`, `35b3f06`) → `PARENTS=2`.
- `git revert --no-edit -m 1 617e0a7` в disposable-клоне: не отказал синтаксически, начал
  реверт (три реальных конфликта содержимого — `plugin.json`, `content/lessons-learned.md`,
  `scripts/test-onboard.sh` — ожидаемо для коммита, который сам был крупным переименованием;
  конфликт разрешается вручную при реальном инциденте, здесь важна только форма команды).
  `git revert --abort` вернул клон в чистое состояние (`git status --short` — пусто).
- Тот же коммит голым `git revert --no-edit 617e0a7` (без `-m`, старая форма) —
  `error: commit ... is a merge but no -m option was given.`, `fatal: revert failed`, exit
  `128` — подтверждает дефект на актуальной, не архивной истории (соседний runbook доказал то
  же на sha `c70bc14`/`7fbdc0d` из более ранней истории; здесь — тот же приём на текущем HEAD
  `main`).

### Откат ломающего изменения ADR-026

Механических откатных шагов сверх «Откат релизного коммита» нет — `project-curator` не
поставляется этим деревом, и откат релиза плагина автоматически возвращает `agents/
ktalk-processor.md`/`skills/ktalk-registry/SKILL.md` к состоянию до Д1. Если откат нежелателен
целиком (например, только регресс справочников-агентов найден, граница оркестратора работает
верно) — точечный ревёрт только коммита(ов) переезда `agents/references/*.md`, тем же приёмом
(проверить число родителей каждого перед `revert`), не всего релизного merge.

## Monitoring

Тот же принцип, что у обоих соседних runbook'ов — нет сетевых сервисов и очередей этого
плагина, метрики «латентность»/«RPS» неприменимы. Новые сигналы этого релиза:

- **Метрика: код возврата пред-релизного гейта (`check.sh --full`, шаг 1).** Норма — `0`.
  Ненулевой — стоп-условие пайплайна, не алерт дежурному.
- **Метрика: `projectGates: configured (N позиций)` в выводе `check.sh` (Brief for DevOps,
  ADR-025 companion).** Норма — совпадение `N` с числом объявленных путей в `.nauta-gates.yaml`
  (`fast:` — 2, `full:` — 2 дополнительных, итого 4 позиции `projectGates` суммарно, отдельно
  от базисных гейтов `nauta`). Расхождение — гейт объявлен декоративно, не исполняется:
  дефект уровня Д7, не повод править число вручную без расследования.
  Живая проверка (2026-09-03, `check.sh --fast`): `projectGates: configured (2 позиций)`.
- **Метрика: AC-3e gate (шаг 5, health check).** Норма — `0` после документированного пути
  обновления. Ненулевой сразу после публикации — путь обновления снова неполон (регресс
  ровно того класса, который это требование закрывает) — эскалация ниже, не «подождать и
  повторить».
- **Дашборд.** Источники истины — тег `ktalk--v1.10.0` в репозитории плагина и issue-трекеры
  `tools-ai/ktalk-plugin` (закрытие `#5`/`#6`/`#7`) и `mdemyanov/ktalk-cli` (два новых, для

## Escalation

- **Кто дежурит.** Роль `/nauta:devops` эпика (тот же принцип, что у обоих соседних
  runbook'ов) — без отдельного круглосуточного дежурства.
- **Когда эскалировать.** Шаг 1 (пред-релизный гейт) падает на позиции, не связанной с
  `check-hooks-path.sh` (у которой есть штатный ремонт, см. «Живая проверка» шага 1) —
  расследовать саму позицию, не считать её тем же классом артефакта worktree. Шаг 5 (AC-3e)
  возвращает `BLOCK` после реального прохождения обеих команд README — эскалация на владельца
  платформенной команды `claude plugin update`, не на этот репозиторий: документированный путь
  здесь полон, а несовпадение версии после него — платформенный дефект, не дефект runbook'а.
  Перенос issue `#5`/`#7` (шаг 4) падает на `gh`/`glab` авторизацией — эскалация владельцу
  токена (тот же принцип, что «Санкция публикации» соседнего runbook'а — не решается локально
  агентом без действующей авторизации).

## Known problems

- **`check-hooks-path.sh` красный в изолированной рабочей копии (`.claude/worktrees/<id>`),
  зелёный в главном дереве** → общий `core.hooksPath` в абсолютной форме указывает на каталог
  хуков главного дерева, а не текущей копии (признанное свойство, ADR-081 Д7/SA-097 §3.7,
  живой прецедент — эта же задача) → `bash scripts/install-hooks.sh` (переустанавливает ключ в
  относительной форме, резолвится по-своему в каждой копии) — не расследовать заново, если
  симптом идентичен.
- **`AC-3e gate` возвращает `BLOCK` после того, как обе команды README выполнены и
  `claude plugin update` напечатал «Restart to apply changes»** → сессия не перезапущена
  (изменение вступает в силу только после restart, README называет это явно) → перезапустить
  сессию, повторить `check_installed_version` без повторного `plugin update`.
- **`glab issue close`/`gh issue create` завершаются кодом, отличным от `0`** → протухший
  токен авторизации (`gh auth status`/`glab auth status`) — тот же класс проблемы, что
  «Санкция публикации» соседнего runbook'а называет для публикации пакета → переавторизоваться
  (`gh auth login`/`glab auth login`), не пытаться закрыть issue вручную через веб-интерфейс
  без записи команды, которая сработала бы (иначе следующий релиз-инженер не найдёт
  воспроизводимый путь).
- **Issue `#6` формально закрыт, но `ktalk-processor.md` в развёрнутом у оператора плагине
  всё ещё несёт литерал `project-curator` в шаге вызова, не в отчёте** → оператор не обновил
  плагин (тот же путь, что AC-3e проверяет) → тот же health check шага 5, применённый вручную
  к тексту установленной копии: `grep -n "call.*project-curator\|invoke.*project-curator"
  "$HOME/.claude/plugins/cache/ktalk-plugins/ktalk/<версия>/agents/ktalk-processor.md"` — если
  находит совпадение, копия устарела, не выпуск дефектен.
