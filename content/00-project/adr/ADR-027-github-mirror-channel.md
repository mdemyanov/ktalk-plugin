# ADR-027: Второй канал поставки — публичное GitHub-зеркало payload

**Status:** Proposed
**Date:** 2026-09-04
**Capability:** `openspec/specs/dual-channel-delivery/spec.md`

## Context

BA-001 (`content/30-requirements/2026-09-04-dual-channel-delivery.md`) вводит второй канал
поставки — публичное GitHub-зеркало payload рядом с внутренним GitLab-маркетплейсом — и
оставляет этому решению шесть пунктов формы (Brief for SA): имя маркетплейса второго канала,
механизм одностороннего зеркалирования, место документации, форму проверки внутреннего домена
в гейте состава, форму подтверждения источника истины на GitHub, буквальные команды сверки
паритета. Санкция оператора (входная, не пересматривается) фиксирует состав публичного
репозитория и то, что GitLab остаётся источником истины без обратной автосинхронизации.

Факты, проверенные заново в этой сессии, не унаследованные от BA без перепроверки:
- `python3 -c "import json;print(json.load(open('.claude-plugin/marketplace.json'))['name'])"`
  → `ktalk-plugins`; `plugin.json` `version` → `1.12.0`; `compat.json` →
  `{"package_name": "ktalk-cli", "package_version": "2.0.0"}`.
- `claude plugin tag --dry-run --force` печатает `Tag: ktalk--v1.12.0` — форма `<plugin>--v
  <version>` из ADR-025 Д1 подтверждена на сегодняшнем `plugin.json`, не унаследована текстом.
- `grep -rn "doc-hub\|yandexcloud" --exclude-dir=.git .` (без ограничения `*.md` и без
  исключения `content/`, шире проверки BA) называет ровно четыре места: `README.md:26`,
  `CLAUDE.md:59`, и два места в `content/` (требование BA, companion ADR-025) — последние два
  вне payload по самой санкции оператора, поэтому не предмет починки, только предупреждение о
  ловушке для гейта (см. Д4).
- `find . -iname "*.gitlab-ci*"` и `find . -path "*/.github/*"` — пусто: в дереве сегодня нет
  ни файла CI, ни каталога `.github/`; `ls LICENSE` — файла нет. Три факта — вход для Д2 и Д5,
  не предмет пересмотра.
- `gh repo view mdemyanov/ktalk-cli --json visibility,licenseInfo` → `PUBLIC`/`MIT` (пакет уже
  публичен, прецедент лицензии); `gh repo view mdemyanov/ktalk-plugin` → repository not found
  (имя свободно) — оба прогнаны заново этой сессией.
- `scripts/check-plugin-composition.sh:65` — проверка на первый внутренний домен продукта —
  сканирует **весь** каталог (`.`, минус `.git`/`__pycache__`/`.beads`/`agent-memory`/сам
  скрипт) — включая `content/`. Наивное повторение этого паттерна для второго домена сломало
  бы прогон немедленно: `content/` уже цитирует `doc-hub.gitlab.yandexcloud.net` в прозе
  (BA-001 и companion ADR-025), и это же решение добавляет ещё одно упоминание в свой
  собственный Context. Это и есть ловушка, названная Brief for SA п.4 — разобрана в Д4.

Открытый вопрос ADR-025 («самообнаружение устаревания плагином») BA явно оставил за тем
решением; это решение его не касается ни в одну сторону.

## Decision

### Д1. Имя маркетплейса второго канала — `ktalk-plugins-mirror`, вписывается механикой Д2

Публичный `.claude-plugin/marketplace.json` несёт top-level `name: "ktalk-plugins-mirror"`
вместо внутреннего `"ktalk-plugins"`. Суффикс `-mirror` — не декоративный: он повторяет слово,
которым это же решение и BA называют канал текстом («одностороннее зеркало»), поэтому
потребитель, добавивший оба маркетплейса, по одному имени видит направление отношения
(канонический канал без суффикса, зеркало — с ним), не только сам факт различия.

Правка не хранится вторым, отдельно поддерживаемым файлом. `.claude-plugin/` копируется в
payload один в один (входное свойство санкции), поэтому единственная точка, где строка `name`
может стать другой без второго авторского источника, — механический шаг процесса
зеркалирования (Д2): после сборки payload-дерева тега джоб переписывает ровно одно поле
(`name`) в `.claude-plugin/marketplace.json` этой копии, остальное содержимое файла и всего
`.claude-plugin/` не трогает.

**Отклонено:** вести второй, вручную поддерживаемый файл (`marketplace.public.json`) в дереве
источника, копируемый при зеркалировании вместо основного. Два независимо редактируемых
файла с одним и тем же назначением — тот же класс риска рассинхронизации, который это же
требование называет угрозой для паритета каналов (Д6); отличие поля должно быть автоматическим
следствием одного шага пайплайна, не вторым местом, которое кто-то забудет обновить.

### Д2. Одностороннее зеркалирование — GitLab CI-джоб по тегу, без нового входящего доступа

Новый файл `.gitlab-ci.yml` (корень репозитория; вне allowlist Д4, публикации не подлежит)
заводит джоб `mirror-github` с условием запуска по тегу формы `ktalk--v*` (форма ADR-025 Д1,
подтверждена заново в Context) на существующем shared-раннере проекта. Джоб: (1) собирает
payload-дерево тега по манифесту Д4; (2) переписывает `name` в скопированном
`marketplace.json` (Д1); (3) пушит это дерево и тот же тег на `github.com/mdemyanov/
ktalk-plugin` по HTTPS токеном, выданным GitHub-репозиторию (protected/masked переменная
CI/CD, доступна только защищённым тегам). При сбое push'а джоб завершается ненулевым кодом,
GitLab-пайплайн показывает красный статус штатным способом (новый канал алертинга не
заводится); релиз на GitLab не откатывается — состояние источника истины push не меняет.
Повторный запуск — вручную (`Retry` в пайплайне), не автоматическим циклом: молчаливый
автоповтор в обратную сторону противоречил бы тому же принципу «без скрытой логики
синхронизации», которым обосновано отсутствие автослияния на стороне issue/PR (Д5).
Тег на GitHub появляется только при успешном push — отсюда и структурное свойство, которое
удовлетворяет Scenario «версия выпущена, но ещё не зазеркалирована» (Д6-таблица ниже): список
тегов на зеркале в любой момент — это ровно то, что реально пушнули, никогда не больше.

**Отклонено:** пул-модель — воркфлоу GitHub Actions, опрашивающий внутренний GitLab. Требует
обратного, входящего доступа к внутреннему GitLab с публичной стороны (учётные данные текут
внутрь, а не наружу) — больше поверхность экспозиции, чем исходящий push с узко
заскоупленным токеном, и именно тот канал, которым санкция оператора (п.3, «обратной
автосинхронизации нет») явно не хочет наделять GitHub.

### Д3. Документация каналов — один README, разный литерал по каналу

`README.md` остаётся одним файлом (он и так копируется в оба канала payload-ом — заводить
второй файл означало бы тот же риск двух источников одного факта, что и в Д1). Раздел
«2. Поставьте плагин» получает два подраздела вместо одного: «Внутренний GitLab (источник
истины)» и «Публичное GitHub-зеркало» — с отдельной командой `/plugin marketplace add` и
именем маркетплейса на каждый (`ktalk-plugins` / `ktalk-plugins-mirror`, Д1). Внутренний
подраздел не несёт литерал домена — вместо него плейсхолдер («внутренний GitLab-адрес — см.
`CLAUDE.md`, «Справочные пути»»), тем же приёмом, что уже несёт пример `.ktalk.toml`
(«пути в примере — плейсхолдеры»); публичный подраздел несёт реальный литерал
`github.com/mdemyanov/ktalk-plugin` — этот адрес не внутренняя инфраструктура, скрывать нечего.

Так один и тот же файл безопасен для публикации байт-в-байт без трансформации содержимого при
зеркалировании — расхождение канала живёт в тексте, не в двух файлах и не в шаге пайплайна.

**Отклонено:** два файла (`README.md` публичный + внутренний с реальным адресом). Отклонено
по тому же основанию, что второй `marketplace.json` в Д1 — два места одного факта, которые
может развести обычная правка одного без другого; отклонено также переписывание README во
время зеркалирования (шаблонная подстановка домена) — лишний шаг пайплайна ради того, что
плейсхолдер в источнике решает без выполнения кода вообще.

### Д4. Проверка внутреннего домена — новый scoped-check по манифесту payload, не по строке 65

`scripts/check-plugin-composition.sh` получает вторую, **ограниченную по области** проверку
для домена `doc-hub.gitlab.yandexcloud.net` — не копию строки 65 (та сканирует всё дерево и
немедленно поймала бы прозу этого же ADR и требования BA, Context выше). Новая проверка
грепает не `.`, а фиксированный список путей — payload-манифест: `.claude-plugin/`, `agents/`,
`commands/`, `skills/`, `references/`, `scripts/`, `README.md`, `LICENSE`, `.github/` (новый
каталог, см. Д5) — тот же набор, что операторская санкция называет составом публичного
репозитория, плюс `.github/`, добавленный этим решением явно (санкция п.1 перечисляет
allowlist по состоянию до появления Д5; расширение — не пересмотр перечня, а его продолжение
тем же принципом: то, что реально публикуется).

Манифест этого набора путей — один файл (`.gitlab/payload-manifest.txt`, не публикуется), а
не два независимо поддерживаемых списка: и джоб зеркалирования (Д2, шаг «собрать payload-
дерево»), и scoped-проверка гейта читают один и тот же список. Сам `check-plugin-
composition.sh` исключает себя из своей новой проверки тем же приёмом, что уже применяет
строка 40 (`--exclude=check-plugin-composition.sh`) к себе — иначе литерал домена внутри
паттерна поиска ловил бы сам себя.

Так гейт отличает «файл уходит в публикацию» (в манифесте — сканируется) от «файл описывает
проверку» (`content/`, `docs/`, ADR, требования, CLAUDE.md, `.gitlab/` — вне манифеста, не
сканируется этой проверкой независимо от того, что цитирует).

**Отклонено:** обобщить существующую строку 65 добавлением второго домена в тот же паттерн
(`'ktalk\.ru|doc-hub\.gitlab\.yandexcloud\.net'`) без сужения области. Технически решило бы
задачу для нового домена ценой немедленного `FAIL` на уже существующей прозе `content/` —
обходить это исключениями по конкретным файлам `content/*` было бы точечным патчем, который
следующая статья, цитирующая домен, снова пробьёт; scoped-манифест решает класс, не
экземпляр.

### Д5. Подтверждение источника истины на GitHub — `.github/` с шаблонами issue/PR и публичным CONTRIBUTING

Новый каталог `.github/` (отсутствует сегодня, Context) входит в payload-манифест (Д4) и несёт
три файла, все — публичное содержимое, отдельное от внутреннего `CONTRIBUTING.md` (тот не
публикуется по санкции оператора без изменений): `.github/CONTRIBUTING.md` — источник истины
внутренний GitLab, GitHub — одностороннее зеркало без автослияния, issue разбираются вручную
и, при принятии, переносятся во внутренний бэклог со ссылкой на исходный; `.github/
ISSUE_TEMPLATE/*.md` и `.github/PULL_REQUEST_TEMPLATE.md` — то же утверждение баннером
вверху формы, которую видит каждый до отправки. Подтверждение — текст, который автор issue/PR
физически не может не увидеть при заполнении формы через нативный механизм GitHub, а не бот-
ответ постфактум: свойство «SHALL be acknowledged» выполнено предъявлением текста, без
автоматизации переноса или закрытия.

**Отклонено:** пиновать комментарий ботом при создании каждого issue. Требует токена с правом
писать в публичный репозиторий от имени сервисного аккаунта и код, который это делает —
лишняя движущаяся часть и лишний секрет ради текста, который шаблон формы показывает
бесплатно и раньше (до отправки, а не после).

### Д6. Паритет каналов — guard резолвимости ref'ов, затем три буквальные команды сравнения

Для одного и того же релизного тега на обоих remote (внутренний `gitlab`, публичный `github`
— именованные remote одного локального клона у релиз-инженера/DevOps) сверка — два шага, не
один: сначала оба ref'а проверяются на резолвимость, затем — три признака паритета. Разделение
обязательно по свойству самих git-команд: `git show <ref>:file` и `git ls-tree <ref> ...` на
неразрешимом `ref` (опечатанный тег, несуществующая версия) одинаково завершаются кодом 128 и
печатают пустой stdout с ОБЕИХ сторон сравнения — `diff` двух пустых потоков тоже пуст, поэтому
без явной проверки ref'а ошибка обращения к тегу неотличима от подтверждённого паритета.
Guard — один на все три команды, не три отдельных: оба ref'а («`gitlab/<tag>`», «`github/<tag>`»)
буквально встречаются в каждой из них, а `git ls-tree` на неразрешимом ref'е ведёт себя так же,
как `git show` (код 128, пустой stdout) — общей проверки достаточно для всех трёх признаков.

`for ref in gitlab/<tag> github/<tag>; do git rev-parse --verify -q "$ref" >/dev/null || { echo "ПАРИТЕТ НЕ ПРОВЕРЕН: ref '$ref' не резолвится"; exit 1; }; done`

| # | Признак | Команда |
|---|---|---|
| 1 | Версия плагина | `diff <(git show gitlab/<tag>:.claude-plugin/plugin.json \| python3 -c "import json,sys;print(json.load(sys.stdin)['version'])") <(git show github/<tag>:.claude-plugin/plugin.json \| python3 -c "import json,sys;print(json.load(sys.stdin)['version'])")` |
| 2 | Пин `compat.json` | `diff <(git show gitlab/<tag>:compat.json) <(git show github/<tag>:compat.json)` |
| 3 | Состав payload | `diff <(git ls-tree -r --name-only gitlab/<tag> -- $(cat .gitlab/payload-manifest.txt)) <(git ls-tree -r --name-only github/<tag>)` |

Пустой вывод всех трёх ПОСЛЕ прохождения guard'а — паритет подтверждён; непустой — дефект
зеркалирования (не повод считать зеркало «версией для другой аудитории», BA-001).
`marketplace.json` намеренно не входит ни в один из трёх (его различающееся поле `name` —
предмет Д1, не дефект); проверка №3 сравнивает состав файлов, не их содержимое, поэтому не
конфликтует с Д1.

**Отклонено:** сравнивать `marketplace.json` целиком как четвёртый признак. Требование
называет ровно три признака; добавление четвёртого создало бы постоянно красную проверку
из-за намеренного расхождения Д1 — тот же vacuous-класс дефекта, о котором предупреждает
`content/lessons-learned.md`.

**Отклонено:** три отдельных `git rev-parse --verify`, по одному перед каждой из трёх команд.
Оба ref'а — общий вход всех трёх признаков; три копии одной и той же проверки несли бы тот же
риск рассинхронизации от точечной правки одной копии без остальных, который это же решение уже
отклоняет в Д1 (второй `marketplace.json`) и Д3 (второй `README.md`).

## Consequences

**Positive:** потребитель различает каналы по имени маркетплейса и по тексту README; паритет
релиза — три исполняемые команды, не декларация; гейт состава ловит второй внутренний домен
без ложных срабатываний на прозу `content/`; обращения с публичного канала не создают скрытого
обратного потока в код или бэклог.

**Negative:** новый каталог `.github/` и файл `.gitlab-ci.yml` — движущиеся части, которых не
было; `LICENSE` в дереве сегодня нет — Дev обязан завести его до первой публикации; выданный
GitHub-токен — секрет, требующий ротации и области видимости, которых раньше не было.

**Mitigations:** `.gitlab-ci.yml` и `.gitlab/payload-manifest.txt` не входят в payload —
провал их работы не течёт в публичный репозиторий сам по себе; токен — protected/masked,
ограничен защищёнными тегами; отсутствие `LICENSE` — пункт брифа Dev, не открытый вопрос. Д6
несёт guard резолвимости обоих ref'ов перед сравнением: без него опечатанный или несуществующий
тег даёт пустой `diff` с обеих сторон, неотличимый от подтверждённого паритета (находка QA,
учтена до принятия решения).

Это решение **extends in part** ADR-025: Д1 ADR-025 (форма тега `<plugin>--v<version>`) —
переносится без изменений, становится условием запуска Д2 этого решения; Д3 ADR-025 (полнота
пути обновления) — расширяется вторым подразделом README (Д3 этого решения), не пересматривая
формулировку для внутреннего канала; Д2, Д4–Д7 ADR-025 (description маркетплейса, retired-имя,
переезд `agents/references/`, гейтовый контур) — не затронуты, второго канала не касаются.
Открытый вопрос ADR-025 Д4 (самообнаружение устаревания) остаётся за тем решением без
изменений — этот ADR его не расширяет и не сужает.

## Alternatives Considered

Цена каждой отклонённой альтернативы — инлайн при своём решении (Д1–Д6 выше), тем же приёмом,
что ADR-024/ADR-025.
