# ADR-025: Поставочная поверхность плагина и доставка релиза потребителю

**Status:** Proposed
**Date:** 2026-09-03
**Capability:** `openspec/specs/release-delivery-tails/spec.md`

## Context

BA-001 (`content/30-requirements/2026-09-03-release-delivery-tails.md`) фиксирует пять
самостоятельных разрывов между тем, что владелец плагина публикует, и тем, что видит и
получает потребитель, плюс открытый архитектурный вопрос, который BA явно передаёт этому
решению не разрешённым. Все замеры ниже прогнаны заново в этой сессии (не унаследованы от
BA без проверки — урок 2026-08-31, PM/SA):

- `claude plugin tag --dry-run --force` (флаг обходит только незакоммиченный
  `.nauta-authority-observations.jsonl`, не логику тега) печатает `Tag: ktalk--v1.9.0` для
  сегодняшнего `plugin.json`, тогда как `git tag -l` называет шесть тегов формы `vX.Y.Z`
  (`v1.3.0`…`v1.9.0`) — ни один не совпадает с формой инструмента.
- `claude plugin validate .` на сегодняшнем `.claude-plugin/marketplace.json` даёт
  `⚠ Found 1 warning: description: No marketplace description provided`.
- `~/.claude/plugins/known_marketplaces.json` — 23 записи, ровно одна (`nsmp-plugins`) несёт
  `"autoUpdate": true`; `claude plugin marketplace add --help` перечисляет только `--scope` и
  `--sparse` — ключа, включающего `autoUpdate` за потребителя, нет ни у одной опубликованной
  команды.
- `~/.claude/plugins/installed_plugins.json`: запись `ktalk@ktalk-plugins` несёт две записи
  разного `scope` — `user` на `1.9.0` (`lastUpdated: 2026-09-02`) и `local` (проект
  `naumen-cto`) на `1.5.0` (`lastUpdated: 2026-08-26`) — живое подтверждение того самого
  отставания, которое BA описывает текстом.
- `agents/references/two-pass-analysis.md`, `protocol-template.md`,
  `vault-update-and-report.md` — все три дают в `claude plugin tag --dry-run` предупреждение
  «No frontmatter block found», то есть платформа сканирует их как кандидатов в агенты по
  расположению, не по наличию смыслового фронтматтера.
- `content/.doc-root.yaml:10` и `.nauta-gates.yaml:103` называют пакет литералом `ktalk-mcp`
  — retired-имя (переход зафиксирован ADR-024); `README.md:50` утверждает, что токен
  «подхватывают и CLI, и MCP-сервер» — `ktalk --help` (прогнано заново) не содержит `mcp` ни
  в каком регистре, MCP-поверхности у пакета нет с ADR-022.
- `bash scripts/check.sh --fast` печатает три признания: `projectGates: absent`,
  `branchDiscipline` не объявлен («undetermined»), и три гейта (`check-adr-line-limit.py`,
  `check-test-subject-governs.py`, `check-content-actuality.py`) не доставлены, потому что
  `.nauta-scripts-basis.yaml` называет `nauta 0.27.0`, тогда как в кеше плагина установлена
  `0.28.2` (`find ~/.claude/plugins/cache/nauta/nauta -maxdepth 1` — восемь версий, старшая
  `0.28.2`; все три недостающих гейта физически присутствуют в её payload).

## Decision

### Д1. Форма релизного тега — `claude plugin tag`, существующие теги не переписываются

Начиная со следующего релиза плагина, тег создаётся командой `claude plugin tag` (не ручным
`git tag`) — она формирует ровно ту строку, которую платформа резолвит при разрешении
версионных зависимостей (`<plugin>--v<version>`), и попутно проверяет согласие `plugin.json` с
записью маркетплейса — это её свойство, не побочный эффект, отдельная проверка не заводится.

Шесть уже опубликованных тегов (`v1.3.0`…`v1.9.0`) **не переписываются и не удаляются**.
Форсированное перемещение или удаление тега, уже разрешённого кем-то ранее (клоном,
локальным чек-аутом), молча подменяет то, что резолвится по этому имени — тот же класс
риска, который ADR-024 Д3 уже отказалась допускать для `--force` при установке пакета:
там результат явный отказ вместо тихой подмены, здесь — тот же принцип, применённый к тегу.
Новая форма действует только вперёд, начиная со следующего релиза; ретроактивный тег
`ktalk--v1.9.0` для уже опубликованной версии не заводится этим решением — сегодня ни один
известный потребитель не резолвит версионное ограничение против этого плагина, поэтому цена
задержки до следующего релиза ниже цены заведения второго тега на тот же коммит без явной
необходимости.

Отклонено: переименовать шесть существующих тегов в новую форму — переписывание истории
тегов миграцией является риском согласно этому же решению (см. выше), не техническим
неудобством, которое можно принять ради единообразия.

### Д2. `description` манифеста маркетплейса

`.claude-plugin/marketplace.json` получает top-level `description`, отдельное от
`description` записи `plugins[0]`. Проверено вживую (скретч-правка, не закоммичена):
добавление поля убирает предупреждение `claude plugin validate .` полностью — `✔ Validation
passed` без предупреждений.

### Д3. Полный документированный путь обновления и явная граница возможностей издателя

README называет **обе** команды в порядке `claude plugin marketplace update ktalk-plugins` →
`claude plugin update ktalk@ktalk-plugins` → перезапуск сессии — не только первую. Рядом —
явное утверждение границы: издатель не может включить фоновое обновление за потребителя ни
одной опубликованной командой (`claude plugin marketplace add --help` не даёт флага для
`autoUpdate`; сам ключ — свойство `known_marketplaces.json` потребителя, правится только на
его стороне) — эта граница называется текстом, не остаётся недосказанностью и не
подаётся как то, что от издателя не зависит вовсе (зависит его документация полноты пути,
не факт применения потребителем).

### Д4. Самообнаружение устаревания плагином — отклонено в этом раунде

Точка подключения существует (шаг 0 онбординга, `ktalk-onboard.sh check`, уже исполняется
каждым навыком/агентом и уже печатает команду ремонта для пакета CLI). Решение — не
использовать её для этой цели сейчас, по трём независимым основаниям:

1. **Формат не обещан плагину.** `~/.claude/plugins/marketplaces/<mkt>/`,
   `~/.claude/plugins/known_marketplaces.json`, `~/.claude/plugins/installed_plugins.json` —
   внутреннее состояние менеджера плагинов платформы, не документированный контракт,
   аналогичный `ktalk --version`/`uv tool list` (публичные интерфейсы инструментов, от
   которых плагин уже явно зависит и на чей формат вывода уже опирается онбординг-скрипт).
2. **Имя маркетплейса не выводится однозначно.** У плагина нет статически известного имени
   маркетплейса, из которого он поставлен (`claude plugin marketplace add` даёт потребителю
   выбрать любое имя) — единственный наблюдённый на этой машине путь к нему (форма каталога
   кеша `~/.claude/plugins/cache/<mkt>/<plugin>/<version>/`, откуда в принципе можно было бы
   вывести `<mkt>` из `${CLAUDE_PLUGIN_ROOT}`) — недокументированная деталь реализации
   раскладки кеша, не контракт; альтернатива (сканировать все клоны маркетплейсов в поиске
   записи `plugins[].name == "ktalk"`) неоднозначна при нескольких маркетплейсах, несущих
   разные пакеты с одинаковым литеральным именем.
3. **Даже успешное чтение не даёт того, что нужно оператору.** Клон маркетплейса сам может
   отставать от опубликованного релиза (та же причина, по которой отстала копия владельца
   этой машины) — сравнение «версия плагина против версии в клоне» доказывает не «устарел
   относительно опубликованного», а более слабое «устарел относительно того, что уже
   скачано» — разница, которую любой текст результата обязан был бы формулировать явно,
   иначе он читался бы увереннее, чем оправдано данными (то самое запрещённое красными
   линиями «правдоподобная уверенность вместо честного N/A», применённое здесь не к числу, а
   к диагностике).

Ни одно из трёх оснований не техническая невозможность — все три снимаются, если платформа
опубликует стабильный, документированный способ спросить «доступна ли более новая версия
этого плагина» (тогда пересмотр этого решения — отдельная, более дешёвая задача, не
доследование по недокументированному формату). До тех пор путь обновления остаётся полностью
документным (Д3) — README и онбординг называют обе команды текстом; граница называется явно
(«плагин не определяет собственную устарелость — сверяйтесь вручную по документированному
пути»), не прячется.

Отклонено: читать только `${CLAUDE_PLUGIN_ROOT}/.claude-plugin/plugin.json` и молчать, если
клон маркетплейса не найден — совпало бы по форме с «всё актуально» и было бы тем самым
молчаливым «ок» при нечитаемом входе, который красные линии этой задачи прямо запрещают.

### Д5. `agents/references/*.md` переезжают в `references/ktalk-processor/`

Три файла-справочника `ktalk-processor` покидают `agents/` (каталог, который платформа
сканирует как источник агентов по расположению, не по фронтматтеру — `claude plugin tag
--dry-run` подтвердил это предупреждением по всем трём файлам, не отказом их
зарегистрировать) и переезжают в `references/ktalk-processor/two-pass-analysis.md`,
`protocol-template.md`, `vault-update-and-report.md` — новый подкаталог уже существующего
общего `references/` (сегодня несёт один файл, `onboarding.md`, читаемый всеми пятью
промтами по конвенции `${CLAUDE_PLUGIN_ROOT}/references/onboarding.md`).

Подкаталог, а не плоское размещение прямо в `references/`: три файла принадлежат одному
агенту, не общие для всего плагина, как `onboarding.md` — пространство имён по агенту
устраняет коллизию имён на будущее, если у другого агента появится собственный справочник, и
делает владение видимым по одному пути, без чтения содержимого.

Все восемь ссылок `agents/ktalk-processor.md` (сегодня — голый относительный путь
`references/<файл>.md`, строки 47–49, 150, 188, 222, 311, 315) приводятся к той же форме, что
уже несёт строка 36 того же файла и все четыре остальных промта: `${CLAUDE_PLUGIN_ROOT}/references/ktalk-processor/<файл>.md`.

Отклонено: оставить файлы на месте и добавить им фронтматтер — проверено вживую (`claude
plugin tag --dry-run` даёт предупреждение о фронтматтере, но не о регистрации; регистрация
как агент определяется расположением, добавленный фронтматтер её не снимает).

### Д6. Метаданные и README не называют retired-имя пакета

`content/.doc-root.yaml:10` и `.nauta-gates.yaml:103` заменяют литерал `ktalk-mcp` на
описание зависимости по роли («отдельно устанавливаемый CLI-пакет»), не на новый литерал
(`ktalk-cli`) — повторение того же класса регресса, который уже случился один раз при первом
переименовании (урок 2026-09-02: «имя внешней зависимости в промт-слое не называть вовсе,
авторитет — `compat.json`»), только с другим неавторитетным носителем на этот раз.
`README.md:50` («файл подхватывают и CLI, и MCP-сервер») корректируется до факта — только CLI
(`ktalk --help`, прогнано заново, ни `mcp`, ни `serve` ни в каком регистре). Соседняя строка
`README.md:48` (`~/.config/ktalk-mcp/token`) не трогается — это путь конфигурации, реальный и
подтверждённый (`ktalk token status` печатает его буквально), не имя пакета.

### Д7. Гейтовый контур — `projectGates`, `branchDiscipline`, базис `nauta` отдельной задачей

`projectGates` в `.nauta-gates.yaml` подключает три GO-критерия, которые `CLAUDE.md` уже
называет обязательными текстом: `check-plugin-composition.sh` и `check-prompt-language.sh` — в
`fast:` (оба вместе — около 0,5 с, измерено); `test-onboard.sh` — в `full:` (около 33 с,
измерено — на два порядка дороже первых двух, и уже сегодня практика проекта третирует его
как предпубликационную, не подкоммитную проверку). `fast:` исполняется в обоих профилях,
`full:` — только в `--full`; вписывание дорогой сьюты в `fast:` раздуло бы бюджет каждого
быстрого прогона в 30+ раз ради проверки, которая по факту нужна раз на публикацию.

`branchDiscipline.profile: single` — репозиторий уже живёт этим профилем практически (одна
ветка роли на рабочую копию, `.claude/worktrees/<id>`, история веток вида `dev-014-…`,
`epic-…`), решение делает это объявленным, а не выводимым.

Полный ре-синк базиса `nauta` (`/nauta:sync-scripts`, доведение до 0.28.2 и появление трёх
недостающих гейтов) — **отдельная задача**, не часть этого эпика: `/nauta:sync-scripts` —
чужая поставка, замораживающая 20 файлов по sha256 (`.nauta-scripts-basis.yaml`), и урок
2026-08-29 этого дерева запрещает править доставляемые чужим плагином скрипты вручную;
сам ре-синк — операция с собственным риском конфликтов (поле `conflicts:` базиса), требующая
отдельного прогона и ревью, не довесок к волне про доставку релиза. Конкретный, измеренный
симптом отставания базиса, не гипотетический: `.gitignore` этого дерева (синхронизирован под
`nauta 0.27.0`) не несёт строку `.nauta-authority-observations.jsonl`, которую собственный
`.gitignore` `nauta 0.28.2` уже объявляет как «запись сессии рабочей машины, не коммитится» —
живой прогон `check-plugin-composition.sh` в рабочей копии-worktree подтвердил, что этот
файл (не отслеживаемый git, не входящий в состав плагина) ложно срабатывает на проверку
«абсолютный путь домашнего каталога». Это не довод в пользу немедленного ре-синка (симптом
решается точечно, см. companion, «Находка при верификации»), а довод в пользу того, что
отставание базиса — не абстрактный риск, а уже дающий наблюдаемые последствия факт.

## Consequences

**Positive:** релизный тег резолвится платформой корректно начиная со следующего релиза;
маркетплейс проходит `claude plugin validate .` без предупреждений; документированный путь
обновления действительно переводит установленную копию на новую версию, а не останавливается
на кэше; список агентов сессии не содержит справочных файлов; метаданные и README не
расходятся с фактическим составом зависимости и интерфейса; три GO-критерия `CLAUDE.md`
исполняются автоматически, не по памяти; дисциплина веток объявлена, а не выводится.

**Negative:** восемь ссылок `ktalk-processor.md` и минимум пять внешних файлов
(`skills/ktalk-eval/references/eval-rubric.md`, `skills/ktalk-registry/references/
analysis-quality.md`, `skills/ktalk-registry/references/registry-format.md`, два файла
`openspec/specs/`) несут литеральный путь `agents/references/…`, который переезд делает
устаревшим текстом, если его не поправить тем же раундом (полный список — companion, «Точка
правки: перенос `agents/references/`»). `check-plugin-composition.sh` в его сегодняшнем виде
даёт ложный `FAIL` в рабочей копии-worktree (два независимых пробела в списке исключений
`grep`, не связанных с этим решением по существу, но становящихся блокирующими в момент
подключения гейта в `projectGates`) — Д7 не самортизирован без companion-фикса, см. «Brief for
Dev». Самообнаружение устаревания остаётся нерешённой болью там, где README читают не до, а
после того, как отставание уже стало проблемой — Д4 принимает эту цену явно, не прячет её.

**Mitigations:** переезд `agents/references/*.md` — переименование путей, не изменение
содержимого файлов; исполняется одним раундом Dev вместе со всеми найденными точками
цитирования (companion называет их по имени файла и строке, не оставляет искать). Ложный
`FAIL` состава — точечный фикс двух `--exclude` в уже существующей функции `check()`, не
новый гейт и не редизайн. Отсутствие самообнаружения компенсируется полнотой
документированного пути (Д3) — корень измеренной BA проблемы (README называл только половину
шагов) устраняется независимо от исхода Д4.

## Alternatives Considered

Цена каждой отклонённой альтернативы — инлайн при своём решении (Д1–Д7 выше), тем же приёмом,
что ADR-024.
