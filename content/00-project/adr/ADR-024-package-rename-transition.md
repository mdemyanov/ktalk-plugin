# ADR-024: Переход `ktalk-mcp` → `ktalk-cli` — идентичность пакета в `compat.json`, коллизия слота, откат

**Status:** Proposed
**Date:** 2026-08-31
**Capability:** `openspec/specs/package-rename-transition/spec.md`

## Context

BA-001 (`content/30-requirements/2026-08-31-package-rename-transition.md`) закрывает пять
свойств второго ломающего изменения подряд — переименование пакета `ktalk-mcp` в `ktalk-cli`
— и прямо оставляет SA три вопроса: форму разрешения коллизии слота `uv tool install` между
двумя разными именами пакета (не версиями одного, как в ADR-022 Д3), схему идентичности
пакета в `compat.json` (сегодня — только версия, зашитая в имя ключа `ktalk_mcp_version`), и
текст/код возврата для «пакет не тот» отдельно от «версия не та».

Три факта, установленные чтением, а не предположением:
- `ktalk --version` пакета `ktalk-mcp` печатает `f"ktalk-mcp {__version__}"`
  (`ktalk_mcp/cli.py:381`, дерево пакета, только чтение) — литерал имени дистрибутива уже
  присутствует в выводе, но `installed_version()` сегодня вырезает из него только цифры
  регэкспом, отбрасывая имя.
- `remedy_cmd_text()`/`remedy_cmd_array()` (`scripts/ktalk-onboard.sh:32-42`) и фрагмент
  `installed_version()` (`:57`) зашивают литерал `"ktalk-mcp"` текстом внутри функции, не
  переменной — при переименовании эти литералы обязаны стать параметром, иначе плагин после
  релиза продолжит печатать и исполнять команды с именем пакета, который выводится из
  обращения.
- Три сообщения `cmd_check`/`cmd_install`/`finish_install` (строки 137, 147, 337, 359) тоже
  называют пакет литералом `"ktalk-mcp"` в тексте для оператора — та же зависимость.

## Decision

### Д1. `compat.json` — два generic-поля вместо версии, зашитой в имя ключа

Ключ `ktalk_mcp_version` заменяется парой `package_name` + `package_version`. Идентичность
несёт **значение**, а не имя поля — при следующем переименовании меняются только значения,
имена ключей — нет.

Отклонено: переименовать ключ в `ktalk_cli_version` (тот же самый манёвр ADR-022 Д3
«`_min_version` → `_version`», но повторённый на имени пакета — при СЛЕДУЮЩЕМ переименовании
воспроизводит ровно ту же церемонию заново, схема не переживает второй проход). Отклонено:
держать оба ключа рядом (`ktalk_mcp_version` — legacy, `ktalk_cli_version` — новый) — тот же
вопрос «какой ключ авторитетен», который сама замена `_min_version`→`_version` уже устраняла
однажды; заводить его снова для имени пакета — регресс того решения.

### Д2. Несовпадение пакета — отдельный, именованный статус, не вариант `outdated`

`installed_identity()` (расширение `installed_version()`) разбирает **оба** токена уже
получаемого вывода `ktalk --version` — имя дистрибутива и номер версии — вместо того чтобы
отбрасывать первый; тем же способом расширяется резервный путь через `uv tool list`,
построчно сверяемый с конечным списком известных идентичностей (`ktalk-mcp`, `ktalk-cli`).
`cmd_check`/`finish_install` сравнивают имя и версию раздельно: несовпадение имени —
новый статус `wrong_package` и новый код возврата; несовпадение только версии при
совпадающем имени — прежний `outdated`, без изменений.

Отклонено: оставить один статус `outdated` на оба случая — стирает разницу между «поставить
отсутствующий пакет» и «откатить чужую, возможно совместимую с чем-то другим установку»,
ровно ту неоднозначность, которую требование просит убрать (BA, «Вопрос к SA»). В текстовом
(не `--json`) режиме иного способа различить состояния для внешнего потребителя по коду
возврата нет — текстовое сообщение для этого недостаточно, если вызывающая сторона машина, не
человек.

### Д3. Санкционированный `install` никогда не добавляет `--force`; коллизия слота останавливает, а не разрешается

Команда ремонта остаётся `uv tool install <pkg>==<pin>` без `--force` — та же форма, что и до
этого решения. Когда слот уже занят другим пакетом, `uv` сам отказывает (код 2, замер BA);
скрипт распознаёт этот отказ по тексту вывода и репортит новый статус `slot_collision`
(не общий `install_failed`), называя оба пакета. Ни при какой санкции скрипт не повторяет
попытку с `--force` — принудительная замена остаётся действием, которое оператор набирает
руками, а не предлагает или исполняет автоматизация: любой автоматический путь к `--force`
(пусть и под санкцией) и есть тот молчаливый захват, который требование запрещает буквально
(«Neither package's default install flow SHALL silently overwrite the other's `ktalk`
command»).

Санкция на ремонт при смене идентичности переиспользует существующий `allow_update`, новый
ключ не заводится: граница ADR-022 Д2 «команда уже существует, указывает на что-то другое» —
уже описывает и версию другого пакета, не только другую версию того же. Отклонено: новый
ключ `allow_migrate` — дробит уже фейл-клоузд, протестированную санкционную модель ради
случая, который существующий предикат ADR-022 Д2 покрывает дословно.

### Д4. Откат — принудительная переустановка целевой идентичности вперёд, никогда не «удалите новый пакет»

Замеренная третья строка таблицы (удаление пакета, чей бинарник жив, стирает файл целиком;
запись второго пакета в `uv tool list` остаётся, но не «оживает» — код **127**) исключает
инструкцию «удалите `ktalk-cli`, `ktalk-mcp` восстановится» как правильный шаг отката.

Схема отката, в этом порядке:
1. Принудительно переустановить целевую (откатываемую) идентичность явно —
   `uv tool install <target>==<pin> --force`. Это единственное место, где `--force` руками
   оператора — правильное действие: он не разрешает свежую коллизию автоматизацией
   (запрещено Д3), а восстанавливает заведомо известное состояние явным, штучным вызовом.
2. Проверить результат через живое разрешение (`command -v ktalk` + имя из `ktalk --version`),
   не через `uv tool list` — список подтверждённо не отражает, кто реально исполняется, после
   принудительной замены (замер BA, наблюдение 2).
3. Только после подтверждённого шага 2 — снять зависшую регистрацию оставленного пакета
   (`uv tool uninstall`). Раньше шага 1 этот шаг не выполняется никогда: именно эта
   последовательность («удалите новый — старый вернётся сам») и была тем сценарием, который
   BA измерила как оставляющий оператора без рабочей команды вовсе.

Отклонено: «удалить новый пакет и ожидать возврата старого» — измеренно ведёт к коду 127, не к
отклонённой альтернативе на бумаге, а к воспроизведённому дефекту.

### Д5. Версия-указатель `ktalk-mcp` не получает отдельного распознавания

Любая установленная `ktalk-mcp` (версия-указатель или более ранняя) равно `wrong_package`
относительно пина на `ktalk-cli` — скрипт не разбирает и не реагирует на текст депрекации,
он принадлежит собственному каналу пакета, ортогонален соответствию пину. Решения не
требуется, и оно не принимается.

### Д6. Requirement `cli-only-boundary` «Default install excludes the MCP-only dependency» — retired в спеке, superseded in part относительно ADR-022

Решение SA-002 в дереве пакета (снять `fastmcp` из `dependencies` целиком — без extra, без
MCP-точки входа, без выделенного набора MCP-тестов) делает три из четырёх сценариев этой
Requirement не просто невыполненными, а постоянно неисполнимыми: точку входа негде запускать
(сценарий 2), MCP-тесты, которым предписано «работать как прежде», удалены (сценарий 3), а
четвёртый сценарий (таймаут холодной установки) теряет сравнительную базу «полного набора
зависимостей».

Requirement помечена **retired в `openspec/specs/cli-only-boundary/spec.md`**: текст сохранён
дословно как исторический след решения (приём ADR-023 Д1 — указатель, не удаление), датированная
пометка добавлена над её четырьмя сценариями и в `Purpose` спеки. Две другие Requirement этой же
capability («declares no MCP interface surface», «pins an exact package version») не тронуты —
это частичный, не полный supersede. Полная карта пометок и синхронизация companion-статьи
ADR-022 — companion этой задачи, раздел «Retirement `cli-only-boundary`».

Отклонено: переписать сценарии под новое (полностью снятое) состояние — задваивает предмет с уже
существующей в той же capability Requirement «declares no MCP interface surface» и стирает след
того, что Requirement изначально просила. Отклонено: удалить Requirement целиком — тот же манёвр,
что ADR-023 Д1 уже отклонила однажды для другого артефакта (34 битые ссылки, «решено против
того, чего нет»); пометка retired даёт ту же ясность со следом.

Это **superseded in part** относительно ADR-022, установившей Requirement: тело, статус и
frontmatter ADR-022 не редактируются (процедура supersede) — отношение зафиксировано здесь и в
разделе «Related articles».

## Consequences

**Positive:** идентичность и версия диагностируются раздельно везде, где скрипт уже говорит
с оператором (`check`/`install`/`status`); коллизия называет оба пакета по имени, а не
оставляет текст `uv` единственной диагностикой; откат получает проверенно верное целевое
действие вместо интуитивно понятного, но измеренно ломающего.

**Negative:** `cmd_check`/`cmd_install`/`finish_install`/`report`/`install_report` получают
по одной новой ветке сравнения и статусу каждый — больше поверхности, чем версия-only пин;
`--json`-вывод получает новое поле (`installed_package`/`pinned_package`) рядом с уже
существующими `installed_version`/`min_version` — вторая точка внешнего изменения поверх
переименования самого пина. `cli-only-boundary` — принятая
capability с реальным тестовым покрытием — получает первую в этом дереве пометку retired-in-place
внутри спеки (Д6); прецедент, которому будущие ревью drift будут следовать буквально.

**Mitigations:** новая ветка переиспользует ту же последовательность вызовов
(`command -v`/`ktalk --version`/`uv tool list`), что скрипт уже делает — новых подпроцессов
нет, только более широкий разбор уже захватываемого вывода; рост JSON — аддитивный (новое
поле), не переименование поля, на который уже завязан внешний потребитель (`min_version`
сохраняет имя по прецеденту ADR-022 companion).

## Alternatives Considered

Цена каждой отклонённой альтернативы — инлайн при своём решении (Д1–Д4 выше); ADR не дублирует
их отдельным списком, чтобы не разойтись текстом с уже написанным обоснованием.
