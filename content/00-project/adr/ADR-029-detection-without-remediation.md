# ADR-029: Обнаружение отставного режима авторизации без устранения

**Status:** Proposed
**Date:** 2026-09-08
**Capability:** `openspec/specs/session-only-auth/spec.md`

## Context

BA-001 (`content/30-requirements/2026-09-08-retired-mode-detection.md`) добавляет
`scripts/ktalk-onboard.sh check` факт: переменная `KTALK_PERSONAL_API_KEY` задана в окружении
процесса. Требование само фиксирует контракт поведения — предупреждающий код 14, чтение
только окружения процесса (не файлов оболочки, не `.env`), текст с именем команды и списком
из пяти операций (`get-room`, `list-calendar`, `create-meeting`, `cancel-meeting`,
`search-contacts`). Три `### Requirement:` и их `#### Scenario:` уже приняты в
`openspec/specs/session-only-auth/spec.md` (строки 155–227). Этот ADR не переписывает
контракт BA — он записывает решение владельца, стоящее рядом: почему обнаружение не
сопровождается устранением, и цену каждой отклонённой альтернативы устранения.

Владелец задал вопрос дословно: реализован ли хук, который при обновлении плагина сам
удалит остатки отставного режима, если они применены рядом с плагином. Ответ — нет, и это
решение записывает его как архитектурную границу, а не как незакрытую задачу.

Факты, на которые опирается решение:
- ADR-022 Д1: с решения о снятии MCP-поверхности плагин «не объявляет MCP-сервер вовсе» —
  вторичного пути, кроме CLI, для чего-либо больше нет. Хук автообновления, правящий
  состояние машины помимо CLI, — ровно вторая заявленная поверхность, которую ADR-022 снял.
- Модель санкции онбординга: состояние машины меняет оператор своей командой в своём
  терминале (`scripts/ktalk-onboard.sh grant install`, `grant update`); агент без TTY
  отказывает кодом 33 (`references/onboarding.md`, разделы «Code 10»/«Code 11»:
  «The user runs this command. The agent never runs it: without a terminal it refuses
  (code 33)»). Молчаливая правка файла оболочки при автообновлении обходит эту модель
  целиком — файл меняется без того, чтобы оператор сам ввёл команду.
- `content/10-domain/research/2026-09-07-cli-2-1-0-auth-modes.md` §1: установленная
  `ktalk-cli` 2.1.0 читает `KTALK_PERSONAL_API_KEY` первым в приоритете и будет читать его,
  пока не выйдет версия по заявке `github.com/mdemyanov/ktalk-cli#10` (открыта, ADR-028
  Д1 уже фиксирует её вне периметра плагина). Удаление сегодня ничего не мигрирует: код,
  который придаёт переменной приоритет, не меняется этим ADR и не может быть изменён из
  дерева плагина (ADR-012, тонкая обёртка).
- Файл оболочки (`~/.zshenv` и подобные) принадлежит оператору целиком, несёт произвольное
  число не относящихся к плагину присвоений и не читается плагином ни для чего другого.
  Заявление владельца (не измерение координатора): на его машине `~/.zshenv` продолжает
  объявлять `KTALK_PERSONAL_API_KEY` уже после релиза 1.15.0, чья документация (README,
  `references/onboarding.md`) просит переменную снять — сама просьба текстом оказалась
  недостаточной причиной снять её.

## Decision

### Д1. Плагин обнаруживает отставной режим и не устраняет его — граница окончательная для этого эпика

`check` называет факт (код 14, контракт BA выше) и на этом останавливается: не выполняет
`unset`, не правит файл оболочки, не предлагает сделать это за оператора. Устранение —
действие оператора над своими файлами, вне периметра плагина по той же причине, по которой
плагин не читает эти файлы для самого обнаружения (BA-001, раздел «Почему обнаружение —
только переменная процесса»).

**Отклонено (а): хук, автоматически удаляющий переменную из окружения при обновлении
плагина.** Цена — тройная. Во-первых, `unset` в переменной окружения текущего процесса не
переживает завершение процесса и ничего не устраняет на постоянной основе; устранение,
которое ничего не устраняет, вводит оператора в заблуждение хуже отсутствия хука. Во-вторых,
даже будь устранение постоянным, снятие переменной сегодня ломает единственный путь к пяти
операциям, для которых `ktalk-cli` 2.1.0 (§1 RES-001) не имеет альтернативного профиля —
пока не закрыта заявка `#10`, личный ключ не резервный путь, а рабочий для этих пяти команд.
Автоматика превратила бы предупреждение в поломку тех же операций, о которых предупреждает.
В-третьих, обновление плагина без предшествующего диалога с оператором — не то место, где
модель санкции ожидает изменение состояния машины (модель — выше).

**Отклонено (б): хук, правящий файл оболочки (`~/.zshenv` и подобные) при обновлении
плагина.** Цена выше, чем у (а), и по другому основанию — необратимость чужого содержимого.
Файл оболочки не принадлежит плагину и несёт произвольные, не относящиеся к `ktalk`
присвоения; программная правка требует парсинга синтаксиса оболочки, которую плагин не
выбирает и не контролирует (`bash`, `zsh`, `fish` — разный синтаксис присвоения), и первая
же ошибка парсинга ломает не переменную, а весь файл автозапуска оператора. Это ровно
вторая интерфейсная поверхность, которую ADR-022 закрыл: обращение к машине хозяина в обход
единственного заявленного пути (CLI, вызываемого явной командой оператора). Онбординг уже
устанавливает для более безопасного действия (`uv tool install`) переход в отдельную
санкцию (`grant install`/`grant update`) с отказом без TTY (код 33) — молчаливая правка
чужого dotfile при автообновлении не проходит даже этот менее строгий барьер, не говоря о
более разрушительном действии без какой-либо санкции вовсе.

**Отклонено (в): не заводить обнаружение вовсе — оставить всё документации, как было до
этого эпика.** Цена измерена, не гипотетична: на машине владельца `~/.zshenv` продолжает
объявлять переменную уже после релиза 1.15.0, чья документация (README, `references/
onboarding.md`, ADR-028) просит её снять. Просьбы текстом, ничем не подкреплённой в момент
отказа операции, оказалось недостаточно — обнаружение в `check` существует ровно потому,
что документация сама по себе не сработала на измеренном случае.

### Д2. Устранение — исключительно ручное действие оператора; хук не появляется ни в каком будущем виде этого эпика

Оба отклонённых варианта устранения (а, б) остаются отклонёнными до тех пор, пока не
изменится сама модель, на которую они опираются, — не как открытый вопрос этого эпика, а
как исчерпанная развилка: BA-001 явно вывела правку файлов оболочки из периметра
требования, и это решение не создаёт альтернативного механического пути к тому же
результату в обход этого периметра.

## Consequences

**Positive:** оператор получает диагностику раньше отказа операции (BA-001, JTBD) без
второй интерфейсной поверхности и без риска порчи чужого файла; модель санкции онбординга
не приобретает исключения для одного частного случая; граница симметрична модели, уже
принятой ADR-022 (единственный путь — CLI, вызываемый явно) и ADR-028 (плагин не читает
значение и не выбирает режим).

**Negative:** оператор с переменной, объявленной в файле автозапуска оболочки, видит
предупреждение `check` на каждом заходе, пока не отредактирует файл сам — измеренный случай
владельца показывает, что это происходит не единожды и не быстро.

**Mitigations:** сообщение кода 14 (контракт BA-001, спека `session-only-auth`) называет
точную немедленную команду (`unset KTALK_PERSONAL_API_KEY`) и явно говорит, что она не
переживает новую оболочку — оператор не принимает разовую команду за постоянное решение;
предупреждение, не блокировка (BA-001, «Почему предупреждение, а не блокировка») — сессия
не останавливается из-за находки, не мешающей операциям, которыми оператор не пользуется.

## Alternatives Considered

Цена каждой отклонённой альтернативы — инлайн при Д1 (варианты а, б, в) тем же приёмом, что
ADR-024/ADR-025/ADR-027/ADR-028.
