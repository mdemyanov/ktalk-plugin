# ADR-028: Единственный документированный режим авторизации плагина — токен сессии

**Status:** Proposed
**Date:** 2026-09-08
**Capability:** `openspec/specs/session-only-auth/spec.md`

## Context

BA-001 (`content/30-requirements/2026-09-07-session-only-auth.md`) фиксирует решение
владельца сузить промт-слой плагина до одного документированного режима авторизации — токена
браузерной сессии — и снять `KTALK_PERSONAL_API_KEY` из числа поддерживаемых/рекомендуемых.
RES-001 (`content/10-domain/research/2026-09-07-cli-2-1-0-auth-modes.md`) даёт код, на который
решение опирается: приоритет источников токена в установленной `ktalk-cli` 2.1.0
(`KTALK_PERSONAL_API_KEY` → `KTALK_SESSION_TOKEN` → файл `~/.config/ktalk-mcp/token` → отказ,
`config.py:93-131`), асимметрию `OPERATION_PROFILES` (`endpoints.py:47-145`: пять операций —
только session, `list_archive`/отчёт по участникам — только api-key), отсутствие TTL у
сессионного токена (§4), и то, что `get_full_participants` под session — не деградация, а
другая формула данных (`get_recording`+`get_conference`, флаг `incomplete`, §3).

Рамка — ADR-012 «Границы плагина ktalk» (репозиторий пакета `ktalk-mcp`,
`content/00-project/adr/ADR-012-plugin-boundary.md`, наполнен): плагин не вендорит и не правит
код пакета, секреты и выбор режима — не его код. ADR-022 «CLI-граница» (этот репозиторий)
держит `compat.json` точным пином `2.1.0` — этот пин не двигается.

Заявление владельца (сессия 2026-09-07: личный ключ на его контуре фактически не работает) —
мотивация со слов владельца, не измерение координатора; ниже цитируется как заявление.

Имя capability, предложенное BA — `session-only-auth`, — подтверждается без изменений: оно
называет результирующее свойство (один режим), а не процесс сужения к нему.

## Decision

### Д1. Сессионный токен — единственный режим; граница с кодом пакета явная

Промт-слой (`README.md`, `references/`, `skills/`, `agents/`, `commands/`) называет сессионный
токен единственным поддерживаемым режимом: не описывает `KTALK_PERSONAL_API_KEY` как
поддерживаемый/рекомендуемый вариант и не формулирует правило приоритета — приоритетовать
больше нечего.

«Плагин не поддерживает режим» и «CLI не принимает значение» — разные утверждения, граница —
ADR-012/ADR-022: плагин не читает значение токена и не выбирает режим сам, «поддерживает» здесь
значит то, что промт-слой документирует и подсказывает при отказе. `ktalk-cli` 2.1.0 продолжает
читать `KTALK_PERSONAL_API_KEY` и отдавать ему приоритет (RES-001 §1) — снятие поддержки в коде
отслеживает отдельная заявка пакета (`github.com/mdemyanov/ktalk-cli#10`), вне периметра этого
решения. Оператор с ранее заданной переменной продолжит авторизовываться ключом независимо от
текста плагина — расхождение зафиксировано явно, не маскируется. Практическое следствие не
зависит от заявления владельца о нерабочем ключе: единственная операция, для которой ключ был
единственным путём (`list-archive`, Д3), в тексте плагина никогда не предлагалась.

**Отклонено:** «два режима, правило приоритета» плюс файл токена третьим источником. После
сужения поверхности у инструкции нет второго члена, между которым приоритетовать — абзац о
приоритете исчезает не потому, что код его больше не имеет (RES-001 — обратное), а потому что
описывать стало нечего.

### Д2. Файл токена и переменная называются полностью в README и `onboarding.md`; общий сниппет не заводится

Обе точки входа (README, шаг 3; `references/onboarding.md` — повторный онбординг) называют файл
токена (`~/.config/ktalk-mcp/token`/override) наравне с переменной как место значения, и
`ktalk token set -` как команду записи. Текст не обязан быть дословно идентичен, но каждый файл
самодостаточен — оператор не уходит во второй за рабочей инструкцией целиком.

**Отклонено:** единый текст, подключаемый ссылкой из обоих мест. Markdown не даёт транслюзии;
ссылка вместо текста заставляет оператора с истёкшей авторизацией уходить за инструкцией в
момент отказа — цена риска рассинхронизации ниже цены потери самодостаточности в этом сценарии.

### Д3. `list-archive` и отчёт по участникам — инвариант capability, не архитектурная замена

Промт-слой не документирует эти операции — это уже так сегодня (`grep -rn "list-archive"` по
дереву плагина, кроме исследования, — пусто) — и остаётся так же после снятия ключа,
зафиксированное Requirement capability, не отдельным решением с альтернативами.

**Отклонено:** проектировать замену по образцу `get_full_participants` (под session —
композиция, не деградация). Аналогия не работает: у неё есть реальный серверный путь; у
`list_archive`/`get_participants_report` профиль session — `None` (RES-001 §2) — составлять
замену не из чего. Путь, которого в контуре не существует, — задача пакета, не плагина.

### Д4. Статья FR-28 — superseded in part; тело и статус не редактируются

Requirement FR-28 статьи `content/30-requirements/2026-08-18-onboarding-sanctioned-install.md`
(«два режима… ключ побеждает») противоречит Д1 и **считается superseded этим решением в этой
части**. Остальное — FR-26, FR-27, FR-29, FR-30, FR-31, NFR-17..19, «Конфликт с ADR-012» —
описывает процесс онбординга, не содержание инструкции, и не затрагивается.

По правилу supersede (`content/00-project/adr/_index.md`), применённому по аналогии к статье
требования: тело и статус старой статьи не редактируются — отношение зафиксировано здесь и в
дельте `plugin-onboarding-sanctioned-install/spec.md`. Смена статуса статьи — отдельная задача
PM.

**Отклонено:** править FR-28 на месте — стирает след того, что поменялось и почему.

### Д5. Сторож на литерал `KTALK_PERSONAL_API_KEY` — вводится, периметр = Scenario capability

`scripts/check-plugin-composition.sh` получает проверку по образцу «MCP-имя операции встреч
вместо CLI» (blanket-запрет литерала): ищет `KTALK_PERSONAL_API_KEY` в `README.md`,
`references/`, `skills/`, `agents/`, `commands/` — периметр дословно = Scenario «No prompt-layer
file names the retired mode as supported» (`session-only-auth`). `scripts/`, `content/`,
`openspec/` — вне периметра: `ktalk-onboard.sh` легитимно проверяет факт наличия переменной по
имени, а `content/`/`openspec/` обязаны цитировать литерал как факт о коде пакета — та же
ловушка, что уже поймана для гейта внутреннего домена (ADR-027 Д4, `lessons-learned.md`).
Литерал сегодня есть в периметре трижды (`README.md:142`, `references/onboarding.md:138,141`) —
проверка станет зелёной только после их правки (DEV-001); до этого она обязана падать.

**Отклонено:** расширить проверку «секрет со значением» на голое имя без значения. Та проверка
ловит присвоенное значение, не факт документирования режима — смешение усложнило бы диагностику
без выгоды.

## Consequences

**Positive:** одна стабильная точка — одна команда, один текст отказа на любом из трёх входов
BA-001; гейт и capability называют один периметр литерала; инвариант `list-archive`/отчёта по
участникам зафиксирован до того, как правка документации случайно пообещает недоступную
операцию.

**Negative:** оператор с ранее заданной `KTALK_PERSONAL_API_KEY` получает иное поведение CLI,
чем теперь описывает текст плагина (Д1) — расхождение принято сознательно; статья FR-28
остаётся в дереве с формально не изменённым статусом до задачи PM; два независимых места
инструкции (Д2) требуют синхронной правки при следующем изменении контракта авторизации.

**Mitigations:** обе правки README/`onboarding.md` реализует один DEV-001 в одном проходе, окно
рассинхронизации не открывается; Requirement/Scenario capability и сторож Д5 делают Д1/Д2
машинно-проверяемым фактом после DEV-001/DEV-002; статус FR-28 — явный пункт брифа PM (Д4).

## Alternatives Considered

Цена каждой отклонённой альтернативы — инлайн при своём решении (Д1–Д5 выше), тем же приёмом,
что ADR-024/ADR-025/ADR-027.
