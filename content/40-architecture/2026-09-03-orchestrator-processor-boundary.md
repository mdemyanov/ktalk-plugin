# Граница оркестратора и обработчика: делегирование `project-curator` и проверка личности транскрипта

**ADR:** `content/00-project/adr/ADR-026-orchestrator-processor-boundary.md`
**Requirement:** `content/30-requirements/2026-09-03-release-delivery-tails.md`
**Capability:** `openspec/specs/release-delivery-tails/spec.md`

## Context

ADR-026 решает два вопроса границы `ktalk-registry` (оркестратор) / `ktalk-processor`
(обработчик): кто вызывает `project-curator` (issue #6) и как обработчик защищается от
данных, подменённых гонкой `get-transcript` (issue #5). Эта статья — реализационная деталь:
точное место вставки в оба промт-файла, контракт полезной нагрузки между обработчиком и
оркестратором, и бриф для Dev, DevOps и QA-author.

## Components

| Компонент | Ответственность | Входы | Выходы | Зависимости |
|-----------|------------------|-------|--------|-------------|
| `ktalk-processor`, шаг 2b (новый) | Сверяет участников полученного транскрипта с `participants` промта; один повтор на несовпадение | ответ `get-transcript --chunk 0`, `participants` из промта | подтверждённый транскрипт → далее по алгоритму; неподтверждённый → hard-stop | ничего нового — чистое сравнение текста, без дополнительного инструмента |
| `ktalk-processor`, «Final step» (переписывается) | Определяет затронутые проекты, кладёт их в отчёт | `registry.directories.projects_active` (шаг 0b), анализ встречи | строка `Проекты затронуты: {ids}`/`нет` в финальном отчёте | не вызывает `project-curator`, не проверяет его установленность |
| `ktalk-registry`, шаг 5.5 (новый) | Собирает завершения обработчиков одного прогона, копит объединение id, вызывает `project-curator` не более раза | task-уведомления о завершении фоновых `ktalk-processor`, их финальные отчёты | вызов `project-curator` (или пометка пропуска) в сводке прогона | инструмент вызова агента, уже используемый шагом 5 |
| `project-curator` (агент хозяина, вне дерева плагина) | Обновляет карточки проектов, сверяет консистентность команды/статуса | задача от оркестратора: id проектов + список (`meeting_date`, `protocol_path`) по каждому | правки карточек проектов | собственный контракт хозяина, этой статьёй не проектируется |

## Boundaries

- Обработчик после этого решения не хранит и не проверяет установленность `project-curator` —
  это целиком забота оркестратора (ADR-026 Д2).
- Батч, который ждёт шаг 5.5, живёт в пределах одной сессии оркестратора: обработчик,
  упавший или зависший до отправки финального отчёта, выпадает из набора, и вызов
  `project-curator` для этого прогона не происходит **даже за проекты, о которых успели
  отчитаться другие обработчики того же прогона** — оркестратор не умеет отличить «обработчик
  ещё работает» от «обработчик никогда не завершится», и не вводит таймаут (его выбор — вне
  мандата этой статьи, ADR-026 «Negative»).
- Проверка личности сверяет только участников — не `recording_id`, не длительность: у ответа
  `get-transcript` нет ни одного из этих двух полей (см. «Integration points»). Дизайн не
  чинит кэш/гонку в `ktalk-cli` — корень остаётся в дереве пакета.
- Не решается этой статьёй: конкурентная запись обработчиков в один и тот же файл карточки
  проекта или профиля участника со стороны шагов «Automatic» (`vault-update-and-report.md`,
  «Add the meeting to the project card's log», «Append an entry to История 1-1») — это
  происходило и до делегирования `project-curator`, независимо от него; наблюдение issue #6
  про одновременную правку `smrm-ecosystem.md`/`apavlov.md` двумя обработчиками относится
  именно сюда, не к самому шагу делегирования. Капабилити-спека этого требования не покрывает
  данный след — он остаётся открытым риском, не тихо устранённым.
- Транскрипт, для которого распознавание участников невозможно (полностью анонимизированные
  метки спикеров вместо имён), — не разбираемый этой статьёй частный случай сравнения; Dev
  фиксирует конкретное правило разбора, QA-author фиксирует, что реализовано, фактом теста
  (тот же принцип, что уже применён в `content/40-architecture/2026-08-31-cli-only-
  boundary.md`, «Edge cases», к нормализации версий).

## Data flow

### Проверка личности (обработчик, шаг 2 → 2b → 2.5)

1. `ktalk get-transcript {recording_id} --chunk 0 --json` (не меняется).
2. **Шаг 2b (новый).** Извлечь имена спикеров из полученного текста chunk 0; сравнить с
   `participants[].name` промта. Совпадение хотя бы одного имени — участники подтверждены,
   идти к п.4. Несовпадение — п.3.
3. Ровно один повтор: тот же вызов `get-transcript {recording_id} --chunk 0 --json`. Второй
   результат сравнивается тем же правилом. Совпадение — к п.4. Несовпадение —
   **hard-stop**: не сохранять файл транскрипта, не грузить оставшиеся chunk'и, не запускать
   шаг 2.5 и далее; `ktalk mark-partial {recording_id}` без `--transcript`/`--protocol`;
   финальный отчёт называет запрошенный `recording_id` и найденных участников — сам отчёт при
   этом не несёт заголовок `✅ Встреча обработана`, поскольку встреча не обработана.
4. Участники подтверждены → **теперь** (не раньше) сохранить chunk 0 (и для большого
   транскрипта — догрузить оставшиеся chunk'и, п.5–6 не меняются) по шаблону
   `registry.routing.transcript_archive`. Если п.3 потребовался и решился совпадением —
   финальный отчёт добавляет в «Требует внимания» строку: `get-transcript вернул чужие
   данные при первой попытке, устранено повтором` — транзиентная гонка не пропадает из вида
   оператора молча (ADR-026 Д5).
5. Дальше — шаг 2.5 и весь алгоритм без изменений.

### Делегирование `project-curator` (оркестратор, шаг 5 → 5.5 → 6)

1. Шаг 5 (не меняется): оркестратор запускает `N` обработчиков в фоне для набора
   `recording_id`, отобранного на шаге 3 этого же вызова навыка — это и есть «прогон» в
   терминах ADR-026 Д3. Оркестратор уже держит для каждого `recording_id` его `date` и
   предложенный `save_location` из собственного шага 4 — эти факты не запрашиваются у
   обработчика повторно.
2. **Шаг 5.5 (новый).** По мере поступления task-уведомлений о завершении каждого
   обработчика прогона: прочитать строку `Проекты затронуты: {ids}`/`нет` его финального
   отчёта, накопить объединение по всем id, отметить обработчика завершённым.
3. Когда все `N` обработчиков прогона отмечены завершёнными:
   - объединение пусто → `project-curator` не вызывается, шаг 5.5 завершается без действия;
   - объединение непусто → попытаться вызвать `project-curator` один раз с задачей вида
     `обнови карточки проектов {ids} с учётом встреч: {date} — {protocol_path или "только
     транскрипт"}, ... . Проверь консистентность команды и статуса.` (тот же текст задачи,
     что раньше строил обработчик поодиночке — ADR-026 Д2 — только на список встреч, а не на
     одну). Если вызов не резолвится (агент не установлен в проекте-хозяине) — поймать это и
     добавить в сводку прогона: `project-curator не установлен — обновление карточек
     пропущено`.
4. Шаг 6 (не меняется): `ktalk export` обновляет markdown-зеркало реестра.

## Integration points

| Точка | Протокол | Контракт | Auth | Rate limit | Обработка ошибок |
|-------|----------|----------|------|------------|-------------------|
| `ktalk-processor` → `ktalk get-transcript` | подпроцесс CLI, `--json` | ответ не несёт ни `recording_id`, ни длительность — только текст/спикеров (issue #5) | — | один повтор на несовпадение, не более | несовпадение после повтора → `mark-partial`, hard-stop |
| `ktalk-processor` → финальный отчёт (текст, читает оркестратор) | task-уведомление о завершении фонового агента | обязательная строка `Проекты затронуты: {ids}`/`нет`; на hard-stop — отчёт без заголовка `✅ Встреча обработана` | — | — | оркестратор не различает «обработчик работает» и «завис» — см. Boundaries |
| `ktalk-registry` → `project-curator` | вызов агента (тот же инструмент, что уже вызывает `ktalk-processor` на шаге 5) | задача: объединённый список id + (`date`, `protocol_path`) по каждой встрече | — | не более 1 вызова на прогон | нерезолвящееся имя агента → пометка пропуска в сводке, не фатальная ошибка |

## Contract with QA-author

**Acceptance scenarios (полный список для ADR-026):**
- Scenario: A processor agent that touched a project does not call project-curator — из
  `### Requirement: Project delegation to project-curator is routed through the orchestrator`
- Scenario: The orchestrator invokes project-curator once, after every processor completes —
  там же
- Scenario: project-curator is not installed in the host project — там же
- Scenario: A matching transcript proceeds without an extra step — из `### Requirement: A
  fetched transcript's identity is verified before it is used`
- Scenario: A mismatched transcript is retried once — там же
- Scenario: A mismatch that survives the retry is a hard stop, not a silent continuation —
  там же

**Architectural context for the tests:**
- Компоненты: `ktalk-processor` (шаг 2b, «Final step»), `ktalk-registry` (шаг 5.5),
  `project-curator` (за пределами дерева плагина — доступен только по факту установленности).
- Границы доверия: `get-transcript` CLI (внешний, недоверенный ответ) → шаг 2b (сверка) →
  анализ; обработчик (недоверенное «завершился ли») → шаг 5.5 (сборка прогона) →
  `project-curator` (внешний, может отсутствовать).
- Носитель проверяемости: и делегирование, и сверка личности **всегда** оставляют
  наблюдаемый след в финальном отчёте/сводке прогона (строка `Проекты затронуты:`,
  подтверждение личности на happy path, пометка пропуска `project-curator`) — это тот
  контракт, по которому тест отличает «проверка реально произошла» от «промт про неё
  написан»: отсутствие следа в конкретном прогоне — сам по себе наблюдаемый дефект, не только
  провал сценария на несовпадении.

**Edge cases / boundary conditions:**
- Обработчик прогона падает/зависает до отправки финального отчёта — шаг 5.5 не вызывает
  `project-curator` вовсе для этого прогона, даже если другие обработчики отчитались об id
  (Boundaries, «Negative» ADR-026). Известное ограничение, а не сценарий с заданным исходом —
  зафиксировать фактом теста, не додумывать таймаут.
- Два прогона навыка запущены до завершения первого (пользователь вызвал навык повторно,
  пока фоновые обработчики первого ещё работают) — id обработчиков не пересекаются между
  прогонами (шаг 3 каждого прогона отбирает из `new`, уже отобранные не предлагаются повторно
  при обычной работе `ktalk sync`/`dashboard`), но проверить, что шаг 5.5 не смешивает
  накопления двух прогонов.
- Большой транскрипт: дозагрузка chunk 2..N действительно откладывается до подтверждения
  личности на chunk 0, а не бежит впереди него — мутационный тест (испортить участников
  chunk 0, убедиться, что запрос chunk 2 не происходит до повтора).
- Транзиентное несовпадение, устранённое повтором, — попадает в «Требует внимания», не
  пропадает бесследно (Data flow, п.4).
- `save_location: archive_only` при непустом `Проекты затронуты:` — `project-curator`
  получает путь к транскрипту вместо протокола; собственный контракт чтения — вне этой
  статьи, но факт, что оркестратор передаёт именно этот путь, — проверяемый.

**Test-pyramid recommendation:**

| Группа сценариев | Уровень | Обоснование |
|---|---|---|
| A processor agent that touched a project does not call project-curator | integration | требует реального прогона `ktalk-processor` с фиктивным `tools:` без инструмента вызова агента и проверки текста отчёта, не только логики одной функции |
| The orchestrator invokes project-curator once / project-curator is not installed | integration | охватывает границу между двумя агентами и асинхронные task-уведомления одной сессии оркестратора; стаб `project-curator` (резолвится/не резолвится) по образцу стаба `ktalk`/`uv` в `scripts/test-onboard.sh` |
| A matching transcript proceeds without an extra step / retried once | integration | стаб `ktalk get-transcript`, управляемый по номеру вызова (1-й вызов — чужие данные, 2-й — свои); проверка числа вызовов CLI, не только финального результата |
| A mismatch that survives the retry is a hard stop | integration | тот же стаб на оба вызова несовпадающий; проверка отсутствия записанного файла в архиве, вызова `mark-partial` вместо `mark-done`, содержания отчёта |
