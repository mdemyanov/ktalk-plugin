# Переезд требований плагина: раскладка, наименование, брифы

**ADR:** `content/00-project/adr/ADR-023-plugin-requirements-relocation.md`

## Context

Четыре требования, описывающие плагин `ktalk` предметно, физически лежат в дереве пакета
`ktalk-mcp` (BA-001 `ktalk-plugin-56l.9`). Эта статья фиксирует, куда они переезжают, как
называются, что переносится в capability-спеку, а что остаётся у требования, и что делать с
тремя пересечениями с уже принятой `cli-only-boundary` (ADR-022) — решения см. ADR-023 Д2/Д3,
здесь — их разворот и брифы.

**Судьба пути-источника (ADR-023 Д1).** Переезжает содержание, не путь: на всех четырёх старых
путях в дереве пакета остаётся файл-указатель (тип «Прочее», статус Approved) с адресом нового
файла и причиной — 34 ссылки в 22 закрытых документах пакета (пять ADR, `roadmap.md`, четыре
companion-спеки, три security-review, отчёты QA/A-B, три заметки Dev) цитируют требование
исторически и не переживут удаление источника без искажения записи «решено против чего-то,
чего нет». Указатели ведёт владелец/DEV-002 в дереве пакета — не эта задача и не эта статья.

## Naming decision

Три из четырёх источников несут префикс `ktalk-plugin-`, один — `ktalk-prompt-`: оба избыточны
в репозитории, который целиком и есть плагин `ktalk`. Новое имя — `<дата>-<тема>.md`, тот же
шаблон, что уже дали `2026-08-26-agreements-reconciliation.md`, `2026-08-29-prompt-language-boundary.md`,
`2026-08-31-cli-only-boundary.md`. Тема — не копия имени capability дословно (один файл
`meetings-prompt-surface` несёт две capability), а узнаваемый слаг предмета файла.

## Layout decision

Три уже принятых требования этого дерева устроены парой: файл требования на верхнем уровне
`content/30-requirements/<slug>.md` плюс каталог-спутник `content/30-requirements/<slug>/` с
`_index.md` и `at-design.md` — тест-дизайном QA-author, заведённым **после** требования и ADR,
не одновременно с ними. Раскладка воспроизводится для всех четырёх переселенцев один в один:
верхнеуровневый файл заводит DEV-001, каталог-спутник — будущая задача QA-author, когда придёт
её очередь; SA и DEV-001 каталог не создают.

## Required properties

Свойства источников — только `Тип контента`, `Фаза`, `Статус`; `content/.doc-root.yaml` этого
дерева требует четвёртое — `Audience` (C4/C5). DEV-001 обязан добавить `Audience: [Internal]`
в шапку каждого из четырёх файлов при переезде — без него `validate-content.py` даёт error на
первом же прогоне после переноса.

## Три пересечения с `cli-only-boundary` — разворот решения

### 1. Онбординг vs пин версии (ADR-023 Д2) — раздельно, `cli-only-boundary` первичен

`plugin-onboarding-sanctioned-install` не переопределяет, что значит «совместимая версия» —
эта семантика (точный пин, симметричная несовместимость, команда ремонта с версией) уже
Accepted-де-факто поведением ADR-022 и реализована `scripts/ktalk-onboard.sh`
(`pin_version()`, `remedy_cmd_text()` — обе строят пин из `compat.json`, `==%s`, без порога).
Будущая спека онбординга описывает сценарии обнаружения/установки (FR-26…FR-31 исходника) и на
шаге «версия не совпадает» **ссылается** на сценарии `cli-only-boundary` («Installed version
differs from the pin», «The remedy command names the exact version»), а не копирует их текст.

Конкретная находка, которую спека обязана учесть, а не унаследовать буквально: AC исходника
устарел относительно уже поставленного поведения —

| Место в исходнике | Текст AC (устарел) | Факт реализации |
|---|---|---|
| `ktalk-plugin-onboarding.md:77` (FR-27 AC1) | команда установки «дословно… `uv tool install ktalk-mcp`» — без версии | `remedy_cmd_text()` всегда печатает `uv tool install ktalk-mcp==<пин>` |
| `ktalk-plugin-onboarding.md:66-70`, `:146-155` (FR-26 AC3, FR-31) | «версия ниже минимально совместимой», «не ниже минимальной» — язык порога | `pin_version()`/ADR-022 Д3 — точное равенство, отклонение в любую сторону |

Требование как исторический документ не правится (не роль SA и не роль этой статьи); спека —
машинно-проверяемый контракт по факту, поэтому не наследует эти две фразы дословно.

Отдельно подтверждается, не пересматривается: FR-30 AC2 исходника («обновление существующей
версии требует отдельной санкции») совпадает по существу с ADR-022 Д2 (санкция на обновление
остаётся отдельной от установки) — разной аргументацией (идемпотентность онбординга у BA,
разница создания/мутации машинного состояния у SA), один и тот же вывод. Конфликта нет,
дублирования в спеке тоже не нужно — оба текста говорят одно, спека формулирует один раз.

### 2. NFR-20 vs «no MCP interface surface» (ADR-023 Д3) — сливается, обобщённо

`check-plugin-composition.sh` уже сегодня несёт два независимых узла: узкий (`:59-61`, реализует
NFR-20 — grep пяти MCP-имён операций встреч в промт-тексте) и общий декларативный
(`check_no_mcp_server`, `:85-130`, реализует сценарий `cli-only-boundary` «No MCP server is
declared»). Оба зелёные, оба реализованы. Обобщение, которое поглощает узкий случай: текст
промт-слоя (skill/agent/command) не описывает MCP-путь к контуру ни для какой операции, не
только для встреч — то же свойство, что уже проверил тест 46 `cli-only-boundary`
(`content/30-requirements/2026-08-31-cli-only-boundary/at-design.md`, находка 6): устаревший
текст `SKILL.md`/`ktalk-processor.md`, описывающий MCP как рабочий канал, хотя декларация уже
снята — дефект, не пойманный узким списком имён.

Спека `meetings-prompt-surface-reads` не заводит сценарий «нет MCP-имени» — свойство наследуется
от `cli-only-boundary`. Задача, пишущая спеки, обязана расширить вторую Requirement
`cli-only-boundary/spec.md` («The plugin declares no MCP interface surface») текстом, покрывающим
не только манифест, но и промт-текст любого skill/agent/command — редактирование спеки, не ADR
(ADR-022 не пересматривается, supersede-процедура не применяется).

### 3. Прочее пересечение — не найдено сверх названного BA

Прочитаны все FR/NFR `ktalk-plugin-analysis-calibration.md` и `ktalk-prompt-defect-channel.md`
на предмет слов MCP/CLI — совпадений нет: обе capability вне территории `cli-only-boundary`.
Единственная дополнительная стилистическая находка — `ktalk-plugin-onboarding.md:46-48` цитирует
«ADR-012 §2а: MCP вторичен» как источник приоритета CLI; формулировка устарела тем же образом,
что и найденное в п.1 (MCP не «вторичен», а не объявлен вовсе) — спеке следует цитировать
ADR-022, не ADR-012 §2а, для этого утверждения.

## NFR Mapping

- Обязательные properties документарного контура (`content/.doc-root.yaml`) → раздел «Required
  properties» выше: DEV-001 добавляет `Audience` при переезде.
- Пара дрейфа (design трёх домов §5, C15 `validate-content.py`) → строка `**Capability:**`
  добавляется в шапку каждого переехавшего файла ОДНОВРЕМЕННО с переездом, не раньше — порядок
  ниже.
- Отсутствие дубля контракта между `cli-only-boundary` и двумя новыми capability → раздел «Три
  пересечения» выше: ссылка, не копия текста.

## Brief for Dev (DEV-001)

**Архитектура:** этот файл. **Требование:** ADR-023. **Фаза:** Pilot.

**Порядок, обязательный:**
1. Дождаться пяти `openspec/specs/<capability>/spec.md` (следующая задача после SA-002).
2. Переместить четыре файла по «Migration map» под новыми именами, добавить `Audience: [Internal]`.
3. В той же правке вписать строку(и) `**Capability:**` — для `2026-08-18-meetings-prompt-surface.md`
   две через запятую (`meetings-prompt-surface-reads`, `meeting-write-sanction-workflow`).
4. Обновить `content/30-requirements/_index.md` четырьмя новыми пунктами.
5. Прогнать `bash scripts/check.sh --fast` — обязан остаться зелёным.

Шаги 2-3 — одна правка, не две: голое перемещение без строки `**Capability:**` красит C15
немедленно. В дереве пакета тот же гейт молчит по независимой причине — путь-источник после
переезда несёт тип «Прочее», не «Требование» (ADR-023 Д1), и `check_capability_link` применяется
только ко второму типу; это не зависит от того, готов ли в пакете openspec-каркас (SA-001,
отдельная задача, к моменту этой правки уже завершена — 8 capability под `openspec/specs/` в
дереве пакета).

**Acceptance scenarios:** отсутствуют до появления пяти спек — сценарии называет задача,
пишущая `openspec/specs/*/spec.md`, следующая после этой.

## Contract with QA-author

Полный список сценариев недоступен на этом шаге — все пять `openspec/specs/*/spec.md` пишет
задача после SA-002. Контракт ниже — контекст для той задачи и для теста, который придёт
следующим после неё.

**Архитектурный контекст:**
- Компоненты: `content/30-requirements/*` (четыре мигрирующих файла), `openspec/specs/*/spec.md`
  (пять новых capability), `openspec/specs/cli-only-boundary/spec.md` (расширяется, не создаётся
  заново), `scripts/validate-content.py` (C15 — гейт пары дрейфа), `scripts/check-plugin-composition.sh`
  (уже реализует и узкий, и общий MCP-check).
- Границы доверия: SA не пишет спеки и не трогает существующий текст ADR-022; спека-автор не
  переносит файлы и не правит `**Capability:**` за Dev.

**Edge cases / граничные условия из дизайна:**
- Порядок «специи → перенос+Capability одной правкой» — нарушение порядка красит C15 сразу же
  (не отложенный риск, наблюдаемый на первом прогоне `check.sh --fast`).
- Расширение `cli-only-boundary/spec.md` второй Requirement — риск случайно продублировать
  сценарий вместо обобщения существующего; проверка — сравнение текста Requirement до/после
  правки, не только наличие новой строки.
- AC-язык источника онбординга (`ktalk-plugin-onboarding.md:77`, `:146-155`) не должен попасть в
  спеку дословно — см. таблицу в разделе «Три пересечения», п.1.

**Test-pyramid recommendation:**
| Группа | Уровень | Обоснование |
|---|---|---|
| Наличие `**Capability:**` и резолвимость пути (C15) | unit/статический | уже проверяет `validate-content.py`, регрессии на новых файлах — тот же гейт |
| Обобщённая проверка «нет MCP в промт-тексте» после расширения `cli-only-boundary` | integration | требует прогона `check-plugin-composition.sh` на реальном дереве, не изолированной функции |
| Совпадение AC онбординга с фактическим поведением `ktalk-onboard.sh` (пин, не порог) | integration | уже покрыто существующей сьютой `test-onboard.sh` cli-only-boundary — новая спека не должна плодить второй тест того же факта |
