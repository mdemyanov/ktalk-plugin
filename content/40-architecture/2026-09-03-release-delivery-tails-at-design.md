# AT-design: хвосты релиза 1.9.0 (QA-001)

**Требование:** [2026-09-03-release-delivery-tails.md](../30-requirements/2026-09-03-release-delivery-tails.md)
**Capability:** `openspec/specs/release-delivery-tails/spec.md` (9 `### Requirement:`, 16 `#### Scenario:`)
**Companion-статьи SA:**
[2026-09-03-release-delivery-tails.md](2026-09-03-release-delivery-tails.md) (ADR-025,
поставочная поверхность), [2026-09-03-orchestrator-processor-boundary.md](2026-09-03-orchestrator-processor-boundary.md)
(ADR-026, граница оркестратора/обработчика)

Стаб: [scripts/test-release-delivery-tails.sh](../../scripts/test-release-delivery-tails.sh)
(`bash scripts/test-release-delivery-tails.sh`).

## Почему один стаб, а не два (по числу ADR)

Оба ADR закрывают ОДНО требование и ОДНУ capability-спеку (`release-delivery-tails`) — деление
на два файла воспроизводило бы границу SA-документов, не границу теста: QA-runner прогоняет
приёмку по требованию целиком, не по ADR. Прецедент дерева расходится по обоим направлениям
(`test-plugin-requirements-relocation.sh` — одна сьюта на волну из пяти capability;
`test-agreements-reconciliation.sh` — одна сьюта на единственное требование) — правило «одна
сьюта на волну», не «одна сьюта на ADR» или «россыпь по сценарию». Внутри файла AC-1…AC-16 идут
подряд в порядке появления `#### Scenario:` в spec.md, с явным разделителем-заголовком на
каждый — при необходимости QA-runner может прогнать секцию отдельно (`grep -A20 'AC-9 —'`),
второй файл ради этого не нужен.

## Уровень пирамиды и почему прикладной сьюты для ADR-026 нет

Требование живёт в дереве тонкой обёртки (ADR-012): прикладного кода, который вызывал бы
`get-transcript`/`project-curator` из этого репозитория, нет — оба вызова делает LLM-агент,
следуя промту. Сценарии `A processor agent…`/`The orchestrator invokes…`/`A matching
transcript…`/`A mismatched transcript…`/`A mismatch that survives…` (AC-8…AC-13) поэтому
проверяются ДВУМЯ разными приёмами, а не одним:

1. **Автоматизируемая часть (этот стаб).** Присутствие и форма инструкции в промт-файле —
   правильный шаг существует, между правильными соседними шагами, называет правильные
   литералы (`project-curator`, `mark-partial`, «ровно один»/«не более»). Тот же принцип, что
   `scripts/test-agreements-reconciliation.sh` уже документирует дословно для похожего случая
   (шаг 5.5 сверки договорённостей): «здесь нет прикладного кода… можно проверить наличие и
   форму инструкций, а не факт, что модель им следует».
2. **Неавтоматизируемая часть (не этот стаб).** Что РЕАЛЬНО делает LLM-агент, получив стаб
   `get-transcript`, управляемый по номеру вызова (1-й вызов — чужие данные, 2-й — свои), —
   companion ADR-026 предлагает именно такой стаб (по образцу `stub()` из
   `scripts/test-onboard.sh`), но им управляет не bash-скрипт, а реальный вызов Claude-агента:
   это не то, что можно исполнить простым `bash scripts/test_x.sh` без интерактивной сессии.
   Носитель — QA-runner / ручной прогон живого навыка поверх такого CLI-стаба, не текст этого
   документа. Названо явно в «Не покрывается» ниже, по одному разу на сценарий, а не тихо
   опущено.

Из девяти требований spec.md семь (`### Requirement:` формы `A release tag…` … `The
GO-criterion gates…`) проверяются статически или живым вызовом `claude plugin`/`check.sh` —
для них стаб — полноценный, поведенческий (наблюдаемый выход инструмента), не суррогат текста.

## Boundary cases

- AC-2: `claude plugin validate .` возвращает **exit 0 даже с предупреждением** (замерено
  живьём в этой сессии) — граница между «предупреждение» и «ошибка» здесь не про код
  возврата: стаб обязан читать STDOUT, а не полагаться на код (см. Error cases, masked
  failure).
- AC-4/AC-5: три файла переезжают ОДНИМ раундом Dev, вместе с восемью ссылками того же файла
  и пятью внешними цитатами (companion, таблица «перенос agents/references/») — переезд без
  правки ссылок и переезд ссылок без физического переноса файлов — два РАЗНЫХ, оба красных,
  промежуточных состояния; стаб различает их (AC-4 проверяет расположение файла, AC-5 —
  форму и резолвируемость ссылки) намеренно раздельно, а не одной комбинированной проверкой.
- AC-7: assert на README ловит ровно один известный литерал («MCP-сервер»); переформулировка
  того же ложного утверждения другими словами (например, «MCP-инструмент», «MCP-клиент») не
  поймана статическим grep — остаётся ручным ревью текста против факта `ktalk --help`
  (тот же класс ограничения, что REL-7b в `test-plugin-requirements-relocation.sh`, «семантическая
  достаточность остаётся ручным ревью»).
- AC-11…AC-13: правило сравнения участников (частичное совпадение, транслитерация,
  анонимизированные метки спикеров) — companion ADR-026, Boundaries, называет это открытым
  частным случаем: «Dev фиксирует конкретное правило разбора, QA-author фиксирует, что
  реализовано, фактом теста». Этот стаб фиксирует только СТРУКТУРНОЕ наличие правила (шаг 2b
  существует, различает match/retry/hard-stop) — точное правило сравнения (например, порог
  совпадения по количеству имён) не специфицировано ни требованием, ни спекой и не может быть
  предметом стаба, написанного до Dev.
- AC-13: догрузка chunk 2..N для большого транскрипта откладывается до подтверждения на
  chunk 0 — companion сама называет это мутационным тестом («испортить участников chunk 0,
  убедиться, что запрос chunk 2 не происходит до повтора»), то есть поведенческим, не
  текстовым — вне этого стаба, см. «Не покрывается».

## Error cases (два обязательных класса)

**Malformed/mistyped input** (искажённый, не отсутствующий идентификатор — целевой
«пользователь» здесь чаще Dev/владелец плагина, набирающий путь/литерал/идентификатор
маркетплейса, не оператор Толка):

- AC-2 (пустая строка вместо отсутствующего ключа): проверка `top and top != plugin_desc` в
  стабе различает «ключа нет» и «ключ есть, значение `""`» — оба дают `0`, ни один не
  засчитывается как исправление.
- AC-3 (мистайп идентификатора маркетплейса/плагина — точный класс «URL-сегмент, не просто
  отсутствующее значение»): `assert_contains` требует ТОЧНОГО совпадения `ktalk-plugins` и
  `ktalk@ktalk-plugins` — правдоподобный, но неверный вариант (`ktalk-plugin` в единственном
  числе, `ktalk/ktalk-plugins` другим разделителем) не проходит проверку.
- AC-4/AC-5 (опечатка в новом пути): `references/ktalk-proccessor/` (лишняя `c`) или
  `reference/ktalk-processor/` (без `s`) не совпадают с точным путём, который проверяет
  AC-4b/AC-5a/c — красный, а не ложный зелёный на «похожем» пути.
- AC-6 (мутация `compat.json` на синтетическое имя — предписано companion дословно):
  `zzz-synthetic-pkg-qa001` — эта же техника закрывает и «естественный» мистайп имени
  зависимости, не только специально сконструированный случай.
- AC-8…AC-10, AC-11…AC-13 (опечатка в имени агента/литерале): `project-curator` с
  подчёркиванием, `mark_partial` вместо `mark-partial` — `assert_contains` по точному
  литералу не находит опечатанный вариант, красный.
- AC-15 (мистайп значения перечня): отдельный scratch-тест AC-15e — `.nauta-gates.yaml` во
  временном каталоге с `profile: bogus-value` — `check-branch-discipline.py` обязан вернуть
  код 2 (громкая ошибка), не молчаливо принять как «single» или «undetermined».
- AC-1: класс применим (владелец плагина мог набрать `git tag v1.9.0` руками вместо
  `claude plugin tag`), но **не закрыт этим стабом** — рукописный тег не проходит ни через
  один код этого дерева, поймать мистайп мог бы только сам релизный рансбук текстом
  инструкции (Д1), не автоматический гейт; называю явно, не молчу.
- AC-16: класс не применим — сценарий сравнивает две версии инструментария, пользовательского
  идентификатора/URL-сегмента здесь нет. N/A.

**Masked failure** (тихое принятие/редирект/фолбэк вместо наблюдаемой ошибки):

- AC-2: `claude plugin validate .` возвращает **exit 0 даже при найденном предупреждении**
  (замерено живьём) — стаб, проверяющий только код возврата, был бы тем самым тихим «ок»;
  AC-2b читает STDOUT намеренно, не код.
- AC-3: центральный мотивирующий дефект всей волны — `claude plugin marketplace update`
  завершается успехом (exit 0), но НЕ переводит установленную копию на новую версию;
  оператор, буквально выполнивший документированный шаг, остаётся на старой версии без
  единого сигнала. AC-3a-d проверяют ПОЛНОТУ текста именно поэтому — неполный текст и есть
  форма этой маскировки на уровне документации.
- AC-4: ADR-025 явно называет и отклоняет побег через маскировку — «оставить файлы на месте и
  добавить им фронтматтер» убрал бы предупреждение `claude plugin tag --dry-run` («No
  frontmatter block found»), но НЕ снял бы регистрацию файла агентом (регистрация решается
  расположением, не фронтматтером). AC-4b проверяет РАСПОЛОЖЕНИЕ на диске, не только текст
  предупреждения инструмента — это и есть защита от этой конкретной маскировки.
- AC-5: сломанная ссылка не даёт ошибки НИ на одном автоматическом прогоне этого дерева —
  `Read` инструмента вернёт ошибку только в момент, когда реальный агент попытается её
  прочитать в живой сессии, то есть постфактум. AC-5c (fs-резолвируемость) — единственный
  способ поймать это ДО первого живого использования, не после.
- AC-6: замена retired-литерала на другой хардкод-литерал (`ktalk-cli`) читалась бы как
  починка при поверхностном ревью — companion называет это дословно тем же классом регресса.
  AC-6a-masked/AC-6b-masked закрывают этот путь отдельной проверкой (см. «Сегодня»: vacuous
  green до правки Dev, содержательна после).
- AC-8/AC-9: **тихое исчезновение всей функции** — если Dev уберёт вызов из `ktalk-processor.md`
  (закрывая AC-8), но не добавит шаг 5.5 в `SKILL.md` (не закрывая AC-9), делегирование
  тихо пропадает целиком, а не переезжает. Два раздельных AC (не один комбинированный)
  — намеренная защита именно от этого случая: AC-8 зелёный сам по себе ничего не доказывает
  без AC-9.
- AC-11…AC-13: **мотивирующий инцидент всего ADR-026** — `get-transcript` вернул чужой
  транскрипт с кодом 0 и валидным JSON, ничто в ответе не отличало подмену (issue #5). Вся
  цепочка AC-11→13 существует, чтобы превратить эту тихую подмену в наблюдаемую остановку;
  AC-13 (mark-partial без `--transcript`, отчёт без «✅ Встреча обработана», явное указание
  участников) — прямая проверка того, что остановка НАБЛЮДАЕМА, не просто «агент что-то не
  сохранил молча».
- AC-14: гейт может быть УПОМЯНУТ в выводе `check.sh` (декларативно, YAML прочитан), но не
  ИСПОЛНЕН реально при несовпадении пути/расширения — AC-14f/g/h проверяют маркер `▶
  scripts/<путь>` реального исполнения (`run_check`, `scripts/check.sh:445`), не только факт
  строки `projectGates: configured (N позиций)`.
- AC-1: релизный тег мог бы молча продолжать создаваться командой `git tag` (шесть
  исторических тегов — живое тому свидетельство) без единого сообщения об ошибке — тег
  СОЗДАЁТСЯ, просто не в той форме. Не закрыт стабом (см. Error cases, malformed input, тот же
  пункт) — тот же названный, не молчаливый пробел.

## Не покрывается (out of scope этого стаба)

- **AC-3 (поведенческая часть).** «Установленная копия действительно перешла на новую
  версию» — состояние `~/.claude/plugins/installed_plugins.json` вне дерева репозитория.
  Носитель: шаг релизного рансбука DevOps (замер до/после команды, по образцу живого замера
  companion ADR-025 в этой же сессии), не тест кода.
- **AC-8…AC-13, поведенческая часть.** Реально ли LLM-агент следует записанной инструкции
  (реально ли не вызывает `project-curator`, реально ли делает РОВНО один повтор, реально ли
  останавливается) — не автоматизируется bash-стабом без прикладного кода (ADR-012). Носитель
  — QA-runner / ручной прогон живого навыка с CLI-стабом `get-transcript`, управляемым по
  номеру вызова (образец — `stub()` в `scripts/test-onboard.sh`), и стабом
  резолвинга/нерезолвинга `project-curator`; сам стаб CLI — задача этой же следующей волны
  QA-runner, не заведён здесь.
- **AC-13, догрузка chunk 2..N после подтверждения.** Требует живого мутационного прогона
  (испорченные участники chunk 0 → проверка, что запрос chunk 2 не происходит до повтора) —
  тот же носитель, что предыдущий пункт.
- **AC-15, различение single/team на одной паре имён веток (companion, Edge cases).**
  Измерено: `_guard_branch_names()` в доставленном `check-branch-discipline.py` (nauta 0.28.2,
  заморожен по sha256) не читает значение `profile` вовсе — `grep team
  scripts/check-branch-discipline.py` находит его только в перечне `PROFILES` и в двух
  текстах сообщений об ошибке, не в логике сторожа. Не закрываемо Dev этого раунда (чужая
  доставка). Носитель: бэклог-пункт SA/DevOps к следующему `/nauta:sync-scripts`.
- **AC-16 целиком.** Сравнение версии базиса с установленным инструментарием — состояние
  машины оператора (`~/.claude/plugins/cache/nauta/nauta`), не воспроизводимо в CI. Носитель:
  ручная процедурная проверка DevOps при каждом `/nauta:sync-scripts` (ADR-025 companion, Д7:
  «вне автоматизируемого контракта этого дерева»); стаб печатает факт информационно (замер
  этой сессии: базис `0.27.0`, установлено `0.28.2`), но не считает его в PASS/FAIL.
- **Регистрация новой сьюты в `projectGates`.** Не эта задача — брифу PM явно: «сам этот блок
  заводит Dev, не ты». Названо Dev-у как требование ниже.

## Регистрация в `projectGates` (требование к Dev, не выполнено этим стабом)

Эта сьюта — с живыми подпроцессами (`claude`, дважды `check.sh`, дважды scratch-git) — по
профилю ближе к `test-onboard.sh` (замер: ~23 с общего времени прогона), чем к дешёвым
`check-plugin-composition.sh`/`check-prompt-language.sh` (~0,5 с, ADR-025 companion). Если Dev
регистрирует её в `.nauta-gates.yaml`, место — `projectGates.full`, не `.fast`, тем же
основанием, каким ADR-025 Д7 уже развёл `test-onboard.sh` и два дешёвых гейта. Регистрация не
обязательна для приёмки ЭТОГО требования (никакой `#### Scenario:` спеки не требует
существования ЭТОЙ сьюты как факта) — но если Dev её всё же подключает, профиль `full:`, не
`fast:`.
