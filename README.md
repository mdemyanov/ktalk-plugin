# ktalk — Claude Code plugin

Навыки и агенты для обработки записей встреч Контур.Толк (KTalk): реестр
обработки, двухпроходный анализ и протоколирование встречи, оценка качества
анализа, чтение транскриптов/саммари.

Плагин — тонкая обёртка (ADR-012): код и обращение к API живут в отдельно
устанавливаемом пакете `ktalk-mcp`, здесь — только промты и объявление
MCP-сервера, без секретов и без встроенных путей конкретного проекта.

## Установка плагина

Marketplace — git-источник, репозиторий этого плагина:

```
/plugin marketplace add https://doc-hub.gitlab.yandexcloud.net/tools-ai/ktalk-plugin.git
/plugin install ktalk@ktalk-plugins
```

Обновление — `/plugin marketplace update ktalk-plugins`. Плагин версионируется
отдельно от пакета `ktalk-mcp` (ADR-012 §4): совместимость версий не
навязывается манифестом, предусловие ниже проверяется вручную.

## Предусловие: пакет `ktalk-mcp` в PATH

Навыки вызывают контур через CLI `ktalk` (ADR-012 §2а), MCP-сервер `ktalk`
(объявлен в `.mcp.json` этого плагина) — вторичный путь для чтения контента.
Без установленного пакета не работает ни один сценарий.

```
uv tool install ktalk-mcp
which ktalk-mcp
uv tool list | grep ktalk-mcp
ktalk --help
```

Плагин обнаруживает отсутствие или устаревание пакета сам (ADR-014) и показывает команду
установки. Выполнить установку за вас он может только по явной санкции:

    bash <путь к плагину>/scripts/ktalk-onboard.sh check             # состояние пакета: PATH, uv, версия
    bash <путь к плагину>/scripts/ktalk-onboard.sh grant install     # выдать санкцию (только в терминале)
    bash <путь к плагину>/scripts/ktalk-onboard.sh install           # установить/обновить по санкции
    bash <путь к плагину>/scripts/ktalk-onboard.sh status            # какие санкции выданы
    bash <путь к плагину>/scripts/ktalk-onboard.sh revoke install    # отозвать

После `install` полезно повторить `check`: `install` возвращает 0 только если после запуска
менеджера версия действительно не ниже минимальной, иначе 11.

Санкция хранится в `${XDG_CONFIG_HOME:-$HOME/.config}/ktalk/onboarding.toml` (права 0600) и
действует на всю машину. Санкция на установку не разрешает обновление — для него нужна отдельная
`grant update`. Нет файла или ключа — санкции нет.

Минимально совместимая версия пакета объявлена в `compat.json` этого плагина. Версия ниже —
предупреждение, не блокировка.

## Конфигурация проекта-хозяина: `.ktalk.toml`

Раскладка каталогов и маршрутов конкретного проекта (архив транскриптов,
каталог профилей участников, каталог активных проектов, шаблоны путей
протоколов) не зашита в промты плагина — она объявляется файлом
`.ktalk.toml` в корне проекта-хозяина (SA-003, формат и алгоритм discovery —
`content/40-architecture/ktalk-plugin-spec.md` в репозитории пакета
`ktalk-mcp`).

Пример (пути — плейсхолдеры, подставить свои):

```toml
[registry]
db_path = "PATH/TO/TRANSCRIPTS_ARCHIVE/.registry.db"

[directories]
people = "PATH/TO/PEOPLE_PROFILES"
projects_active = "PATH/TO/ACTIVE_PROJECTS"

[routing]
committee = "PATH/TO/MEETINGS/committees/{id}/{date}.md"
standup = "PATH/TO/MEETINGS/standups/{date}.md"
transcript_archive = "PATH/TO/TRANSCRIPTS_ARCHIVE/{YYYY}/{date}_{type}_{title}.md"
eval_report = "PATH/TO/TRANSCRIPTS_ARCHIVE/eval/reports/{date}_{title}.md"

[integrations]
qmd = false
```

Все секции опциональны. Отсутствующий ключ — не ошибка: шаг, которому он
нужен, явно помечает результат как «маршрут/каталог не объявлен» и не
угадывает путь (контракт деградации, FR-21/FR-24). Секретов
(`KTALK_SESSION_TOKEN`, `KTALK_PERSONAL_API_KEY`, `KTALK_BASE_URL`) в
`.ktalk.toml` быть не должно — их место, как и раньше, окружение процесса
или `.mcp.json`/`.env` проекта-хозяина (FR-25).

Проверить, что конфигурация читается и резолвится верно:

```
ktalk config show --json
```

## Где живут данные

Реестр обработки и сырые транскрипты — данные пакета, не плагина
(ADR-013). По умолчанию — централизованное хранилище
`${XDG_DATA_HOME:-$HOME/.local/share}/ktalk` (права `0700`/`0600`, вне
каталогов, которые обычно попадают под облачную синхронизацию). Если
`.ktalk.toml` объявляет `registry.db_path`, он побеждает машинный дефолт
(приоритет: `--db` > `KTALK_REGISTRY_DB` > `.ktalk.toml` > машинный
дефолт).

Протоколы встреч, зеркало реестра (`registry.md`) и профили участников —
артефакты проекта-хозяина, в централизованное хранилище не переносятся
(NFR-16).

## Миграция существующего реестра

Перенос реестра из сегодняшнего расположения (например, из архива
транскриптов внутри проекта) в централизованное хранилище — не побочный
эффект установки или первого запуска плагина, а отдельная явная команда
(NFR-12):

```
ktalk migrate-to-central-store PATH/TO/EXISTING/.registry.db
```

До вызова этой команды реестр остаётся там, где лежит сегодня — плагин не
переносит файл самостоятельно.

## Навыки и агенты

- `skills/ktalk-registry/` — реестр обработки записей (sync, дедуп,
  экспорт), маршрутизация протоколов по `.ktalk.toml`.
- `skills/ktalk-eval/` — оценка качества анализа встречи.
- `agents/ktalk-processor.md` — двухпроходный анализ встречи и
  протоколирование.
- `agents/ktalk-evaluator.md` — оценка готового протокола.
- `commands/ktalk-registry.md` — точка входа в реестр из команды.

Интеграция с `qmd` (сопоставление участника с профилем через сторонний
MCP) — опциональная, активируется только если `qmd` уже используется в
проекте-хозяине (`.ktalk.toml`, `[integrations] qmd = true`) и фактически
доступен в сессии; при отсутствии шаг не падает, а помечает результат как
недоступный (ADR-012 §5).

## Совместимость с проектом, где плагин уже работал как копия в `.claude/`

Если в проекте ранее использовались одноимённые агенты/навыки как файлы
`.claude/agents/`, `.claude/skills/`, `.claude/commands/` — они перекрывают
плагинного агента/навык молча (механизм платформы, не специфика ktalk).
Переключение на плагин — двухшаговая процедура: установить плагин, затем
явно удалить файлы-копии отдельным коммитом. Автоматически это не
происходит (runbook OPS-001).
