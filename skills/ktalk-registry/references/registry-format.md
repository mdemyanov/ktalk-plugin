# Модель данных реестра ktalk

> **Источник истины — SQLite.** Markdown-зеркало реестра больше **не** ведётся
> вручную и **не** парсится как источник. Оно генерируется командой
> `ktalk export` (read-only).

## Операционное хранилище: SQLite

### Расположение

Путь резолвится пакетом `ktalk-mcp` приоритетом: флаг `--db PATH` >
env `KTALK_REGISTRY_DB` > путь из `.ktalk.toml` проекта-хозяина
(`registry.db_path`, `ktalk config show --json`) > машинный дефолт.
Этот навык не хранит и не предполагает конкретный путь.

### Схема

```sql
recordings(
  recording_id PRIMARY KEY, name, date,            -- date = YYYY-MM-DD (дата записи)
  duration_min, status,                            -- new|processing|done|skipped|partial
  meeting_type,                                    -- 1-1|committee|session|standup|status|other
  transcript_path, protocol_path, processed_at,
  created_at, updated_at, raw_json
)
participants(
  recording_id REFERENCES recordings ON DELETE CASCADE,
  ktalk_id, name, vault_id,                         -- vault_id nullable
  PRIMARY KEY (recording_id, ktalk_id)
)
meta(key PRIMARY KEY, value)                        -- last_synced, sync_count, schema_version
```

WAL + `busy_timeout=5000` + транзакция на операцию → параллельные фоновые
`ktalk mark-*` безопасны.

## Поверхность CLI `ktalk`

Все команды поддерживают `--json` (валидный JSON в stdout; ошибки — stderr + ненулевой код).

| Команда | Назначение |
|---|---|
| `ktalk config show` | Раскладка проекта-хозяина (реестр, каталоги, маршруты, интеграции) |
| `ktalk sync [--days 7]` | Загрузить записи из ktalk, upsert новых (`new`), экспирация, дашборд. Идемпотентно. |
| `ktalk dashboard` | Новые записи + статистика по статусам. |
| `ktalk list [--status S]` | Список записей с фильтром. |
| `ktalk show <id>` | Детали записи + участники (ktalk_id, vault_id). |
| `ktalk mark-processing <id>` | → `processing` (агент в начале). |
| `ktalk mark-done <id> --transcript P --protocol P [--type T]` | → `done`, пути + `processed_at`. |
| `ktalk mark-partial <id> [--transcript P] [--protocol P]` | → `partial`. |
| `ktalk mark-skipped <id>` | → `skipped` вручную. |
| `ktalk set-vault-id <id> <ktalk_id> <vault_id>` | Привязка профиля к участнику. |
| `ktalk export [--out PATH] [--full]` | Регенерация markdown-зеркала. |
| `ktalk migrate <vault> [--dry-run]` | Разовый импорт из старых markdown-реестров. |
| `ktalk get-transcript <id> [--chunk N] [--chunk-size N]` | Транскрипт записи (чтение контента). |
| `ktalk get-summary <id>` | Саммари записи (чтение контента). |

## Дедупликация и экспирация (делает CLI)

- Уникальный ключ — `recording_id`; повторный `sync` не добавляет дубликаты
  (upsert обновляет контент, но **не** сбрасывает `status`/пути).
- Экспирация: записи `new` строго старше N дней (по умолчанию 7) → `skipped`
  при `sync`, проставляется `processed_at`.

## Статусы

| Статус | Значение | Переход |
|--------|----------|---------|
| `new` | Обнаружена, не обработана | → `processing`/`done`/`skipped` |
| `processing` | Взята агентом в работу | → `done`/`partial` |
| `done` | Транскрипт сохранён, обновления записаны | Финальный |
| `skipped` | Пропущена (старше N дней или вручную) | Финальный |
| `partial` | Частично обработана | → `done` при доработке |

Флаг «нет профиля» — это свойство участника (пустой `vault_id`), а **не**
отдельный статус записи.

## Markdown-зеркало (генерируется `ktalk export`)

`ktalk export` перезаписывает markdown-зеркало реестра проекта-хозяина с
шапкой-предупреждением `<!-- GENERATED by ktalk export — НЕ редактировать вручную -->`.
Содержит две таблицы (для git-видимости и disaster recovery):

**Необработанные записи** (`new`/`processing`/`partial`):
`recording_id | Название | Участники | Дата | Длительность | Статус`

**Обработанные записи** (`done`/`skipped`; по умолчанию текущий + предыдущий
месяц, `--full` — вся история):
`recording_id | Название | Дата | Статус | Дата обработки | Путь транскрипта | Путь протокола`

Это формат, который CLI **эмитит**, а не источник, который кто-то поддерживает руками.

## Формат участников

Участники хранятся в формате `Имя Фамилия (ktalk:ID)`, через запятую:

```
Имя Фамилия (ktalk:412), Имя Фамилия (ktalk:668)
```

Связка участника с профилем фиксируется командой
`ktalk set-vault-id <id> <ktalk_id> <vault_id>` на шаге 4.1 оркестратора
(если каталог профилей объявлен в `.ktalk.toml` хозяина).

## Формат транскрипта (сохраняемый файл)

```yaml
---
type: transcript
source: ktalk
recording_id: "ID"
title: "Название"
date: YYYY-MM-DD
participants:
  - Имя Фамилия (ktalk:ID)
  - Имя Фамилия (ktalk:ID)
---

# Название — YYYY-MM-DD

Текст транскрипта...
```

Путь сохранения — по шаблону `routing.transcript_archive` из `.ktalk.toml`
хозяина (`ktalk config show --json`); если ключ не объявлен — путь не
угадывается, шаг помечает это явно.

`type`: `1-1`, `committee`, `session`, `standup`, `status`, `other`

## Формат протокола (сохраняемый файл)

```yaml
---
type: meeting
subtype: {meeting_type}
recording_id: "ID"
title: "Название"
date: YYYY-MM-DD
duration_min: {N}
participants:
  - "[[{путь directories.people}/{id}/{id}|Имя Фамилия]]"
source: ktalk
transcript: "[[{путь по routing.transcript_archive}]]"
decisions_count: {N}
commitments_count: {N}
unclear_count: {N}
---
```

Фиксированные секции протокола (порядок не меняется) — см. `analysis-quality.md`
и `agents/references/protocol-template.md`.
