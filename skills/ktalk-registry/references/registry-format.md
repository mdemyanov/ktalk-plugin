# The ktalk registry data model

> **SQLite is the source of truth.** The markdown mirror of the registry is **no longer**
> maintained by hand and is **not** parsed as a source. It is generated by
> `ktalk export` (read-only).

## Operational store: SQLite

### Location

The path is resolved by the CLI package in this priority order: the `--db PATH` flag >
the `KTALK_REGISTRY_DB` environment variable > the path from the host project's `.ktalk.toml`
(`registry.db_path`, `ktalk config show --json`) > a machine default. This skill neither holds
nor assumes any particular path.

### Schema

```sql
recordings(
  recording_id PRIMARY KEY, name, date,            -- date = YYYY-MM-DD (дата записи)
  duration_min, status,                            -- new|processing|done|skipped|partial
  meeting_type,                                    -- 1-1|committee|session|standup|status|other
  transcript_path, protocol_path, processed_at,
  created_at, updated_at, raw_json
)
participants(
  recording_id REFERENCES recordings ON DELETE CASCADE,
  ktalk_id, name, vault_id,                         -- vault_id nullable
  PRIMARY KEY (recording_id, ktalk_id)
)
meta(key PRIMARY KEY, value)                        -- last_synced, sync_count, schema_version
```

WAL + `busy_timeout=5000` + one transaction per operation → concurrent background
`ktalk mark-*` calls are safe.

## The `ktalk` CLI surface

Every command supports `--json` (valid JSON on stdout; errors go to stderr with a non-zero
exit code).

| Command | Purpose |
|---|---|
| `ktalk config show` | The host project's layout (registry, directories, routes, integrations) |
| `ktalk sync [--days 7]` | Fetch recordings from ktalk, upsert new ones (`new`), expire, dashboard. Idempotent. |
| `ktalk dashboard` | New recordings plus statistics by status. |
| `ktalk list [--status S]` | The list of recordings, filtered. |
| `ktalk show <id>` | Recording details plus participants (ktalk_id, vault_id). |
| `ktalk mark-processing <id>` | → `processing` (by the agent, at the start). |
| `ktalk mark-done <id> --transcript P --protocol P [--type T]` | → `done`, paths + `processed_at`. |
| `ktalk mark-partial <id> [--transcript P] [--protocol P]` | → `partial`. |
| `ktalk mark-skipped <id>` | → `skipped`, manually. |
| `ktalk set-vault-id <id> <ktalk_id> <vault_id>` | Bind a profile to a participant. |
| `ktalk export [--out PATH] [--full]` | Regenerate the markdown mirror. |
| `ktalk migrate <vault> [--dry-run]` | One-off import from the old markdown registries. |
| `ktalk get-transcript <id> [--chunk N] [--chunk-size N]` | A recording's transcript (content reading). |
| `ktalk get-summary <id>` | A recording's summary (content reading). |

## Deduplication and expiration (done by the CLI)

- The unique key is `recording_id`; a repeated `sync` adds no duplicates (the upsert refreshes
  the content but does **not** reset `status` or the paths).
- Expiration: `new` records strictly older than N days (7 by default) become `skipped` on
  `sync`, and `processed_at` is filled in.

## Statuses

| Status | Meaning | Transition |
|--------|---------|------------|
| `new` | Discovered, not processed | → `processing`/`done`/`skipped` |
| `processing` | Taken by an agent | → `done`/`partial` |
| `done` | Transcript saved, updates written | Final |
| `skipped` | Skipped (older than N days, or manually) | Final |
| `partial` | Partially processed | → `done` once finished |

The "no profile" flag is a property of a participant (an empty `vault_id`), **not** a separate
status of the recording.

## The markdown mirror (generated by `ktalk export`)

`ktalk export` overwrites the markdown mirror of the host project's registry, with the warning
header `<!-- GENERATED by ktalk export — НЕ редактировать вручную -->`. It holds two tables,
for git visibility and disaster recovery:

**Unprocessed recordings** (`new`/`processing`/`partial`):
`recording_id | Название | Участники | Дата | Длительность | Статус`

**Processed recordings** (`done`/`skipped`; by default the current and the previous month,
`--full` — the whole history):
`recording_id | Название | Дата | Статус | Дата обработки | Путь транскрипта | Путь протокола`

This is the format the CLI **emits**, not a source anyone maintains by hand — the column
headers above are literal and stay Russian.

## Participant format

Participants are stored as `Имя Фамилия (ktalk:ID)`, comma-separated:

```
Имя Фамилия (ktalk:412), Имя Фамилия (ktalk:668)
```

A participant is bound to a profile by
`ktalk set-vault-id <id> <ktalk_id> <vault_id>` at orchestrator step 4.1 (if a profile
directory is declared in the host's `.ktalk.toml`).

## Transcript format (the saved file)

```yaml
---
type: transcript
source: ktalk
recording_id: "ID"
title: "Название"
date: YYYY-MM-DD
participants:
  - Имя Фамилия (ktalk:ID)
  - Имя Фамилия (ktalk:ID)
---

# Название — YYYY-MM-DD

Текст транскрипта...
```

The save path follows the `routing.transcript_archive` template from the host's `.ktalk.toml`
(`ktalk config show --json`); if the key is not declared, the path is not guessed — the step
says so explicitly.

`type`: `1-1`, `committee`, `session`, `standup`, `status`, `other`

## Protocol format (the saved file)

```yaml
---
type: meeting
subtype: {meeting_type}
recording_id: "ID"
title: "Название"
date: YYYY-MM-DD
duration_min: {N}
participants:
  - "[[{путь directories.people}/{id}/{id}|Имя Фамилия]]"
source: ktalk
transcript: "[[{путь по routing.transcript_archive}]]"
decisions_count: {N}
commitments_count: {N}
unclear_count: {N}
---
```

The protocol's fixed sections (the order never changes) — see `analysis-quality.md` and
`references/ktalk-processor/protocol-template.md`.
