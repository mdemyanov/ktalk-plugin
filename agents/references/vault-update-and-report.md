# Гибридное обновление и итоговый отчёт

Reference-файл `ktalk-processor.md` (шаги 6/7 ядра).

## Автоматически (без подтверждения)

**Профили участников** (только если `registry.directories.people` объявлен и
каталог существует — иначе шаг помечается недоступным, не выполняется наполовину):
- Добавить запись в секцию `История 1-1` (для встреч типа 1-1)
- Обновить/добавить строки в открытые договорённости профиля — формат:
  ```
  | {дата} | {договорённость} | {срок или —} | ⬜ не начато |
  ```
- Добавить `ktalk_id` в frontmatter профиля если отсутствует
- Указать источник: `> Обновлено на основе встречи "{название}" ({date})`

**Проекты** (только если `registry.directories.projects_active` объявлен):
- Добавить встречу в лог карточки проекта: `{путь}/{id}/{id}.md`
- Обновить статус существующей задачи если явно сказано, что она завершена

**Реестр (через CLI `ktalk`, не редактируя markdown):**

При успешной обработке — перевести запись в `done`, проставив пути и тип:

```
ktalk mark-done {recording_id} \
  --transcript {путь по registry.routing.transcript_archive} \
  --protocol {save_location} \
  --type {meeting_type}
```

Если протокол не создавался (`archive_only`) — опусти `--protocol`.

Если обработка получилась **частичной** (не удалось довести до конца, например
неполный транскрипт или прерванный анализ) — вместо `mark-done`:

```
ktalk mark-partial {recording_id} \
  --transcript {путь по registry.routing.transcript_archive} \
  [--protocol {save_location}]
```

CLI атомарно проставляет статус, пути и `processed_at`, обновляет SQLite-реестр.
Markdown-зеркало регенерируется оркестратором (`ktalk export`) — агенту трогать
его не нужно.

## С подтверждением (показать список → ждать ответа пользователя)

- Создать профиль нового человека (нет в каталоге профилей)
- Создать новый проект
- Закрыть или изменить статус проекта
- Создать архитектурное решение (ADR/decision record)
- Изменить приоритет в конфигурации проекта (если применимо)

Формат запроса подтверждения:
```
⚠️ Требует подтверждения:

1. Создать профиль: "Артём Пермяков" (ktalk:3197, упомянут в встрече)
2. Создать ADR: "Выбор Flowable для BPM движка" (обсуждали архитектурное решение)

Подтвердить все? (да/нет/выборочно: 1,2)
```

## Итоговый отчёт

```
✅ Встреча обработана: "{recording_name}" — {date}

Транскрипт:  {путь по registry.routing.transcript_archive, или пометка "маршрут не объявлен"}
Протокол:    {save_location или "не создавался"}

Автоматически обновлено:
  • {person}.md — добавлена договорённость: "{текст}" (срок: {дата или —})
  • {project}/{project}.md — добавлена встреча в лог
  • [если были обновления статусов задач]
  • [если каталог профилей/проектов не объявлен в .ktalk.toml — явная пометка здесь]

Требует внимания:
  • [UNCLEAR] {неясный момент} (⏱ {HH:MM:SS})
  • [если есть новые участники без профилей]
  • [если сопоставление участника с профилем недоступно — qmd и/или directories.people — явная пометка]

Флаги для владельца проекта:
  • [если есть — см. two-pass-analysis.md, пункт E]

Реестр обновлён: ktalk mark-done {recording_id} (статус → done)
```
