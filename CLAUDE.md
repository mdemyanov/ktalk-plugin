# ktalk — контекст проекта

Claude Code плагин для обработки записей встреч Контур.Толк: реестр, двухпроходный анализ, протоколирование, оценка качества анализа.

Правила рассуждения, стек и границы этого проекта. Роли и контракт вызова субагента — в `AGENTS.md`.

## Контекст проекта

Claude Code плагин `ktalk` — тонкая обёртка (ADR-012) над отдельно устанавливаемым
пакетом `ktalk-mcp`: здесь живут только промты и агенты, без кода обращения
к API, без секретов и без путей конкретного проекта-хозяина.

Помогает владельцам встреч Контур.Толк: реестр обработки записей, двухпроходный
анализ транскрипта и протокол встречи, оценка качества анализа, чтение
транскриптов и саммари, работа с расписанием (создание и отмена встреч по
санкции оператора).

## Стек

Плагин Claude Code: markdown-промты (`skills/`, `agents/`, `commands/`,
`references/`) плюс bash-скрипты в `scripts/`. Стороннего прикладного кода нет.

- Манифест плагина — `.claude-plugin/plugin.json`. Интерфейсной поверхности,
  кроме CLI, плагин не объявляет (ADR-022).
- Ключевая внешняя зависимость — пакет `ktalk-mcp`: CLI `ktalk` — единственный
  путь к контуру. Версионируется отдельно от плагина; `compat.json` называет
  точную требуемую версию, а не нижний порог.

## Команды сборки и проверки

Сборки нет — плагин ставится из git-источника marketplace. Проверки ручные:

```
bash scripts/test-onboard.sh              # тесты онбординг-скрипта
bash scripts/check-plugin-composition.sh  # состав плагина: нет путей/секретов хозяина
```

`check-plugin-composition.sh` — GO-критерий перед публикацией: ненулевой код
возврата означает провал сборки.

## Архитектурные правила

ADR-012 — тонкая обёртка:

- Прикладной код и обращения к API живут в пакете `ktalk-mcp`, не здесь. В дереве
  плагина — только промты, агенты, команды и вспомогательные bash-скрипты.
- CLI `ktalk` — единственный путь к контуру (ADR-012 §2а, доведено ADR-022).
  Никакой второй интерфейсной поверхности плагин не объявляет.
- В дереве не должно быть ни секретов, ни абсолютных путей, ни раскладки vault'а
  конкретного проекта-хозяина: всё это приходит параметрами от вызывающей стороны.
  Проверяется `scripts/check-plugin-composition.sh`.
- Схема исполнения — оркестратор (skill) → субагенты (`ktalk-processor`,
  `ktalk-evaluator`) с параметрами в промте.
- Версии плагина и `ktalk-mcp` независимы; совместимость фиксируется в `compat.json`.

## Справочные пути

- `README.md` — установка, предусловие `ktalk-mcp`, состав навыков.
- `CONTRIBUTING.md` — правила внесения изменений.

- `compat.json` — матрица совместимости версий плагина и пакета.

## Красные линии проекта

- **Ничего от хозяина в дереве плагина.** Ни секретов, ни токенов, ни абсолютных
  путей, ни раскладки конкретного vault'а, ни внутренних доменов. Перед публикацией
  — `bash scripts/check-plugin-composition.sh`; ненулевой код возврата блокирует сборку.
- **Запись в контур — только по явной санкции оператора.** Создание и отмена встреч
  проходят через preview и подтверждение; ни один навык не выполняет их одним шагом
  и не «досоглашает» за пользователя.
- **Транскрипты, саммари и профили участников — персональные данные.** Не покидают
  vault хозяина, не попадают в примеры, тесты, промты и коммиты этого репозитория.

## Требования к рассуждениям

1. **Действуй первым.** Нужна информация — читай, не спрашивай.
2. **Факты, не версии.** Приводи вывод инструмента, цитируй файл. Не проверил — не утверждай.
3. **Верифицируй перед выводом.** «Работает», «исправлено», «готово» без вывода команды — не результат.
4. **Лаконичность.** Проблема → решение → результат.

## Порядок работы

Ролевую работу ведут субагенты плагина `nauta`, координацию — главный контекст (`/nauta:pm`).
Канонический порядок: Researcher (опц.) → BA → SA → QA-author → Dev → QA-runner → приёмка BA →
DevOps (если есть деплой). Каталог ролей и контракт вызова субагента — в `AGENTS.md`.

## Правило трёх домов

- Переживёт закрытие эпика как ответ на «почему так» → `content/`.
- Машинно-проверяемый контракт поведения → `openspec/specs/<capability>/spec.md`.
- Живёт только внутри эпика (очередь, стадии, счётчики раундов, test-report) → стор задач,
  **никогда** не в `content/`.

Статья в `content/` и её capability-спека объявляют пару строкой `**Capability:**`.
Язык дельты («теперь стало», «раунд 3», «переделано после ревью») в постоянном документе запрещён.

## Красные линии (универсальные)

- НЕ публиковать секреты: `.env`, токены, API-ключи, credentials, приватные ключи. Содержимое
  каждого нового файла проверяется до `git add`; реальное значение вместо плейсхолдера — блокер.
- НЕ включать PII: реальные имена, контакты, персональные данные.
- НЕ менять `content/.doc-root.yaml` и схему properties без решения SA и ADR.
- НЕ создавать статьи в `content/` без обязательных properties.
- НЕ брать задачу `/nauta:dev` без предшествующего артефакта SA.
- НЕ передавать тесты в QA-runner до стабов QA-author.
- Тесты и линтеры (если в проекте есть) — зелёные перед коммитом.

## Объём

Пиши плотно: таблицы и списки вместо простыней, ведущее предложение несёт главное. Сумма строк
`CLAUDE.md` + `AGENTS.md` — предмет гейта объёма; порог живёт в `.nauta-gates.yaml`, и без этого
файла проверка молчит, а «Errors: 0» валидатора означает «не проверялось», не «нарушений нет».
